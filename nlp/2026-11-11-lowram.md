## 中文讲解

### 开场

这里是每日前沿文章。今天讲一篇华为诺亚方舟实验室伦敦团队和伦敦大学学院合作的论文，名字叫 LowRAM，讲的是怎么给大模型的 KV cache 瘦身。

它的出发点很简单，在同一个注意力头里，value 大部分可以从 key 推出来。既然推得出来，就没必要全部存下来。

### 问题

先说 KV cache 是什么。大模型一个 token 一个 token 往外生成的时候，前面每个 token 的 key 和 value 只算一次，存起来，后面每一步都拿来复用，这块缓存就叫 KV cache。

好处是省掉了大量重复计算，代价是显存。上下文越长，同时服务的请求越多，这块缓存就越大，长上下文的时候，它会成为运行时显存的大头，直接限制 batch size 和吞吐。

### 以前的方法

一类思路是改架构，比如线性注意力、状态空间模型，或者减少每个 token 缓存量的注意力变体。但这些都要预训练，或者大量微调，而现在大多数开源模型，用的还是带完整 KV cache 的分组查询注意力。

所以另一类方法，直接作用在训练好的模型上。主要有三种，驱逐，也就是把不重要的 token 扔掉，量化，也就是降低存储精度，还有低秩分解，用更小的矩阵去近似 KV。

作者指出，这三类方法利用的是不同方向的冗余，基本互不冲突。但 key 和 value 之间的冗余，还很少有人去用。

### 核心想法

key 和 value 是从同一个输入算出来的，只是乘了不同的投影矩阵。作用不一样，但出身相同，所以两者之间有可以预测的关系。

作者先做了一个对比实验，在 Mistral-7B 上，固定 3 倍压缩，试了好几种预测方向，比如用上一层的 key 预测这一层的 value，用这一层的 value 预测这一层的 key。结果是，用同一层的 key 去预测同一层的 value，在 LongBench 上保住的性能最多。

还有两个发现。一是重建 value 普遍比重建 key 效果好，二是重建误差小，不等于下游任务表现好，所以作者主要看下游表现做决策。

于是有了一个不对称的设计，value 用 key 来预测，key 本身则按它的低秩结构去压缩。

### 方法

先看 value 这一侧，作者叫它 value cache amortisation，可以理解为把 value 的存储摊销掉。在 prefill，也就是模型读入整段提示词的阶段，给每一层的每个 KV 头，现场训练一个很小的两层 MLP，输入 key，输出 value。

这个 MLP 还带一条线性旁路，初始值直接用模型自己的 key 和 value 投影矩阵算出来，用的是伪逆。这是借鉴 Slim Attention 的做法，相当于先拿到模型权重本身能给出的最好的线性近似，再让 MLP 学非线性的修正。

预测肯定不完美。所以作者算出每个 token 的重建误差，只给误差最大的那一部分 token，存下真实值和预测值之间的差，也就是残差。解码时，value 就等于 MLP 的预测，加上这些残差。

存多少残差，就是在显存和保真度之间做取舍。整个 value 缓存变成了两部分，一部分是 MLP 参数，和长度无关，是固定成本，另一部分是残差和它们的索引，随长度增长，但斜率比原来小得多。论文的分析显示，在 4 倍压缩下，固定成本只有在两三千 token 以下才占主导。

再看 key 这一侧。作者直接用了已有的方法 xKV，把相邻几层的 key 拼在一起，共享一组低秩基，因为相邻层的 key，主要方向很接近。压缩之前，还会先把位置编码 RoPE 反解掉，算注意力的时候再加回去。

这套方法有两个明显的开销。第一是 prefill 时要现场训练 MLP，主实验里每段上下文要做 150 步梯度更新。作者的办法是元学习，具体是一阶 MAML，离线学一个好的初始化，这样上线时只要 2 步更新。

第二是解码时，如果每一步都把整个缓存重建一遍，计算就吃不消。作者借鉴 ShadowKV，把上下文切成小块，每块用 key 的平均值当路标，每一步只重建和当前 query 最相关的那些块，另外少量异常块和最近的一段窗口，保持精确存储。

### 实验和效果

实验用了 Mistral-7B、Llama-3.1-8B 和 Qwen3.5-4B 三个模型，评测用长上下文基准 RULER 和 LongBench，结果都报告成相对于不压缩时的百分比。

先看表 1。在 Mistral 和 Llama 上，3 倍压缩保住了百分之 97.9 到 99.4 的性能。4 倍压缩时，大多在百分之 96.0 到 99.6 之间，例外是 Llama 在 RULER 上，掉到 93.9，作者认为是残差预算变少了。

Qwen3.5-4B 是混合架构，只有全注意力层有常规的 KV cache，所以只压缩这部分。它在 RULER 上和不压缩持平，在 LongBench 上保住百分之 94.4 到 97.8。

再看速度。用了元学习初始化之后，单看 value 这部分，首个 token 的延迟是不压缩的 1.3 倍，而现场训练 150 步是 26.3 倍，300 步是 55.5 倍。论文也说明，加上 key 的分解，完整流程的开销会比这个更高。

解码吞吐看这张图，Llama-3.1-8B，4 倍压缩。batch 小的时候，不压缩反而更快，但它很快就受限于显存，曲线走平，LowRAM 还能继续往上走。三种上下文长度下，LowRAM 都能跑到 batch 28，在 26 万多 token 的上下文上，峰值吞吐大约是不压缩的 5 倍。

这两个加速也有代价，看表 2，同样是 4 倍压缩。选择性重建基本不掉分，元学习初始化和 300 步的完整训练相比，在 RULER 上损失 1.4 到 4.4 个点，在 LongBench 长样本上损失 2.4 个点。两个都打开，RULER 保住百分之 92.4 到 96.8，LongBench 长样本是 92.9。

作者的建议是，一段上下文只问一次，就用元学习初始化，同一段上下文要反复问，比如文档问答、共享前缀的服务，就值得花时间完整训练，因为成本只付一次。

### 和以前方法的对比

LowRAM 还能和驱逐、量化叠在一起用。看表 3，Mistral 在 LongBench 上，4 倍的 LowRAM 再加上量化，压缩比到 6.4 倍，保住的性能反而从 97.9 升到 99.4。作者的解释之一是，残差用低精度存，同样的预算能多存一些残差。

但和驱逐叠加就没那么顺。驱逐把序列变短了，MLP 的固定成本却不变，留给残差的空间更少。比如 Llama 在 RULER 上，LowRAM 加驱逐压到 8 倍，只保住百分之 79.9。

再看表 4，在 LongBench 超过一万 token 的样本上，比较保住至少百分之 90 性能时，各方法最多能压多少。Mistral-7B 上，单用驱逐是 10 倍，量化是 7.5 倍，LowRAM 是 9 倍，三者叠加能到 26.9 倍，还保住百分之 94.5。

只看 value 这一侧的对比在表 5。key 保持精确，在 Llama-3.1-8B 上，把 MLP 预测和 xKV 这种低秩方法分别用在 value 上。4 倍压缩时，MLP 预测在 RULER 上保住 98.2，在 LongBench 上保住 99.3。xKV 在 RULER 的高压缩比上略好一点，但在 LongBench 上，每个压缩比都是 MLP 预测领先。

消融实验说明了哪些部件最关键，看表 7，Mistral-7B，value 压缩 3 倍。去掉残差，从 99.0 掉到 64.9，换成线性预测器，只剩 57.5，一层里所有头共用一个 MLP，掉 19.5 个点，说明每个头从 key 到 value 的映射很不一样。

残差给谁也很关键。看图 5，同样的残差预算，随机挑 token，在大海捞针任务上得分不到 40，按重建误差挑，能到 98。

我的判断是，这篇最有价值的是那个观察本身，key 和 value 应该分开对待。它提供的是一个新的压缩维度，可以和量化、驱逐叠加，而不是替代它们。

我的判断是，对比也有不足。驱逐和量化各只选了一个代表方法，同样做预测加残差的 AQUA-KV，论文只在自己的框架里复现了它考察过的预测方向，端到端结果里没有和它直接比较。

### 局限

作者自己说的局限，首先是没有评测长文本生成。现在 MLP 是在 prefill 时一次拟合的，新生成的 token 直接精确存着，如果输出很长，就需要每隔一段重新压缩一次。

其次，LowRAM 适合长上下文。MLP 参数是固定成本，几千 token 之后才摊得开，所以它在 4K 长度的 RULER 上掉得比 LongBench 多，和驱逐叠加时效果也没那么干净。

另外从实验设置看，prefill 时要训练，速度和精度之间要做取舍，而且实验只覆盖了 40 亿到 80 亿参数的模型。

### 未来方向

作者想弄清楚，key 到 value 的关系有多少是跨上下文共用的，有多少是每段上下文特有的，以及难预测的 token 在不同上下文里是否稳定。弄清楚这些，可以更有效地分配显存和计算。

我的判断是，最值得关注的落地场景是共享前缀和长文档问答，同一段上下文被反复查询，训练成本只付一次。如果后续能在更大的模型和长输出上验证，它会是推理服务里很实用的一层压缩。

## English walkthrough

### Intro

This is Daily Frontier Papers. Today's paper comes from Huawei's Noah's Ark Lab in London and University College London. It's called LowRAM, and it's about shrinking the KV cache of large language models.

The starting point is a simple observation. Inside a single attention head, the values can mostly be predicted from the keys. And if you can predict something, you don't need to store all of it.

### Problem

Quick refresher on the KV cache. When a model generates text one token at a time, it computes the key and value for every earlier token once, stores them, and reuses them at every later step. That store is the KV cache.

It saves a huge amount of recomputation, but it costs memory. The cache grows with context length and with the number of requests you serve at once, and at long contexts it dominates the model's activation memory. That caps your batch size and your throughput.

### Prior work

One response is to change the architecture: linear attention, state-space models, or attention variants like grouped-query and multi-head latent attention that store less per token. But those need pretraining or heavy finetuning, and most open-weight models still use grouped-query attention with a full KV cache.

So a second line of work compresses the cache of a frozen, already-trained model. There are three main families. Eviction throws away unimportant tokens. Quantisation stores entries at lower precision. And low-rank decomposition approximates the cache with smaller factorised matrices.

The authors point out that these families exploit redundancy along different axes, so they largely don't overlap. What's been left mostly untouched is the redundancy between keys and values.

### Key idea

Keys and values are computed from the same input, just through different projection matrices. They do different jobs, but they share an origin, and that makes the relationship between them predictable.

The authors first ran a comparison on Mistral-7B at a fixed three-times compression. They tried several prediction directions, such as predicting this layer's values from the previous layer's keys, or this layer's keys from this layer's values. The winner was predicting a layer's values from that same layer's keys. It kept the most LongBench performance.

This figure shows two more things. Reconstructing values generally works better than reconstructing keys. And a lower reconstruction error doesn't necessarily mean better downstream performance, so the authors base their design choices mainly on downstream results.

That leads to an asymmetric design. Values are predicted from keys, while the keys themselves are compressed using their low-rank structure.

### Method

Start with the values. The authors call this value cache amortisation. During prefill, when the model reads in the whole prompt, they fit a tiny two-layer MLP for every KV head in every layer. Keys go in, values come out.

The MLP also has a linear side branch, initialised straight from the model's own key and value projection matrices using a pseudoinverse. That idea comes from Slim Attention. It gives the best linear map the model's weights can offer, and the MLP learns a non-linear correction on top.

The prediction won't be perfect. So the method measures the reconstruction error of every token and stores the residual, the difference between the true value and the prediction, only for the tokens with the largest errors. At decoding time, a value is the MLP's prediction plus any stored residual.

How many residuals you keep is the memory-versus-fidelity dial. The value cache now has two parts. The MLP parameters are a fixed cost that doesn't depend on length. The residuals and their indices grow with length, but much more slowly than the original cache. The paper's analysis shows that at four-times compression, the fixed cost only dominates below roughly two to three thousand tokens.

Now the keys. Here the authors reuse an existing method, xKV. It stacks the keys of several adjacent layers and shares one low-rank basis across them, since neighbouring layers have similar dominant directions. Before compressing, they also undo the rotary position encoding, RoPE, and reapply it at attention time.

This has two obvious costs. The first is training the MLP during prefill. The main experiments use one hundred and fifty gradient updates per context. The fix is meta-learning, specifically first-order MAML, to learn a good initialisation offline, so that at inference only two updates are needed.

The second is decoding. Rebuilding the whole cache at every step would eat up the compute you saved. Borrowing from ShadowKV, they split the context into small chunks, use each chunk's mean key as a landmark, and at each step rebuild only the chunks most relevant to the current query. A few outlier chunks and a recent window are kept exact.

### Results

The experiments use three models, Mistral-7B, Llama-3.1-8B and Qwen3.5-4B, on the long-context benchmarks RULER and LongBench. Every result is reported as a percentage of the uncompressed baseline.

Table 1 first. On Mistral and Llama, three-times compression keeps between ninety-seven point nine and ninety-nine point four percent of baseline. At four times, recovery stays between ninety-six and ninety-nine point six, except Llama on RULER, which falls to ninety-three point nine. The authors put that down to the smaller residual budget.

Qwen3.5-4B is a hybrid model, and only its full-attention layers keep a conventional KV cache, so only those are compressed. It matches the baseline on RULER and keeps ninety-four point four to ninety-seven point eight percent on LongBench.

Now speed. With the meta-learned initialisation, the value part alone adds a time-to-first-token overhead of one point three times the baseline, compared with twenty-six point three times at one hundred and fifty updates, and fifty-five point five times at three hundred. The paper notes that the full pipeline, with key factorisation, costs more than that.

Decode throughput is in this figure: Llama-3.1-8B at four-times compression. At small batch sizes, the uncompressed baseline is actually faster. But it quickly becomes memory-bound and flattens out, while LowRAM keeps climbing. LowRAM runs batch size twenty-eight at all three context lengths, and at about two hundred and sixty thousand tokens it reaches roughly five times the baseline's peak throughput.

Those speedups have a price, shown in Table 2, again at four-times compression. Selective reconstruction costs almost nothing. The meta-learned initialisation, compared with full three-hundred-update fitting, costs one point four to four point four points on RULER and two point four on the long LongBench samples. With both switched on, RULER recovery is ninety-two point four to ninety-six point eight percent, and long LongBench is ninety-two point nine.

The authors' advice: if a context is queried once, use the meta-learned initialisation. If the same context serves many queries, as in document question answering or shared-prefix serving, full fitting is worth it, because you pay that cost only once.

### Comparison

LowRAM also stacks with eviction and quantisation. In Table 3, for Mistral on LongBench, adding quantisation to four-times LowRAM pushes compression to six point four times, and recovery actually goes up, from ninety-seven point nine to ninety-nine point four. One reason the authors give: storing residuals at lower precision lets you keep more of them within the same budget.

Eviction is a rougher fit. It shortens the sequence but leaves the MLP's fixed cost unchanged, so there's less room for residuals. Llama on RULER with LowRAM plus eviction at eight times keeps only seventy-nine point nine percent.

Table 4 looks at LongBench samples longer than ten thousand tokens, and asks how far each method can compress while keeping at least ninety percent of baseline. On Mistral-7B, eviction alone reaches ten times, quantisation seven point five, and LowRAM nine. All three stacked reach twenty-six point nine times, while keeping ninety-four point five percent.

Table 5 isolates the value side. Keys are kept exact, and on Llama-3.1-8B, the MLP predictor and the low-rank method xKV are each applied to the values. At four times, the predictor keeps ninety-eight point two on RULER and ninety-nine point three on LongBench. xKV is slightly ahead on RULER at the higher ratios, but on LongBench the predictor leads at every ratio.

The ablations in Table 7, Mistral-7B at three-times value compression, show which parts matter. Remove the residuals and recovery drops from ninety-nine to sixty-four point nine. Swap in a linear predictor and it's fifty-seven point five. Share one MLP across all heads in a layer and you lose nineteen point five points, which suggests each head has its own key-to-value geometry.

Which tokens get residuals matters too. In Figure 5, with the same residual budget, picking tokens at random scores under forty on a needle-in-a-haystack task. Picking them by reconstruction error reaches ninety-eight.

My read is that the most valuable thing here is the observation itself: keys and values should be treated differently. It adds a new compression axis that stacks with quantisation and eviction rather than replacing them.

My read is that the comparisons also have gaps. Eviction and quantisation are each represented by a single method, and AQUA-KV, which also predicts and stores residuals, only appears as prediction directions re-run inside the authors' own framework, not as a direct end-to-end baseline.

### Limitations

The authors' own limitations come first. They haven't evaluated long generations. The MLP is fitted once at prefill and newly generated tokens are stored exactly, so long outputs would need periodic re-compression.

Second, LowRAM is suited to long contexts. The MLP parameters are a fixed cost that only pays off after a few thousand tokens, which is why it loses more on four-thousand-token RULER than on LongBench, and why it combines less cleanly with eviction.

And from the setup itself: prefill involves training, so you trade speed against accuracy, and the experiments only cover models from four to eight billion parameters.

### Future work

The authors want to understand how much of the key-to-value relationship is shared across contexts and how much is specific to each one. Warm-starting and the Slim initialisation help, which points to a shared part. Test-time fitting still adds more, which points to a specific part. They also ask whether hard-to-predict tokens are stable across contexts. Answering that could make memory and compute allocation more efficient.

My read is that the place to watch is shared prefixes and long-document question answering, where one context is queried again and again and the fitting cost is paid once. If it holds up on bigger models and long outputs, this could be a very practical extra layer of compression for inference serving.
