## 中文讲解

### 开场

这里是每日前沿文章。今天讲一篇高丽大学、KAIST 和 Google Cloud AI Research 合作的论文，名字叫 CEPO，讲的是怎么给多智能体系统自动优化 prompt。

一句话概括，它不发明新的优化器，而是改变 prompt 的结构，再告诉现有的优化器，每一部分该往哪个方向改。

### 问题

先说背景。多智能体系统，就是让好几个大模型 Agent 分工合作，比如一个读文字，一个看图，一个负责汇总，一起回答一个问题。

这种系统要做好，需要两件事。每个 Agent 把自己那份活干好，这叫执行。Agent 之间配合得好，这叫协调。

而每个 Agent 怎么干活、怎么配合，都写在它的 prompt 里。prompt 写得好不好，直接影响整个系统的效果。

### 以前的方法

手写 prompt 很费劲，所以有了 prompt 优化，让一个大模型根据失败案例反复改写 prompt，再用验证集挑出最好的版本。论文用到的 PE2、OPRO、ProTeGi 都是这类通用方法，MASPO 则是专门为多智能体设计的。

作者指出的问题是，这些方法通常只改每个 Agent 自己的 prompt，协调规则和执行细节，混在同一段文字里。

这样一来，想改一条大家都该遵守的协调规则，就得在好几个职责不同的 prompt 里分别改，还要保持一致。

论文图 1 的左边就是这个对比。以前的做法，协调和执行耦合在每个 Agent 的 prompt 里，优化时也不区分角色。

### 核心想法

CEPO 的想法分两层。第一层，把 prompt 拆开，拆成一份所有 Agent 共享的协调者 prompt，加上每个 Agent 自己的执行者 prompt。

协调者 prompt 写系统层面的规则，比如怎么分享发现，遇到分歧怎么标出来，怎么给后面的环节留信息。执行者 prompt 写这个 Agent 具体怎么干活。

第二层，叫角色对齐的优化。改协调者 prompt 的时候，给优化器一段专门的元指令，引导它关注团队协作。改执行者 prompt 的时候，换另一段元指令，引导它关注这个 Agent 怎么完成任务。

元指令，就是写给优化器看的说明书，告诉它这次改 prompt 要往哪里改。表 1 摘录了这两段说明书的原文。

### 方法

具体怎么用。每次调用某个 Agent，实际给它的 prompt，就是把共享的协调者 prompt，拼在它自己的执行者 prompt 前面。

这样改一次协调者 prompt，所有 Agent 同时收到同样的新规则。改某个执行者 prompt，只影响这一个 Agent。

要注意，两层 prompt 最后都是用同一个系统整体的验证分数来挑选的。元指令只给出不同的修改方向，并没有定义两个不同的数值目标。

优化分两个阶段。第一阶段，固定所有执行者 prompt，只优化协调者 prompt，跑几轮，用验证分数挑出最好的一版。

第二阶段，把选好的协调者 prompt 固定住，再去优化指定的一部分执行者 prompt。图 2 画的就是这个流程。

底层用哪个优化器都可以，PE2、OPRO、ProTeGi、MASPO 都能直接接进来，CEPO 只负责 prompt 的结构和优化方向。

作者在附录里也比较了不同的顺序。在他们的文档实验里，先协调者、后执行者效果最好，交替着优化要差一些。

### 实验和效果

实验覆盖四个领域、11 个基准，包括文档理解、数学推理、代码生成和长视频理解。

文档理解用了两个现成的多智能体系统。MDocAgent 有五个 Agent，底座是 Qwen-3.5 的 4B 模型。DocAgent 有三个 Agent，底座是 GPT-5-mini。优化器用的是 PE2，由 GPT-5.4 来改写 prompt。

结果在表 2。两个系统在五个文档基准上全部提高，平均分分别提高 4.3 和 2.7 个百分点。

提升最大的是 DocAgent 在 MMLongBench-Doc 上，从 59.5 提到 67.4，高了 7.9 个百分点。

数学和代码，用的是 MASPO 论文里基于 Qwen3-8B 的多智能体系统。表 3 显示，单用 MASPO，平均分从 68.82 提到 72.85，再加上 CEPO 是 73.89，五个基准都比单用 MASPO 高。

长视频理解，表 7 显示，LongVideoAgent 原本是 60.3，用 PE2 优化后是 63.4，加上 CEPO 是 64.9。

换不同优化器的结果在表 8。在 MDocAgent 上，PE2、ProTeGi、OPRO 三种优化器加上 CEPO 之后，五个文档基准全部比单用优化器高，幅度在 0.6 到 6.5 个百分点之间。

### 和以前方法的对比

再看拆解实验，在 MDocAgent 和 MMLongBench-Doc 上，见表 4。基线是 54.1，只加一份大模型生成、没经过优化的协调者 prompt，是 55.6。

只优化执行者 prompt，也就是普通的 PE2，是 57.9。只优化协调者 prompt，是 58.6。两层都优化，并且用角色对齐的元指令，是 61.0。

元指令对调的实验在表 6。协调者用协调指令、执行者用执行指令，是 61.0。反过来用，是 57.7，最差。两层用同一种指令，结果在两者之间。

成本方面看表 5。CEPO 每层只优化 1 轮，就到了 60.1，比普通 PE2 优化 3 轮的 57.9 还高，API 调用也更少。调用量相近的时候，CEPO 是 61.0，PE2 优化 6 轮反而是 57.4。

作者还排除了一个疑问，是不是 prompt 更长就更好。把普通 PE2 的 prompt 放长到和 CEPO 差不多，准确率反而降到 54.0，比不优化的 54.1 还低。

还有一个现象，看图 3。Agent 从 1 个加到 5 个，不优化的系统几乎没有提升，普通 PE2 忽高忽低，3 个 Agent 时还低于不优化。CEPO 的分数随 Agent 数量单调上升，领先基线的幅度，从 2 个 Agent 时的 3.9，扩大到 5 个时的 6.9。

图 4 是优化出来的 prompt 的样子。协调者 prompt 从一段笼统的系统介绍，变成了团队规则，比如证据冲突时要明确标出来，自己答不全时要说明还缺什么。执行者 prompt 变成了具体的操作步骤，比如表格题先筛行、再取列。

我的判断是，这篇的价值在于把一个工程上常见的直觉，变成了可以复用的结构。共享规则单独放、单独改，现有的优化器不用改就能用上，接入成本很低。

### 局限

论文没有单独的局限章节，下面几点来自论文自己报告的结果。

第一，提升并不均匀。在 LongDocURL 上，两个系统分别只提高了 0.5 和 0.3 个百分点。

第二，成本、Agent 数量、元指令对调这些分析，都只在 MDocAgent 加 MMLongBench-Doc 这一个组合上做。

第三，多优化不一定更好。每层的优化轮数从 3 加到 4，准确率从 61.0 掉到 58.6。要优化的执行者从一个增加到多个，也没有进一步提升，所以 MDocAgent 上默认只优化一个，就是给出初始答案的 GENERAL Agent。

第四，文档基准没有自带训练集，作者把测试集按文档切成 10、10、80 三份，表里的文档分数，是在自己切出的测试集上、由 GPT-5-mini 判对错算出来的。作者报告，基线在这个切分上的分数和原测试集很接近。

第五，协调者的元指令是针对具体系统写的，附录里 MDocAgent 和 DocAgent 各用一份，内容贴着各自的流程。

另外，作者说计划在论文被接收后公开完整代码。

### 未来方向

作者明确留给以后的，是多个执行者 prompt 的联合优化。附录里还有一个结果，在 MMLongBench-Doc 上优化出来的协调者 prompt，直接搬到另外四个文档基准上，平均 69.3，比在各自数据集上专门优化的 71.6 低 2.3 个百分点，说明协调规则有一定的可迁移性。

我的判断是，接下来最值得看的，是这套结构能不能用在更开放的 Agent 任务上，比如浏览网页、操作软件这类要和环境多轮交互的场景，以及元指令本身能不能也自动生成，而不是每个系统单独写一份。

## English walkthrough

### Intro

This is Daily Frontier Papers. Today's paper comes from Korea University, KAIST and Google Cloud AI Research. It's called CEPO, and it's about automatically optimizing the prompts of a multi-agent system.

The short version: it doesn't invent a new optimizer. It changes how the prompts are structured, and then tells an existing optimizer which direction each part should move in.

### Problem

Some background first. A multi-agent system splits one job across several language-model agents. One reads the text, one looks at the images, one writes the final answer, and together they answer a question.

To work well, the system needs two things. Each agent has to do its own job well. Call that execution. And the agents have to work well together. Call that coordination.

Both of those live in each agent's prompt. So the quality of the prompts has a direct effect on how well the whole system performs.

### Prior work

Writing those prompts by hand is tedious, which is why prompt optimization exists. A language model looks at failure cases, rewrites the prompt, and a validation set picks the best version. The paper uses PE2, OPRO and ProTeGi, which are general-purpose methods of this kind, and MASPO, which was built specifically for multi-agent systems.

The authors' complaint is that these methods typically edit only each agent's own prompt. Coordination rules and execution details end up tangled in the same block of text.

So if you want to change one rule that every agent should follow, you have to make that change in several prompts with different jobs, and keep them consistent.

Figure one, on the left, shows the contrast. In prior work, coordination and execution are coupled inside each agent's prompt, and the optimizer treats every prompt the same way.

### Key idea

CEPO works on two levels. The first is to split the prompt into one coordinator prompt that every agent shares, plus a separate executor prompt for each agent.

The coordinator prompt holds system-level rules, like how to share findings, how to flag a disagreement, and what to pass on to later stages. The executor prompt says how this particular agent should do its task.

The second level is what they call role-aligned optimization. When the optimizer edits the coordinator prompt, it gets one meta-instruction that points it at teamwork. When it edits an executor prompt, it gets a different one that points it at how that agent carries out its task.

A meta-instruction is simply a brief written for the optimizer, telling it what this round of edits is supposed to improve. Table one quotes excerpts from both.

### Method

Here's how it runs. Whenever an agent is called, the prompt it actually sees is the shared coordinator prompt placed in front of its own executor prompt.

That means one edit to the coordinator prompt reaches every agent at once, while an edit to an executor prompt only changes that one agent.

One detail matters here. Both layers are still selected by the same system-level validation score. The meta-instructions steer the edits in different directions, but they don't define two separate numerical objectives.

Optimization has two phases. In phase one, all the executor prompts are frozen and only the coordinator prompt is optimized for a few rounds. The validation score picks the best version.

In phase two, that coordinator prompt is frozen, and a chosen subset of executor prompts gets optimized. Figure two lays out the whole pipeline.

Any optimizer can sit underneath. PE2, OPRO, ProTeGi and MASPO all plug in directly. CEPO only supplies the prompt structure and the guidance.

The appendix also compares schedules. In their document experiments, coordinator first and executors second worked best, and alternating between the two did worse.

### Results

The experiments cover eleven benchmarks in four areas: document understanding, math reasoning, code generation and long-video understanding.

For documents they use two existing multi-agent systems. MDocAgent has five agents running on a four-billion-parameter Qwen three point five model. DocAgent has three agents running on GPT-5-mini. The optimizer is PE2, with GPT-5.4 doing the rewriting.

Table two has the results. Both systems improve on all five document benchmarks, with average gains of four point three and two point seven points.

The biggest jump is DocAgent on MMLongBench-Doc, from fifty-nine point five to sixty-seven point four, a gain of seven point nine points.

For math and code they use the Qwen3 eight-billion-based multi-agent system from the MASPO paper. In table three, MASPO alone lifts the average from sixty-eight point eight two to seventy-two point eight five. Adding CEPO takes it to seventy-three point eight nine, and it beats MASPO alone on all five benchmarks.

On long video, table seven shows LongVideoAgent starting at sixty point three, reaching sixty-three point four with PE2, and sixty-four point nine with CEPO on top.

Table eight swaps the optimizer. On MDocAgent, adding CEPO to PE2, ProTeGi or OPRO beats the optimizer alone on every one of the five document benchmarks, by between zero point six and six point five points.

### Comparison

Now the ablations, on MDocAgent with MMLongBench-Doc, in table four. The baseline is fifty-four point one. Just adding a coordinator prompt written by a language model, with no optimization, gives fifty-five point six.

Optimizing only the executor prompt, which is plain PE2, gives fifty-seven point nine. Optimizing only the coordinator gives fifty-eight point six. Optimizing both, with role-aligned meta-instructions, gives sixty-one point zero.

Table six swaps the meta-instructions. Coordination guidance on the coordinator and execution guidance on the executor gives sixty-one point zero. Swapping them gives fifty-seven point seven, the worst result. Using the same guidance for both lands in between.

On cost, look at table five. CEPO with a single round per layer already reaches sixty point one. That beats plain PE2 with three rounds, at fifty-seven point nine, and uses fewer API calls. At a similar number of calls, CEPO reaches sixty-one point zero, while PE2 with six rounds actually drops to fifty-seven point four.

The authors also check whether longer prompts are the real reason. When plain PE2 is allowed to write prompts about as long as CEPO's, accuracy falls to fifty-four point zero, just below the unoptimized fifty-four point one.

There's one more pattern, in figure three. Going from one agent to five, the unoptimized system barely improves, and plain PE2 bounces around, even dipping below the unoptimized system at three agents. CEPO rises steadily with each added agent, and its lead over the baseline grows from three point nine points with two agents to six point nine with five.

Figure four shows what the optimized prompts look like. The coordinator prompt goes from a generic system description to team rules, like flagging conflicting evidence explicitly and saying what's still unresolved when you can't fully answer. The executor prompt becomes a concrete procedure, like filtering the table rows first and then pulling the requested column.

My read is that the value here is turning a common engineering instinct into a reusable structure. Shared rules get their own slot and their own edits, and existing optimizers can use it without modification, so the cost of adopting it is low.

### Limitations

The paper has no separate limitations section, so the points below come from results the paper itself reports.

First, the gains are uneven. On LongDocURL, the two systems improve by only zero point five and zero point three points.

Second, the analyses of cost, agent count and the meta-instruction swap are all run on a single setup: MDocAgent on MMLongBench-Doc.

Third, more optimization isn't always better. Raising the rounds per layer from three to four drops accuracy from sixty-one point zero to fifty-eight point six. Optimizing more than one executor doesn't help further either, so on MDocAgent the default optimizes just one, the GENERAL agent that produces the initial answer.

Fourth, the document benchmarks have no training sets, so the authors split each test set by document into ten, ten and eighty percent. The document scores are measured on their own test split, with GPT-5-mini judging correctness. They report that baseline scores on this split are close to those on the original test sets.

Fifth, the coordinator meta-instructions are written for specific systems. The appendix shows one for MDocAgent and another for DocAgent, each tailored to its own pipeline.

And the authors say they plan to release the full codebase once the paper is accepted.

### Future work

What the authors explicitly leave for later is optimizing several executor prompts jointly. The appendix also has a transfer result: a coordinator prompt optimized on MMLongBench-Doc and moved unchanged to four other document benchmarks averages sixty-nine point three, against seventy-one point six for prompts optimized on each dataset, a gap of two point three points, so the coordination rules carry over to some degree.

My read is that the thing to watch next is whether this structure holds up on more open-ended agent work, such as browsing the web or operating software, where agents interact with an environment over many turns, and whether the meta-instructions themselves can be generated automatically instead of written separately for each system.
