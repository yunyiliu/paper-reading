## 中文讲解

### 开场

这里是每日前沿文章。今天讲一篇阿里巴巴 MAI-UI 团队的论文，叫 MAI-Gym，一个给 GUI Agent 做评测和强化学习训练的开源平台。

GUI Agent，就是看着屏幕截图，像人一样点击、输入，去操作手机和电脑的模型。作者还用这个平台训出了一个 9B 模型，称它在两个主流基准上，是 10B 以下开源 GUI Agent 里最好的。

### 问题

先说问题。在数学和写代码上，带可验证奖励的强化学习进步很快，因为这些环境便宜，答案好检查，任务也多。

GUI Agent 难在两点。第一，环境贵。Agent 操作的是整块屏幕，还会改动设备上的文件和设置，所以每一次尝试，都要一台独立的手机、电脑或者浏览器，从确定的初始状态开始。

而且评测和训练往往各写一套 Agent 代码，时间长了就对不上。比如训练时保留最近五张截图，评测时保留十张，评测的其实是另一个 Agent。

第二，缺真实的任务。真实工作常常跨好几个应用，比如回邮件告诉对方附件发票的总金额，这要求邮件、附件和发票在环境里同时存在，而且彼此一致。涉及付款、下单的真实应用，更没法拿来反复练。

### 以前的方法

以前的工作大概分两类，论文这张表做了对比。一类偏基础设施，让评测或训练容易复现，但每个只覆盖一个平台，公开了训练代码的，并行环境最多也就几百个。

另一类偏数据，造了很多新应用和新任务，但既不公开训练代码，也没法跑现有的基准。而且任务往往只基于单个输入文件，或者同一个应用里所有任务共用的样例数据。

### 核心想法

MAI-Gym 的核心设计，是一条共享的 rollout 路径，rollout 就是让 Agent 完整跑一遍任务。评测、收集数据和训练，共用同一套截图处理、上下文构造和动作执行代码，修一处，三处同时生效。

另一半是自动合成。用编程 Agent 造出可以重置的模拟应用，先搭一个前后一致的世界，再从里面出题，模型在哪里失败，就针对哪里出新题。

### 方法

先看架构图。左边是评测和训练共用的 harness 和 rollout 路径，harness 指模型和环境之间那层代码。中间是环境管理器，对外只有请求实例、观察、重置、执行一步和打分五个操作。右边是托管在 Kubernetes 或 Docker 上的各种实例。

规模上，论文说他们跑过两万个环境实例同时并行。一千个全新实例启动，手机端用了 328.4 秒，电脑端 88.9 秒。

还有一个省算力的细节，叫窗口式历史。常见做法只保留最近 k 张截图，每走一步，最老的那张被丢掉，提示词开头一变，推理引擎的 KV cache 就几乎全部作废。

MAI-Gym 把步骤分成每十步一个窗口，窗口之间重叠两步。窗口内只往后追加，缓存可以复用，到了窗口边界，旧截图换成占位符，文字保留。

表 6 里，和逐步的做法相比，前缀缓存命中率从 42.5% 提到 85.9%，每条轨迹的训练输入 token 少了 84.7%，一次训练更新的时间少了 62.6%，代价是 rollout 速度慢了 18.9%。

再看合成。第一种是真实应用的克隆，12306、建设银行、滴滴、美团、大众点评、抖音、小红书，一共七个，都是会花钱、下单或者发帖的应用。编程 Agent 照着真实应用从零做出克隆，后台每次都能重置。这张图上面是真实界面，下面是克隆。

第二种是全新发明的应用，任何模型都不可能见过，用来研究 Agent 能不能靠交互学会陌生界面。每个都是确定性的状态机，结果完全可复现。论文公开了 49 个模拟应用，其中新应用 42 个，带 840 个任务。

任务怎么来。先用一个人物设定和一个场景，生成一整套共享人物、事件和事实的文件和应用记录，比如项目简介、预算表、邮件和日历，说的是同一个项目。

这样任务就不是新建一个叫预算评审的日程，而是把预算评审挪到修订版预算表截止的第二天，Agent 得先读邮件和表格，再去改日历。

验证器的做法比较讲究。先把需求和预期答案写定，再由两次互相独立的生成，分别写出标准答案代码和验证代码，前者直接把环境设成完成状态，后者检查结果，两边看不到对方的输出。

然后实际执行，验证器在初始状态必须打 0 分，跑完标准答案必须打 1 分，重置后又回到 0 分。再让几个模型真的通过界面去做，检查任务能不能做、难度和被钻空子的风险。论文强调，模型可以帮忙造题审题，但强化学习的奖励只来自验证器的执行结果。

训练用的是 GRPO，每个任务做几次，用组内平均分做基线。全对或全错的组没有梯度，所以调度器会估计每个任务的成功率，从没做对过的，和成功率超过 80% 的，只分配少量尝试，把算力留给时对时错的任务。

### 实验和效果

实验设置。MAI-Gym-9B 从 Qwen3.5-9B 出发，先用手机和电脑的混合数据做监督微调热身，再在手机和电脑任务上做一次联合强化学习。

训练用了 5000 个合成任务，512 张 GPU，峰值两万个并发环境，大约训练 96 个小时。奖励只来自代码验证器。

评测有七个基准。MobileWorld 和 OSWorld-Verified 的环境在训练里出现过，但题目没有。另外五个，包括 AndroidWorld、MacAgentBench 这些，环境本身就没训练过。

主结果在表 4。MobileWorld 是 78.4%，OSWorld-Verified 是 76.2%，基座模型分别是 18.0 和 41.8。

和同样 9B 的 UI-Venus-2-9B 比，两项分别高 3.2 和 5.4 个点。在 MobileWorld 上，它还超过了论文列出的 Claude Opus 4.8 的 69.2、GPT-5.5 的 62.4 和 Qwen3.8-Max 的 77.8。

这张图把提升拆开了。大部分提升来自监督微调热身，两个题目没见过的基准，平均分从 29.9 提到 66.4。强化学习再把整体平均从 44.1 提到 50.5，而且五个没训练过的环境，每一个都有提升。

再看迁移。只在 12306 的克隆里做强化学习，用 52 个配对任务测，克隆里的成功率从 36.5% 提到 73.1%，真实手机上的真 12306，从 28.8% 提到 48.1%，提高了 19.2 个百分点。

全新应用上，训练 252 个任务，在 62 个没见过的任务上测，成功率从 25.8% 提到 45.2%，平均步数从 33.3 降到 16.4。没有任何演示，只靠验证器的奖励。

合成任务的数量也有用。在同样的 rollout 预算下，任务从 500 个加到 5000 个，MobileWorld 从 69.2% 提到 78.4%，OSWorld-Verified 从 69.7% 提到 76.2%。

### 和以前方法的对比

先和一种常见做法比，每个领域单独做强化学习，再把两个专家模型的参数加权平均。

表 7 里，从同一个热身模型出发，总预算相同，最好的合并在 MobileWorld 上是 76.4，在 OSWorld-Verified 上是 74.8，还来自不同的合并比例。联合训练两项都更高，是 78.4 和 76.2。

但也要看清差距。在 OSWorld-Verified 上，Claude Opus 4.8 是 83.4，Qwen3.8-Max 是 86.1，397B 的 Qwen-CUA 是 86.2，都比它高。没训练过的电脑环境差得更多，MyPCBench 上它是 15.2，Claude Opus 4.8 是 62.0，OSWorld 2.0 的二元成功率只有 3.7。

还有，表里大部分基线分数来自已发表的报告和排行榜，只有八个是作者自己跑的。而论文自己也说，光是换一个 harness，同一个模型的分数就会变。

我的判断是，这篇真正的价值在平台，不在 9B 的分数。评测训练共用一条路径，奖励只来自执行过的验证器，针对的正是 GUI 强化学习最容易出错的地方。

我的判断是，克隆迁移这个结果，对付款、下单这类做错了没法撤销的应用最有意义，可以先在克隆里练。

### 局限

论文没有单独的局限章节，下面几点来自正文自己的说法。

第一，迁移不完整。在 12306 上，克隆和真实应用的差距，从 7.7 个百分点扩大到 25.0，论文明说，克隆里的提升不能完全预测真实应用里的表现。

第二，诊断失败、针对性出题、再训练，这个循环平台支持反复跑，但论文还没有评估多轮的效果。

第三，按论文自己的拆分，大部分提升来自监督微调热身，而热身数据正文没有细讲。另外换成异步的 SAO 算法，和 GRPO 相比，训练时间没有明显的整体优势。

### 未来方向

资源方面，作者公开了框架、合成技能、49 个模拟应用、2000 个带验证器的任务和模型权重。要注意，训练用了 5000 个任务，公开的是 2000 个。

我的判断是，接下来值得看两件事，多轮的自我改进循环能走多远，以及克隆训练能不能推广到 12306 以外的应用。

我的判断是，在没见过的电脑环境上，9B 模型离前沿模型还很远，下一步要看，更大的模型和更多样的环境，能把这段差距补上多少。

## English walkthrough

### Intro

This is Daily Frontier Papers. Today's paper comes from Alibaba's MAI-UI team. It's called MAI-Gym, an open platform for evaluating GUI agents and training them with reinforcement learning.

A GUI agent is a model that looks at screenshots and taps, clicks and types its way through a phone or a computer. The team also used the platform to train a nine-billion-parameter model, which they say is the best open GUI agent under ten billion parameters on two major benchmarks.

### Problem

Start with the problem. Reinforcement learning with verifiable rewards has moved fast in math and coding, because those environments are cheap to run, easy to check, and full of tasks.

GUI agents are hard in two ways. First, the environments are expensive. The agent controls the whole screen and changes the device's files and settings, so every attempt needs its own phone, computer or browser, starting from a known state.

And evaluation and training often keep separate copies of the agent code, which drift apart. If training keeps the last five screenshots and evaluation keeps ten, you're evaluating a different agent from the one you trained.

Second, realistic tasks are scarce. Replying to an email with the total from an attached invoice only works if the email, the attachment and the invoice all exist and agree. And real apps that move money or place orders can't be used for thousands of practice runs.

### Prior work

Earlier systems fall into two camps, as this table shows. Infrastructure-focused gyms make evaluation or training reproducible, but each covers one platform, and those that release training code run at most hundreds of environments in parallel.

Data-focused gyms build new apps and tasks, but release neither training code nor a way to run existing benchmarks. And their tasks often start from a single input file, or from sample data shared across an app.

### Key idea

MAI-Gym's central design choice is one shared rollout path, a rollout being one full attempt at a task. Evaluation, data collection and training reuse the same screenshot processing, context building and action execution, so one fix reaches all three.

The other half is automated synthesis. Coding agents build mocked apps that reset cleanly, the pipeline builds a coherent world before writing tasks in it, and wherever the model fails, new tasks target that failure.

### Method

Here's the architecture. On the left, evaluation and training share one harness, the code between model and environment, and one rollout path. In the middle, an environment manager exposes five operations: request instances, observe, reset, step, and evaluate. On the right, instances hosted on Kubernetes or Docker.

On scale, the team reports running twenty thousand environment instances in parallel. Bringing up a thousand fresh ones took about three hundred twenty-eight seconds for mobile and about eighty-nine for computers.

There's also a neat compute trick, window-wise history. The usual approach keeps the last k screenshots. Every step, the oldest drops off, the start of the prompt changes, and the KV cache is almost entirely wasted.

MAI-Gym groups steps into windows of ten, overlapping by two. Inside a window it only appends, so the cache gets reused. At a window boundary, old screenshots become placeholders while their text stays.

In Table six, compared with the step-wise approach, prefix-cache hits rise from forty-two point five to eighty-five point nine percent, training tokens per trajectory drop by eighty-four point seven percent, and training update time falls by sixty-two point six percent. Rollout speed drops by eighteen point nine percent.

Now synthesis. The first kind is real-world clones of seven apps that move money, place orders or publish posts: the train-ticketing app 12306, China Construction Bank, DiDi, Meituan, Dianping, Douyin and Xiaohongshu. A coding agent rebuilds each one from scratch, over a backend that resets. In this figure, the top row is the real app, the bottom row the clone.

The second kind is novel apps, invented outright, so no model has seen them. They test whether an agent can learn an unfamiliar interface by interacting with it. Each is a deterministic state machine, so results are exactly reproducible. The release has forty-nine mocked apps, forty-two of them novel, with eight hundred forty tasks.

So where do tasks come from? The pipeline starts with a persona and a scenario, then generates files and app records that share people, events and facts. A project brief, a budget spreadsheet, an email thread and a calendar entry all describe one project.

So instead of "create an event named Budget review", a task can say: move the budget review to the day after the revised spreadsheet is due. The agent has to read an email and a spreadsheet before touching the calendar.

Verifiers get careful treatment. Requirements and expected values are fixed first. Then two independent calls write golden code, which sets the environment straight to a finished state, and verifier code, which checks the result. Neither sees the other's output.

Then it's all executed. The verifier must score zero on the initial state, one after the golden code runs, and zero again after a reset. Several models then attempt each task through the interface, and a review checks executability, difficulty and reward-hacking risk. Models help build and review tasks, but RL rewards come only from running the verifier.

Training uses GRPO: each task is attempted several times, and the group average is the baseline. A group that's all right or all wrong gives no gradient, so tasks never solved, or solved more than eighty percent of the time, get only a few attempts. The budget goes to tasks the model sometimes gets right.

### Results

The setup. MAI-Gym-9B starts from Qwen3.5-9B, gets a supervised fine-tuning warm-up on mixed mobile and desktop data, then one joint RL run on mobile and computer tasks.

That run used five thousand synthesized tasks, five hundred twelve GPUs, a peak of twenty thousand concurrent environments, and about ninety-six hours. Rewards came only from code verifiers.

Evaluation covers seven benchmarks. MobileWorld and OSWorld-Verified share their environments with training, but not their tasks. The other five, including AndroidWorld and MacAgentBench, use environments it never trained in.

The main results are in Table four: seventy-eight point four percent on MobileWorld, and seventy-six point two on OSWorld-Verified. The base model scored eighteen and forty-one point eight.

That's three point two and five point four points above UI-Venus-2-9B, a model of the same size. On MobileWorld it also beats the paper's numbers for Claude Opus 4.8 at sixty-nine point two, GPT-5.5 at sixty-two point four, and Qwen3.8-Max at seventy-seven point eight.

This figure splits the gains. Most come from the supervised warm-up, which lifts the average on the two unseen-task benchmarks from twenty-nine point nine to sixty-six point four. RL then raises the overall average from forty-four point one to fifty point five, and improves all five unseen environments.

Now the transfer result. RL only inside the 12306 clone, tested on fifty-two paired tasks, takes clone success from thirty-six point five to seventy-three point one percent. In the real 12306 app, on a physical phone, it goes from twenty-eight point eight to forty-eight point one, up nineteen point two points.

On the novel apps, training on two hundred fifty-two tasks and testing on sixty-two held-out ones, success rises from twenty-five point eight to forty-five point two percent, and average trajectories shrink from thirty-three point three steps to sixteen point four. No demonstrations, only verifier rewards.

More synthesized tasks help too. At a fixed rollout budget, going from five hundred to five thousand tasks lifts MobileWorld from sixty-nine point two to seventy-eight point four, and OSWorld-Verified from sixty-nine point seven to seventy-six point two.

### Comparison

Compare that with a common recipe: run RL separately per domain, then average the two experts' weights.

In Table seven, from the same warm-up and the same total budget, the best merge reaches seventy-six point four on MobileWorld and seventy-four point eight on OSWorld-Verified, from different merge ratios. Joint RL beats both, at seventy-eight point four and seventy-six point two.

But keep the gaps in view. On OSWorld-Verified, Claude Opus 4.8 scores eighty-three point four, Qwen3.8-Max eighty-six point one, and the 397-billion-parameter Qwen-CUA eighty-six point two. On unseen computer environments it's wider: fifteen point two on MyPCBench against sixty-two for Claude Opus 4.8, and three point seven binary success on OSWorld 2.0.

Also, most baseline numbers come from published reports and leaderboards; only eight entries are the authors' own runs. And the paper itself notes that changing the harness alone can change a model's score.

My read is that the platform is the real contribution, not the 9B score. A path shared by evaluation and training, and rewards only from executed verifiers, target exactly where GUI RL tends to go wrong.

My read is that the clone result matters most for apps where a mistake can't be undone. Payments and orders can be practiced in a clone first.

### Limitations

The paper has no dedicated limitations section, so these come from its own text.

First, transfer is incomplete. On 12306, the clone-to-real gap widens from seven point seven to twenty-five points, and the authors say clone gains don't fully predict real-app performance.

Second, the loop of diagnosing failures, writing targeted tasks and retraining can run repeatedly, but the paper doesn't yet evaluate multiple rounds.

Third, by the paper's own breakdown, most of the gain comes from the supervised warm-up, and the main text says little about that data. And the asynchronous SAO algorithm showed no clear overall training-time advantage over GRPO.

### Future work

The team releases the framework, the synthesis skills, forty-nine mocked apps, two thousand tasks with tested verifiers, and the model checkpoint. Note that training used five thousand tasks; the release has two thousand.

My read is that two things are worth watching: how far the multi-round self-improvement loop can go, and whether clone training carries over to apps beyond 12306.

My read is that on unfamiliar computer environments, a 9B model is still far behind frontier systems, and the open question is how much bigger models and more varied environments can close that gap.
