**旧轨迹不给Agent看只决定在哪多试**

## 中文讲解

### 开场

这里是每日前沿文章。今天讲一篇康涅狄格大学和蚂蚁集团的论文，名字叫 SWE-Trail，讲的是怎么给编程 Agent 收集训练数据。

一句话概括，以前收集过的轨迹，不拿给 Agent 看，而是用来决定，下一次收集该在哪儿多花力气。

### 问题

先说背景。编程 Agent 修一个代码仓库里的 issue，要反复地看代码、改代码、跑测试，这一整串推理和操作记录下来，就叫一条轨迹。

这些轨迹越来越多地被拿来当后训练数据。所以轨迹怎么收集，直接决定了模型最后学到什么。

常见做法是，每个 issue 独立跑好几次，再把通过测试的留下来。问题在于，跑得越多，后面的轨迹越重复。

论文先拿数据说话。在 300 个 issue 上，每个 issue 只跑一次，期望能解决 58.4 个。跑第二次多解决 13.1 个，第三、第四、第五次，分别只多 8.0、5.1 和 3.4 个。

更能说明问题的是，那些几次全都失败的 issue，失败的尝试往往改的是同一批文件，两两之间的重合度平均是 0.841。也就是说，独立采样不会因为失败了，就自动换个方向去试。

### 以前的方法

以前的改进主要有两类。一类是收集完以后再加工，比如只留通过的，屏蔽出错的工具调用，删掉多余的步骤。但同一个 issue 的几条轨迹，仍然是各跑各的。

另一类是把以前的经验直接告诉 Agent，相当于给它塞一张提示纸条。这对当前这一次修复可能有帮助。

麻烦出在训练上。轨迹里的推理和动作，是看过纸条以后才写出来的，可模型上线测试的时候，手里没有这张纸条。训练和测试对不上，学到的东西就可能打折扣。

### 核心想法

作者的思路是把两件事拆开。历史只决定在哪儿多花收集的力气，至于下一步具体做什么，还是让 Agent 从自己正常的上下文里生成。

换句话说，历史是给收集器看的，不是给 Agent 看的。图里这条线，论文叫它信息边界，历史从头到尾都不进 Agent 的上下文。

### 方法

方法分两个阶段，这张图是总览。第一阶段在收集开始前离线完成，第二阶段在 Agent 跑的过程中在线触发。

第一阶段，有一个编译器去读这个 issue 以前的几次尝试，找出成功的尝试做对了哪些决定，成功和失败在哪儿分了岔，以及反复出现的失败模式。

如果历史留下了没回答的问题，编译器还会对仓库做一些有限的只读检查，不改代码，也看不到标准答案的补丁。

然后它把这些整理成检测规则。比如图里这一条，改过代码以后没跑任何验证，又接连读了好几次文件，就算命中。

规则不看这是第几步，看的是 Agent 做了什么、看到了什么。所以新的一次尝试，哪怕换了条路走到类似的局面，也能被识别出来。

规则在收集前，要先放到旧轨迹上回放验证，证据不够的就丢掉，留下来的在整轮收集里固定不变。论文报告，用五次历史的设置下，一共编出 687 条候选规则，最后有 397 条通过了检查。

第二阶段，Agent 正常地跑。一旦命中规则，就在这个位置存一个检查点，让 Agent 从自己正常的上下文出发，生成 8 个候选的下一步动作。

第一个候选用平常的温度，当作默认选项。如果历史里有成功也有失败，或者一直都失败，其余候选里就有一部分把温度调高，鼓励它提出不一样的动作。

意思相同的候选先合并，收集器再从剩下的里面，最多挑一个替代动作，拿来和默认动作比。

比法是真跑，从同一个检查点恢复出两个隔离的工作区，两个动作各自往下执行一小段。论文里这一小段，是两次观察的长度。

然后交给一个选择器判断。两段结果打乱顺序给它，它不知道哪个是默认，只有证据清楚地显示一边进展更好，才选那一边，否则就保留默认。

选完以后，Agent 只从选中的那个工作区继续跑完。导出训练数据时，只留选中的路线，Agent 原来的推理和动作一字不改，没选中的分支和收集器的私有信息全部删掉。

为了不让收集变成一棵越长越大的搜索树，每条轨迹最多只做一次这样的比较。

论文附录里有一个 Rust 项目的例子。图里左边是默认动作，改完代码接着读测试文件，右边是 Agent 自己提出的另一个候选，直接跑测试。

两条各跑一小段，右边拿到了测试全部通过的证据，选择器选了右边，Agent 从那里继续，最后这条轨迹解决了问题。

### 实验和效果

实验是这么设计的。用 SWE-rebench V2 里的同一批 300 个 issue，每种方法都收集 1500 条轨迹，也就是每个 issue 五条，跑轨迹的 Agent 都是 GLM-5.1。

然后用这些轨迹训练同一个学生模型，124B 的 Ling-3.0-flash-base，做全参数监督微调，每组数据独立训练三次，取平均。

评测用 SWE-bench Multilingual 的 300 道题，和 SWE-bench Pro 的 731 道题。论文说明，收集用的仓库和这两个评测集没有重叠。

对照组主要有三个。SeedBank 是普通的独立采样。H5 是 SWE-Trail，拿 SeedBank 那五次当历史，再收集五条新的。H0 走同一套流程，但不给历史。

结果在表 1。独立采样训练出来的学生，Multilingual 解决率是 63.33%，SWE-Pro 是 41.22%。H5 分别是 65.67% 和 42.82%，高了 2.33 和 1.60 个百分点，是整张表里最高的。

而且三次独立训练里，H5 的每一次，都超过了独立采样的每一次。

更有意思的是 H0。不给历史，收集到的成功轨迹反而比独立采样多了 37 条，可学生在 Multilingual 上只高了 0.11 个百分点。

加上历史的 H5，成功轨迹只比 H0 再多 16 条，学生却又高了 2.22 个百分点。作者的结论是，收集时成功的轨迹多，不等于训练价值高。

换一个学生模型，Qwen3-14B-Base，结论也成立。H5 比独立采样高 3.11 和 2.42 个百分点，比 H0 也高 1.67 和 1.60 个百分点。

消融实验也在表 1。如果比较的位置改成随机选，两个基准分别掉 1.44 和 1.28 个百分点。如果位置不变，但随机挑一条路线继续，分别掉 0.89 和 1.19 个百分点。作者认为，这说明在哪儿比，和选哪一条，两步都有作用。

历史给得更多会不会更好。把历史从五次加到十次，正常运行之外的额外 token 从 3.07 亿涨到 5.1 亿，多了 66%，学生只再涨 0.22 和 0.14 个百分点。

H5 本身的成本不高。论文报告，不算之前收集历史的花费，H5 最多只比 H0 多用 3.7% 的 token。

### 和以前方法的对比

再看和以前方法的对比。SWE-Gym、SWE-TRACE、SWE-Lego 这几种收集完再加工的方法，作者在同一批独立采样轨迹上做了对照版本，Multilingual 最多高 1.22 个百分点，SWE-Pro 上有两个反而下降。

把经验直接给 Agent 看的 SWE-Exp，两个基准都比独立采样低，分别低 1.33 和 2.78 个百分点。作者认为，这可能是因为模型依赖了训练时有、测试时没有的提示。

还有一个问题，多跑几条再挑最好的，能不能达到一样的效果。每个 issue 跑十条，用验证器挑五条，比 H5 分别低 1.56 和 0.96 个百分点。但把 H5 和独立采样的轨迹合在一起再挑，又比 H5 高 0.56 和 0.32 个百分点，两种做法可以叠加。

我的判断是，这篇最有价值的是 H0 这个对照。它把收集时的成功率和训练价值拆开了，提醒做数据的人，只盯着通过率挑轨迹，可能盯错了地方。

我的判断是，提升幅度也要看清楚。H5 比独立采样，三次训练的置换检验 p 值是 0.05，而 H5 比 H0 的提升，论文给的 95% 置信区间在两个基准上都包含零，统计上还比较边缘。

### 局限

作者自己写的局限有这几条。实验用了两个学生模型，但收集模型只有一个，Agent 框架也只有一个。

每轮收集里，历史是固定的，每个 issue 的收集预算也都一样，没有区别分配。

附录里还有一个小规模的回放分析。18 次比较里，有 13 次被认为候选本身覆盖得不够。选择器再准，也选不出 Agent 根本没提出来的动作。

### 未来方向

作者提到的方向有这些，换别的收集模型和框架去测，在不同轮次之间更新历史，按 issue 分配不同的预算，以及让候选动作更多样。

要推广到编程以外，环境得支持状态恢复，还得有能比较两条路线的反馈，作者提到网页导航可能是一个方向。

我的判断是，这个思路对所有拿 Agent 轨迹做训练数据的团队都有参考价值，历史不一定要当提示塞给模型，也可以用来决定把算力花在哪里。不过目前只在 300 个 issue、一个收集模型上验证过，规模放大以后效果怎样，还要看后续工作。

## English walkthrough

### Intro

This is Daily Frontier Papers. Today's paper comes from the University of Connecticut and Ant Group. It's called SWE-Trail, and it's about how you collect training data for coding agents.

The short version: don't show the agent its earlier attempts. Use them instead to decide where the next round of collection should spend its effort.

### Problem

Some background first. When a coding agent fixes an issue in a repository, it reads code, edits code, and runs checks, over and over. Record that whole sequence of reasoning and actions, and you have a trajectory.

Those trajectories are increasingly used as post-training data. So the way you collect them shapes what the trained model ends up learning.

The usual recipe is to run the agent several times on each issue, independently, and keep the runs that pass the tests. The catch is that the more you sample, the more the later runs repeat the earlier ones.

The paper measures this. Across three hundred issues, one attempt per issue solves fifty-eight point four issues in expectation. A second attempt adds thirteen point one. The third, fourth and fifth add only eight, five point one, and three point four.

The failures tell the same story. On issues where every attempt failed, the failed attempts mostly edited the same files, with an average pairwise overlap of zero point eight four one. Independent sampling doesn't change direction just because it keeps failing.

### Prior work

Earlier fixes come in two kinds. One works after collection: keep the runs that pass, mask flawed tool calls, cut redundant steps. But the trajectories for one issue are still generated independently of each other.

The other kind hands the earlier experience straight to the agent, as advice in its context. That can help the current attempt.

The trouble shows up in training. The reasoning and actions in the trajectory were written after reading the advice, but at test time the trained model has no advice. Train and test no longer match, and the data can teach less than it should.

### Key idea

The authors split the two jobs apart. History decides where to spend extra collection effort. What to actually do next is still generated by the agent, from its ordinary context.

Put differently, the history is for the collector, not for the agent. The paper draws this as an information boundary: history never enters the agent's context.

### Method

There are two stages, and this figure is the overview. Stage one runs offline, before collection starts. Stage two kicks in while the agent is running.

In stage one, a compiler reads the earlier attempts on the issue. It pulls out the decisions that successful attempts made, the points where successful and failed routes split, and failure patterns that keep coming back.

If the history leaves a question open, the compiler can run a few bounded, read-only checks on the repository. They can't edit code, and they never see the reference patch.

It then turns all this into detector rules. The one in this figure fires when the agent has made an edit, hasn't validated it, and keeps reading files.

The rules don't look at step numbers. They look at what the agent did and what it saw, so a new attempt that reaches a similar situation by a different path still gets recognized.

Before collection, every rule is replayed on the old trajectories, rules without enough support are dropped, and the survivors stay frozen for the whole round. The paper reports that with five attempts of history, the compiler proposed six hundred eighty-seven rules, and three hundred ninety-seven passed the checks.

In stage two, the agent runs as usual. When a rule fires, the collector saves a checkpoint, and the agent proposes eight candidate next actions from its normal context.

The first candidate uses the ordinary temperature and serves as the default. If the history was mixed, or never solved, some of the other candidates are sampled hotter, to get more varied actions.

Equivalent candidates are merged, and the collector picks at most one alternative to set against the default.

The comparison is done by actually running both: two isolated workspaces are restored from the same checkpoint, and each candidate runs for a short stretch. In the paper, that stretch is two observations.

Then a selector judges the result. It sees the two runs in shuffled order, without knowing which is the default, and it only switches routes when the evidence clearly shows one making better progress. Otherwise the default stays.

After that, the agent continues only from the chosen workspace. The exported training record keeps just the chosen route, with the agent's own reasoning and actions unchanged, and drops the other branch and everything private to the collector.

To keep this from growing into a search tree, each trajectory gets at most one such comparison.

The appendix walks through a Rust example. On the left is the default action: after an edit, keep reading the test files. On the right is another candidate the agent proposed itself: run the tests.

Both run for a short stretch. The right branch comes back with passing tests, the selector picks it, the agent carries on from there, and the trajectory ends up resolving the issue.

### Results

Here's the setup. Every method collects fifteen hundred trajectories on the same three hundred issues from SWE-rebench V2, five per issue, and every run uses GLM-5.1 as the agent.

Those trajectories then train the same student, the one hundred twenty-four billion parameter Ling-3.0-flash-base, with full-parameter supervised fine-tuning. Each dataset gets three independent training runs, and the scores are averaged.

Evaluation uses SWE-bench Multilingual, with three hundred tasks, and SWE-bench Pro, with seven hundred thirty-one. The paper checks that the collection repositories don't overlap with either benchmark.

There are three main conditions. SeedBank is plain independent sampling. H5 is SWE-Trail, using SeedBank's five attempts as history to collect five new ones. H0 runs the same pipeline with no history.

The results are in Table one. The student trained on independent samples resolves sixty-three point three three percent on Multilingual and forty-one point two two on SWE-bench Pro. With H5 it's sixty-five point six seven and forty-two point eight two. That's two point three three and one point six points higher, the best in the table.

And across the three training runs, every H5 run beat every SeedBank run.

The interesting one is H0. Without history, it actually collects thirty-seven more successful trajectories than independent sampling, yet the student gains only zero point one one points on Multilingual.

H5 collects just sixteen more successful trajectories than H0, but the student gains another two point two two points. The authors' conclusion: a higher success rate during collection is not the same as more useful training data.

The result holds for a second student, Qwen3-14B-Base. H5 beats independent sampling by three point one one and two point four two points, and beats H0 by one point six seven and one point six.

The ablations are in Table one too. Pick the comparison point at random, and the score drops by one point four four and one point two eight points. Keep the point but pick the surviving route at random, and it drops by zero point eight nine and one point one nine. The authors read this as both choices, where to compare and which route to keep, doing work.

Does more history help? Going from five attempts to ten raises the extra tokens beyond normal rollouts from three hundred seven million to five hundred ten million, sixty-six percent more, for a further gain of only zero point two two and zero point one four points.

H5 itself is cheap. The paper reports that, not counting the cost of the earlier attempts, it uses at most three point seven percent more tokens than H0.

### Comparison

Now the comparison with earlier methods. The authors built controlled versions of SWE-Gym, SWE-TRACE and SWE-Lego, which all post-process collected runs, on the same independent samples. The best gain on Multilingual is one point two two points, and two of them actually drop on SWE-bench Pro.

SWE-Exp, which shows the experience to the agent, lands below independent sampling on both benchmarks, by one point three three and two point seven eight points. The authors suggest the model may be leaning on advice that exists in training but not at test time.

Could you just sample more and keep the best? Running ten per issue and letting a verifier keep five comes in one point five six and zero point nine six points below H5. But pool H5 with the independent runs and select from that, and you land zero point five six and zero point three two points above H5. The two approaches stack.

My read is that the most valuable thing here is the H0 control. It separates collection success from training value, and it warns anyone building datasets that filtering on pass rate alone may be optimizing the wrong thing.

My read is also that the margins deserve care. Against independent sampling, the permutation test over three training runs gives p equal to zero point zero five. Against H0, the paper's own ninety-five percent intervals include zero on both benchmarks, so that gap is still borderline.

### Limitations

The authors list these limitations. There are two student models, but only one collection model and one agent scaffold.

Within a collection round the history is fixed, and every issue gets the same budget, with no per-issue allocation.

The appendix also has a small replay analysis. In thirteen of eighteen comparisons, weak coverage by the candidates themselves was flagged as a limitation. A selector can't pick an action the agent never proposed.

### Future work

The directions the authors name are testing other collection models and scaffolds, updating history across rounds, giving different issues different budgets, and making candidate proposals more diverse.

Going beyond code would need environments that can restore state and give feedback for comparing routes. The authors mention web navigation as one possibility.

My read is that the idea carries over to anyone training on agent trajectories: history doesn't have to be stuffed into the prompt, it can decide where the compute goes. But so far it's tested on three hundred issues with one collection model, and how it scales is still an open question.
