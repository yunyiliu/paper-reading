## 中文讲解

### 开场

这里是每日前沿文章。今天讲一篇 MIRIX AI 团队的论文，名字叫 MIRIX-2.0，一个多 Agent 的长期记忆系统。

它想回答的是，Agent 的记忆能不能又准、又实用、又高效。

### 问题

现在的 Agent，工作时间远远超过一个上下文窗口。私人助理会积累几个月的对话，任务型 Agent 会反复碰到相似的问题，所以需要长期记忆。

作者认为，真要部署一套记忆，有三个要求。第一是准确，名字、日期、数量这些细节不能错，两件事不能混。第二是实用，能用团队现有的模型，不用训练，答案能追溯到原始记录，整理记忆时不能毁掉已有内容。第三是高效，每个问题的延迟和 token 成本，不能随着历史变长而失控。

记忆还有两种用法，一种是记用户，要记得广，因为以后可能问到任何细节。另一种是记 Agent 自己的经验，要提炼得精，检索太多反而会分散注意力。MIRIX-2.0 想用同一个存储服务这两种用法。

### 以前的方法

作者把已有做法分成几类，认为每一类都至少放弃了一个要求。第一类把记录压缩成事实或摘要，存得小，但丢掉的细节就找不回来了。第二类把所有记录都留下，直接检索，但要在越来越大、越来越嘈杂的历史里找。

第三类是图记忆，围绕实体和关系组织内容。问题是普通的三元组只能连两个东西，一件涉及多方的事，会被拆成碎片，参与者之间的联系也丢了。

第四类是超图记忆和文件式记忆，都靠摘要一层层往下找，摘要没提到的细节，就很难找到。还有一类把记忆存进模型参数，需要训练，闭源模型也用不了。

### 核心想法

MIRIX-2.0 的核心想法，是把存储和索引分开。完整的记录放在向量数据库里，这是系统的权威记录。图只是索引，图里每条事实，都要标明它来自哪几行记录。

数据库先写入，图写失败也不会丢记忆。图读取出错，就退回直接检索。

这张图是系统全貌。上面从左到右是写入、证据层、超图和检索，下面是一个叫 AutoDream 的离线整理模块。

### 方法

先看写入。一个元记忆管理器，决定每条输入该更新哪几类记忆。记忆一共六类，核心、情景、语义、程序、资源和知识保险库，每一类都有自己专门的写入 Agent。

其中只有情景记忆和语义记忆进超图。情景记忆记发生在具体时间的事，语义记忆记长期成立的事实和概念。

再看超图。它的基本单位叫 frame，可以理解成一条完整的事实。比如一次航班，出发地、目的地、航空公司、同行的人，都挂在同一个 frame 上。日期、价格、数量这些值，也直接留在这条事实上。

还有一个细节，叫事件身份。两次提到同一个有日期的事件，会合并成一条。但两件没写日期、说法又很像的事，比如不同日子的两次跑步，会保持成两条。

检索时，先由一个确定性的规划器，判断问题类型，然后定好预算。单值查询最多取 6 行基础记录和 4 行引用记录，计数问题放宽到 8 行和 12 行。

接着从和问题最匹配的实体进入超图，走两条通道。一条取和这些实体直接相关的记录，另一条在问题涉及关系时打开，沿着关系找到事实，再取这些事实引用的原始记录。最后合并去重，答案拿到的既有事实，也有支撑它的原文。

最后是 AutoDream，它在写入流程之外运行，对两种记忆的处理正好相反。对语义记忆，它只合并重复的实体。比如 steel bottle 和 stainless steel bottle，类型相同，名字的余弦相似度不低于 0.86，再让大模型确认是不是同一个东西。

确认之后，把两个实体的引用合到一起，相关的 frame 也改接到保留的实体上，数据库里的记录不改。

对程序记忆，AutoDream 做的是提炼。它根据任务记录里的原话判断成败，总结出值得复用的经验和应该避免的错误，再写成技能。论文的示意例子是，Agent 买水杯时没选颜色，买成了默认的灰色，之后技能里就多了选颜色尺寸、核对全部条件这两步。

### 实验和效果

第一块实验是记用户。两个对话记忆基准，LoCoMo 和 LongMemEval-S，用 gpt-4o-mini 当裁判，三票取多数。对比的系统有 mem0、A-Mem、MemoryBank、Graphiti 和 HyperMem。

先看每一层的贡献。在 LoCoMo 上，扁平向量记忆是 85.7，加上超图到 88.4，再加 AutoDream 到 91.4。在 LongMemEval-S 上，三个数字是 58.8、70.0 和 72.6，超图这一层就加了 11.2 个百分点。

LongMemEval-S 上，MIRIX-2.0 的 72.6，比最强基线 HyperMem 的 58.3 高 14.3 个百分点。LoCoMo 上是 91.4 对 91.0，只高 0.4 个百分点。

长文档问答这组实验关掉了 AutoDream。单跳问题是 83.0，多跳问题是 71.0，分别比 HyperMem 高 31.0 和 22.0 个百分点。

但它不是全赢。侦探推理问答 DetectiveQA 上，MIRIX-2.0 是 64.8，低于 MemoryBank 的 67.6 和 HyperMem 的 66.2。LoCoMo 的开放域和单跳问题，也是 HyperMem 更高。

第二块是记 Agent 自己的经验。在 ALFWorld 这个交互任务环境里，先用 39 个任务学习，再把记忆冻结，到 134 个没见过的任务上测试，结果取三次运行的平均。用 GPT-6 Luna，没有记忆是 69.4，另一个记忆方法 AWM 是 73.6，MIRIX-2.0 是 76.4。

在 WebShop 购物任务上，没有记忆是 31.9，AWM 是 36.0，MIRIX-2.0 是 37.4。

在 MetaClaw-Bench 上，用 GPT-5.2，MIRIX-2.0 得分 49.2，MetaClaw 的技能库是 44.0。不过这个 44.0 是 MetaClaw 论文报告的数字，不是在完全受控的条件下重跑的。换成 Qwen3.6-35B-A3B，差距只有 52.7 对 51.8。

再看成本，这些计时都来自关掉 AutoDream 的版本。回答速度在五个基准上都快过 HyperMem，比如 LoCoMo 上，每个问题 5.46 秒对 9.70 秒。

代价在写入。三个长文档任务上，建图让写入时间变成扁平记忆的 3.8 到 4.0 倍，回答也比扁平记忆慢。

### 和以前方法的对比

按作者的说法，它和以前系统的区别，在于完整记录始终是权威来源，整理记忆只改变证据怎么连接，不改变证据本身。

但对比结果要细看。LoCoMo 上领先的 0.4 个百分点，对手 HyperMem 的 91.0 是作者自己跑出来的，低于 HyperMem 论文报告的 92.7。

Agent 记忆这边，ALFWorld 上 MIRIX-2.0 的平均分最高，但三次运行的标准差是 6.2，换成 GPT-5.6 Luna 更是到了 14.0。作者自己也说，三次运行不足以证明它稳定强过 AWM。

记忆也不是总有帮助。用 GPT-6 Luna 时，Heat 类任务从 47.8 升到 73.9，Clean 类从 60.2 升到 74.2。但 Pick、Look 和 Pick Two 三类，反而比没有记忆时低。

token 也不一定更省。ALFWorld 每轮测试，没有记忆用 214.7 万 token，MIRIX-2.0 用 381.3 万，是三种记忆方法里最高的。

我的判断是，LoCoMo 这 0.4 个百分点说明不了谁更强。如果拿 HyperMem 自己报告的 92.7 来比，MIRIX-2.0 的 91.4 反而落后，更有说服力的差距，在 LongMemEval-S 和两个长文档任务上。

我的判断是，这篇最值得借鉴的不是某个分数，而是那条工程边界。模型可以判断错，索引可以合并错，但整理语义记忆不会改写已经存下的记录。

### 局限

作者自己写明了几条局限。首先，消融实验是按模块成组添加的，没有单独验证多元 frame、引用原始记录、事件身份和回答时校验各自的作用，所以论文对原因的解释，仍然只是解读。

其次，用户记忆的结果来自单次运行，一部分由大模型裁判打分。Agent 的结果只平均了三次，波动很大，还有一些基线用的是原作者报告的数字。

再有，完整系统没有计时。论文说的检索上限，限制的是一个问题看多少证据，并没有测量历史变长时延迟怎么变化。

论文也没有测实体合并的准确率，以及六个写入 Agent 的分工到底贡献多少。作者还提醒，注入到对话里的内容，可能被存下来，之后被当成可信信息取出来。

### 未来方向

论文没有单独写未来工作，但点明了还要补的测量。完整系统的写入成本和回答成本，需要直接测量。检索到的记录和合并后的实体，也需要直接审计，才能确认背后的机制。代码已经在 GitHub 公开。

我的判断是，接下来最该看的，是完整系统的成本，以及记忆持续增长之后，准确率和延迟能不能守住。目前的结果说明这个方向值得跟进，但长期记忆的问题还没有解决。

## English walkthrough

### Intro

This is Daily Frontier Papers. Today's paper comes from the team at MIRIX AI, and it's called MIRIX-2.0, a long-term memory system built out of multiple agents.

The question behind it is whether an agent's memory can be accurate and practical while keeping the cost of each lookup under control as the history grows.

### Problem

Some background first. Agents now work far beyond a single context window. A personal assistant piles up months of conversation, and a task agent keeps running into similar problems, so both need memory that lasts.

The authors say a memory you'd actually deploy has to clear three bars. It has to be accurate about particulars like names, dates and counts, and keep two events apart. It has to be practical: it works with the models a team already uses, needs no training, traces answers back to stored records, and its consolidation can't destroy what was stored. And it has to be efficient, with latency and token cost per question that stay bounded as history grows.

There's a further wrinkle. Memory about a user has to be broad, because a later question could touch any detail. Memory of an agent's own experience has to be refined, because retrieving too much pulls attention away from the next action. The authors argue a practical system should serve both from one store.

### Prior work

The authors sort existing systems into families, and argue each one gives up at least one of those three bars. Systems that consolidate records into facts or summaries stay compact, but the details they drop are gone for good. Systems that keep everything lose nothing, but have to search an ever larger and noisier history.

Graph memories organize content around entities and relations. The catch is that a plain triple links only two things, so a fact with many participants gets split into fragments, and the connections among them are lost.

Hypergraph and file-system memories both route retrieval through summaries, so a detail no summary mentions is hard to reach. And memories stored in model weights need training and rule out closed models.

### Key idea

The key idea in MIRIX-2.0 is to separate storage from indexing. Complete records live in a vector database, and that's the system of record. The graph is only an index, and every fact in it cites the rows it came from.

That split pays off right away. The database write commits first, so a failed graph write can't lose a memory. And if a graph read fails, the system falls back to direct retrieval.

This figure is the whole system. Across the top you have writing, the evidence plane, the hypergraph and retrieval, and along the bottom an offline consolidation module called AutoDream.

### Method

Start with writing. A Meta Memory Manager decides which kinds of memory each input should update. There are six: core, episodic, semantic, procedural, resource, and a knowledge vault, and each has its own dedicated writer agent.

Only episodic and semantic memory go into the hypergraph. Episodic memory holds things that happened at a particular time, and semantic memory holds durable facts and concepts.

Now the hypergraph. Its basic unit is called a frame, which you can think of as one complete fact. A flight becomes a single frame with its origin, destination, carrier and companion attached, instead of several disconnected triples. Dates, prices and counts stay right on that frame too.

One subtle piece is occurrence identity. Two mentions of the same dated event share one frame. But two undated events that sound alike, say two runs on different days, stay separate rather than collapsing into one.

At query time, a deterministic planner classifies the question as a single-value lookup, a temporal question, an intersection, a list, or a count, and sets a budget. A single-value lookup gets at most six base rows and four cited rows, and a count gets up to eight and twelve.

Retrieval then enters the hypergraph at the anchors that best match the question and opens two lanes. One pulls records tied directly to those anchors. The other opens when the question involves a relation: it follows relations to facts, then pulls the source rows those facts cite. The two are merged without duplicates, so the answer sees both the facts and the text behind them.

Then there's AutoDream, which runs outside the write path and treats two kinds of memory in opposite ways. For semantic memory, it only merges duplicate entities. Take steel bottle and stainless steel bottle: same type, name similarity of at least zero point eight six, and then a language model confirms whether they're the same thing.

A confirmed merge unites the two anchors' citations and rewires their frames to the surviving anchor, and the records in the database don't change.

For procedural memory, AutoDream distills instead. It judges each task session from quotes in the transcript, pulls out lessons to reuse and mistakes to avoid, and turns them into skills. In the paper's illustration, an agent buys a bottle without setting the color and ends up with the default gray, so the skill gains two steps: select color and size, then verify every constraint.

### Results

The experiments come in two halves, and the first is memory about users. Two conversational benchmarks, LoCoMo and LongMemEval-S, are scored by a GPT-4o mini judge with a majority of three votes. The comparison systems are mem0, A-Mem, MemoryBank, Graphiti and HyperMem.

First, the contribution of each layer. On LoCoMo, flat vector memory scores eighty-five point seven, adding the hypergraph gives eighty-eight point four, and adding AutoDream gives ninety-one point four. On LongMemEval-S those numbers are fifty-eight point eight, seventy, and seventy-two point six, so the hypergraph alone adds eleven point two points.

Against other systems, MIRIX-2.0's seventy-two point six on LongMemEval-S is fourteen point three points above the strongest baseline, HyperMem, at fifty-eight point three. On LoCoMo it's ninety-one point four against ninety-one flat, a lead of just zero point four.

The long-document runs have AutoDream switched off. Single-hop questions land at eighty-three and multi-hop at seventy-one, which is thirty-one and twenty-two points above HyperMem.

It doesn't win everywhere. On DetectiveQA, MIRIX-2.0 scores sixty-four point eight, behind MemoryBank at sixty-seven point six and HyperMem at sixty-six point two. HyperMem also stays ahead on LoCoMo's open-domain and single-hop questions.

The second half is memory of an agent's own experience. In the ALFWorld interactive environment, each method learns from thirty-nine tasks, then memory is frozen and tested on one hundred thirty-four unseen episodes, averaged over three runs. With GPT-6 Luna, no memory scores sixty-nine point four, a memory method called AWM scores seventy-three point six, and MIRIX-2.0 scores seventy-six point four.

On WebShop shopping tasks, no memory gets thirty-one point nine, AWM gets thirty-six, and MIRIX-2.0 gets thirty-seven point four.

On MetaClaw-Bench with GPT-5.2, MIRIX-2.0 scores forty-nine point two against forty-four for the MetaClaw skill library. That forty-four is a number reported in the MetaClaw paper, though, not a fully controlled rerun. With Qwen3.6-35B-A3B, the gap is only fifty-two point seven to fifty-one point eight.

On cost, all of these timings come from the version with AutoDream off. It answers faster than HyperMem on all five benchmarks, for example five point four six seconds per question against nine point seven on LoCoMo.

The price shows up at ingestion. On the three long-document tasks, building the graph makes ingestion three point eight to four times slower than flat memory, and answering is slower than flat memory as well.

### Comparison

As the authors put it, what sets MIRIX-2.0 apart is that complete records stay the system of record, the graph is only a bounded index, and consolidation changes how evidence is connected rather than what evidence exists.

But the comparison deserves a closer look. That zero point four lead on LoCoMo is against a HyperMem score of ninety-one that the authors got from their own run, which is below the ninety-two point seven HyperMem's paper reports.

On agent memory, MIRIX-2.0 has the top mean on ALFWorld, but its standard deviation across three runs is six point two, and fourteen with GPT-5.6 Luna. The authors themselves say three runs don't establish a stable advantage over AWM.

Memory doesn't always help either. With GPT-6 Luna, Heat tasks climb from forty-seven point eight to seventy-three point nine, and Clean tasks from sixty point two to seventy-four point two. But Pick, Look and Pick Two all land below the no-memory scores.

It doesn't necessarily save tokens. Per ALFWorld test run, no memory uses about two point one five million tokens, while MIRIX-2.0 uses about three point eight one million, the highest of the three memory methods.

My read is that the zero point four point lead on LoCoMo doesn't tell you who's stronger. Measured against the ninety-two point seven HyperMem reports for itself, MIRIX-2.0's ninety-one point four would trail, so the convincing gaps are on LongMemEval-S and the two long-document tasks.

My read is that the lesson to take from this paper isn't any one score, it's the engineering boundary. A model can misjudge and an index can merge wrongly, but semantic consolidation doesn't rewrite the records already stored.

### Limitations

The authors spell out several limitations themselves. First, the ablations add components in groups, so they don't isolate n-ary frames, cited source rows, occurrence identities or answer-time verification, and the paper's explanations of why things work remain interpretations.

Second, the user-memory results come from single runs, partly scored by a language-model judge. The agent results average just three runs with large spreads, and some baselines are numbers reported by their own authors.

Third, the full system was never timed. And the retrieval bounds cap how much evidence a question inspects, without measuring how latency changes as the history grows.

The paper also doesn't measure merge precision, or how much the six-writer design contributes. The authors further warn that content injected into a conversation can be stored and later retrieved as if it were trusted.

### Future work

The paper has no separate future-work section, but it does name the measurements still missing. The full system's ingestion and answer costs have to be measured directly. Retrieved records and merged anchors also need a direct audit to establish the mechanism. The code is already public on GitHub.

My read is that the thing to watch next is the full system's cost, and whether accuracy and latency hold as memory keeps growing. These results make the design worth following, but they don't mean long-term memory is solved.
