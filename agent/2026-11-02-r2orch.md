## 中文讲解

### 开场

这里是每日前沿文章。今天讲一篇香港中文大学深圳等单位的论文，名字叫 R2Orch，讲的是 Agent 编排怎么自我改进。

一句话说，它让一个给 Agent 团队排兵布阵的模型，自己挑题自己练，边练边把提示词里的技能一条条撤掉，最后不带技能部署。

### 问题

先说背景。所谓编排，就是把任务交给一组 Agent 来做。论文把这组 Agent 画成一张图，每个节点是一个 Agent，有自己的角色提示词和模型，每条边是一次交接。

搭这张图的模型叫 Director。它从空图开始，一步步加 Agent、写提示词、选模型、连关系，最后宣布完成，再由冻结的 Worker 模型去执行，验证器判断对错。

问题在于，现在的编排器，还是在人提前收集好的题目上练，还要靠塞在提示词里的技能，扩展成本高，也很难自己变强。

### 以前的方法

作者把以前的做法分成三类。学习型编排，在固定题库上训练。自我改进的 Agent，自己出题、改记忆、改代码。技能脚手架，训练时先给技能，再按成功率慢慢撤掉。

它们有三个毛病。第一，课程是人设计的。就算自己出题，出题时技能也一直留在上下文里，挑题和撤技能互不通气。

第二，优势坍塌。GRPO 这类方法，靠比较同一道题几次尝试的好坏来学习，几次全对或全错，就学不到东西。自我对弈的题是按带着技能的难度挑的，技能一撤，这些题就容易全错。

第三，评估信号不可靠。按成功率决定撤不撤技能，可成功率里混着题目难度和技能的作用。技能库给每个技能只打一个带噪声的分，时间一长会漂移，甚至加技能还不如不加。

### 核心想法

R2Orch 的思路，是套两个循环。内循环是自我对弈，一个叫 Proposer 的模型挑题，Director 在这些题上练。外循环负责改进内循环本身，哪个技能不再有用，就把它撤掉。

两个循环之间有两条通道。往下传的是目标，叫递归可学性，告诉 Proposer 该挑什么题。往上传的是证据，叫技能撤除，告诉外循环哪个技能可以拿掉。

这样形成一个闭环。失败被提炼成技能，技能被训练进参数，技能撤掉以后，Proposer 又会找到新的失败。最终目标，是部署时不带任何技能。

### 方法

先看最关键的设计，随机分组。每道题，Director 跑五次，叫一个 rollout 组。系统挑一个待测技能，五次里随机选三次把它藏起来，另外两次照常给。

这五次的结果同时干三件事，训练 Director，给 Proposer 的挑题打分，评估这个技能。论文的说法是，一个 rollout 组同时驱动两个循环。

Director 用 GRPO 的组内相对优势更新，奖励是答对得分，减去一点调用 Worker 的成本。因为五次里三次藏着技能，大部分更新，已经在教 Director 不靠这个技能也能做对。

再看往下的通道，递归可学性。一道题如果每次都对，或者每次都错，就学不到东西，成功率在一半左右，学习信号最强。所以这个分数在一半时最高，全对或全错时是零。

关键在于，这个成功率是在藏起技能的那三次上算的。也就是说，Proposer 被奖励去挑撤掉技能之后，结果仍然有对有错的题。这三次本来就要跑，所以挑题不花额外的 rollout。

另外两条规则。五次全对或全错，Proposer 被扣分。藏技能的三次全错，只有带技能的那两次里有做对的，奖励打折。

往上的通道，技能撤除。因为藏不藏是随机分的，每一组就是一次小型随机对照实验。带技能两次的平均成功率，减去不带技能三次的平均成功率，就是这个技能作用的无偏估计。

作者强调，这和看成功率不一样。成功率里混着题目难度，而递归可学性会把难度往一半推，所以拿成功率设门槛，读到的其实是课程，不是技能。这个差值，正好把难度抵消掉了。

每个技能的差值攒起来，用贝叶斯 bootstrap 估计它还剩多少作用。攒够至少 12 条记录，而且后验估计的剩余好处期望不超过 0.02，就撤掉。

另一头，两部分都失败的题，交给一个大模型编辑器提炼成新技能。撤掉的技能，还会在百分之三十的题上重新测试，证据支持就能恢复。

论文还给了理论命题，比如随机藏技能让这个差值无偏，证明在附录里。

### 实验和效果

实验设置。Director、Proposer 和 Worker 的底座都是 Qwen3.5-9B，用 LoRA 训练。一共训练 200 轮，大约 106 个 A100 小时。

评测用了 12 个基准，覆盖问答、数学、代码和交互任务。6 个提供训练题和同分布测试，另外 6 个不参与训练，比如 SWE-Bench 和 WebShop。测试时，R2Orch 不带任何技能。

对比方法有六类，从直接提示、训练底座，到工作流搜索、强化学习编排、技能内化和自我对弈。论文说，所有方法共用同样的冻结 Worker、训练题和算力预算。

结果在表 1。同分布六个基准的平均准确率，直接用 Qwen3.5-9B 是 61.35，R2Orch 是 89.79，最强的对比方法 PATS 是 86.00。

不参与训练的六个基准，平均从 49.84 提到 78.79，PATS 是 76.13。作者报告，R2Orch 在全部 12 个基准上都是最好的。

论文说，领先最多的是 AIME 2026、WebShop 和 ALFWorld。比如 AIME 2026，直接提示 48.67，R2Orch 81.33，PATS 74.00。代码方面，SWE-Bench 解决率从 15.78 提到 42.81，PATS 是 40.16。

一个很说明问题的对比是，只训练底座模型，SFT 和 GRPO 的同分布平均是 56.87 和 61.04，都没有超过不训练的 61.35。作者的解读是，提升来自怎么组织 Worker，而不是 Worker 变强了。

这张图是训练中留出集的准确率，一条带技能，一条不带。训练到一半左右，不带技能的反超了带技能的。论文的解读是，技能在被撤掉之前，就已经不再帮忙了。

还有迁移实验。用 Qwen3.5-9B 当 Worker 训出来的 Director，不重训，直接换上另外六个模型当 Worker，包括 DeepSeek、Gemini、GLM 等，论文报告每个基准都有提升。作者说，弱模型提升最多，不同模型间同分布成绩的差距，从 25.7 分缩小到 6.4 分。

### 和以前方法的对比

消融实验在表 2，都不带技能测试。去掉整个递归自我对弈，只剩 GRPO，AIME 从 81.33 掉到 59.33，WebShop 从 91.09 掉到 71.72。

把技能撤除换成固定技能，AIME 是 66.67，WebShop 是 76.09。换成 PATS 那样按成功率门槛撤技能，AIME 是 74.67，都比完整版低。

只换 Proposer 的挑题目标，比如均匀随机、DAPO 的动态采样、R-Zero 的不确定性奖励，在同分布六个基准上都比不上递归可学性。AIME 上次好的 Absolute Zero 是 77.33。

挑题成本也低。R2Orch 每轮 120 次 rollout，不需要额外的挑题 rollout，DAPO 和 R-Zero 每轮分别是 720 次和 703 次。

挑出的题也更有用。成功率居中的题，新一组出现有对有错的情况，大约是全对或全错的题的四倍。训练后的 Proposer 也学会了跳过已经解决的题。

技能撤除这边，训练中一共撤了 12 次，每次撤除时剩余好处的后验期望最多 0.019。MedQA 的一张结构卡片第 6 轮被撤，后来重新测试又恢复了。

我的判断是，这篇最有价值的，是把技能还有没有用，变成一个能直接测量的量。用随机对照代替成功率门槛，思路干净，也不用多跑 rollout。

我的判断是，也要看清领先幅度。和 PATS 比，同分布平均高 3.8 个百分点，不参与训练的高 2.7 个百分点，不算碾压。每个测试集只有 128 道题，AIME 只有 30 道，几个点的差距要谨慎看。

### 局限

作者写的局限只有一条。初始技能是他们为每个数据集手工定制的，之后的撤除、修订和提炼都建立在上面，换个新领域怎么自动生成初始技能，还没解决。

另外，从实验设置看，训练只用了 Qwen3.5-9B 一个底座。对比方法用的是各自论文报告的最佳配置。主结果表只比准确率，没有列出推理时调用 Worker 的成本。

作者也提到，能自我改进的编排器和任何 Agent 系统一样可能被滥用，建议在沙箱里运行。

### 未来方向

未来方向，论文点出的开放问题，就是自动生成初始技能。作者把这项工作定位为，朝 Agent 编排器递归自我改进迈出的一步。代码已经在 GitHub 公开。

我的判断是，这种随机藏一部分、比较有和没有的做法，不只适用于编排器。任何靠提示词塞经验、塞规则撑着的 Agent，都可以用它判断哪些规则已经学会、可以拿掉。不过论文没有验证这一点，是我的推测。

我的判断是，最值得跟进的是独立复现。几个点的领先，一个训练底座，加上手工定制的初始技能，要看换了模型和任务，结论还站不站得住。

## English walkthrough

### Intro

This is Daily Frontier Papers. Today's paper is led by the Chinese University of Hong Kong, Shenzhen, with co-authors at several other universities. It's called R2Orch, and it's about agent orchestration that improves itself.

In one line: a model that assembles teams of agents picks its own practice tasks, trains on them, and strips away the skills in its prompt one by one, until it can be deployed with no skills at all.

### Problem

Some background first. Orchestration means handing a task to a team of agents. The paper represents that team as a graph. Each node is an agent with its own role prompt and model, and each edge is a hand-off.

The model that builds this graph is called the Director. It starts from an empty graph and edits it step by step: add an agent, set its prompt, pick its model, connect it to others, and finally finish. Then frozen Worker models run the graph, and a verifier checks whether the answer is right.

The problem is that today's orchestrators still learn from tasks that people collected in advance, and they lean on skills written into their prompts. That's costly to scale, and it's hard for them to improve on their own.

### Prior work

The authors sort earlier work into three families. Learned orchestration trains on a fixed pool of tasks. Self-improving agents refine their own tasks, memory or code. And skill scaffolds give a model skills during training, then remove them once a success rate is high enough.

These run into three problems. First, the curriculum is hand-designed. Even methods that pick their own tasks keep the skills in context while doing it, so choosing tasks and withdrawing skills never inform each other.

Second, advantage collapse. Methods like GRPO learn by comparing several attempts at the same task. If every attempt succeeds, or every attempt fails, there's no difference to learn from. Self-play tunes task difficulty with the skills present, so when a skill is removed, those tasks tend to go all-wrong, and the signal collapses again.

Third, unreliable evaluation. Earlier methods decide whether to remove a skill from a success rate, but that number mixes how hard the chosen tasks are with what the skill actually does. And skill libraries that judge each skill by one noisy score drift, until adding a skill can score worse than adding nothing.

### Key idea

R2Orch nests two loops. The inner loop is self-play: a model called the Proposer picks tasks, and the Director trains on them. The outer loop improves the inner loop itself, by removing each skill once it stops helping.

Two channels connect the loops. Going down is the objective, called Recursive Learnability, which tells the Proposer what to pick. Going up is the evidence, called Skill Withdrawal, which tells the outer loop which skill can go.

That closes a cycle. Failures are distilled into skills, skills are trained into the weights, and once skills are withdrawn, the Proposer finds new failures. The end goal is deployment with zero skills.

### Method

Start with the key design, a randomized group. For each task, the Director runs five times, which the paper calls a rollout group. The system picks one skill to test, hides it from three of the five runs chosen at random, and shows it in the other two.

Those five outcomes do three jobs at once: they train the Director, they score the Proposer's pick, and they test the skill. In the paper's words, one rollout group drives both loops.

The Director is updated with GRPO's group-relative advantages, and its reward is correctness minus a small charge for Worker cost. Since three of the five runs hide the skill under test, most of each update is already teaching the Director to succeed without it.

Now the downward channel, Recursive Learnability. The intuition is simple. A task you always solve, or never solve, teaches nothing. The learning signal is strongest when the success rate is around one half. So the score peaks at one half and drops to zero when every attempt agrees.

The twist is where that success rate is measured. Not with the skill present, but on the three runs where the skill under test is hidden. So the Proposer is rewarded for tasks that still produce a mix of wins and losses once the skill is gone. Those three runs happen anyway, so picking tasks costs no extra rollouts.

Two more rules. If all five runs agree, the Proposer is penalized. And if the hidden runs all fail and only the runs with the skill succeed, its reward is discounted.

Then the upward channel, Skill Withdrawal. Because the hidden runs are chosen at random, every group is a small randomized experiment. The success rate with the skill, minus the success rate without it, is an unbiased estimate of what that skill is worth.

The authors stress why this beats a success-rate threshold. The success rate mixes in task difficulty, and Recursive Learnability is deliberately pushing difficulty toward one half, so a threshold ends up reading the curriculum, not the skill. The difference cancels task difficulty out.

These differences pile up per skill, and a Bayesian bootstrap estimates how much benefit the skill has left. Once a skill has at least twelve records, and its expected remaining benefit to the success rate is at most zero point zero two, it's withdrawn.

On the other side, tasks where both halves of the group fail go to a language-model editor, which distills them into new skills. Withdrawn skills aren't gone for good: thirty percent of tasks re-test them, and they can be restored.

The paper also proves some properties, for instance that random hiding makes this difference unbiased. The proofs are in the appendix.

### Results

The setup. The Director, the Proposer and the Workers all start from Qwen3.5-9B, trained with LoRA. Training runs for two hundred cycles, about one hundred and six A100 hours.

Evaluation covers twelve benchmarks across question answering, math, code and interactive tasks. Six supply the training tasks and in-distribution tests. The other six are held out entirely, like SWE-Bench and WebShop. At test time, R2Orch uses no skills at all.

The baselines come in six families: direct prompting, training the backbone, workflow search, RL-trained orchestrators, skill internalization, and self-play with skill evolution. The paper says every method shares the same frozen Workers, the same training tasks and the same compute budget.

The results are in Table 1. On the six in-distribution benchmarks, average accuracy is sixty-one point three five for plain Qwen3.5-9B, eighty-nine point seven nine for R2Orch, and eighty-six point zero zero for the strongest baseline, PATS.

On the six held-out benchmarks, average accuracy goes from forty-nine point eight four to seventy-eight point seven nine, with PATS at seventy-six point one three. The authors report that R2Orch is best on all twelve benchmarks.

According to the paper, the lead is largest on AIME 2026, WebShop and ALFWorld. On AIME 2026, direct prompting scores forty-eight point six seven, R2Orch eighty-one point three three, and PATS seventy-four. On the code side, SWE-Bench resolution rises from fifteen point seven eight with direct prompting to forty-two point eight one, with PATS at forty point one six.

One comparison is telling. Training the backbone alone, with SFT or with GRPO, gives in-distribution averages of fifty-six point eight seven and sixty-one point zero four, neither of them above the untrained sixty-one point three five. The authors' reading is that the gains come from how the Workers are organized, not from better Workers.

Here's the training curve, accuracy on a held-out set, once with skills and once without. About halfway through training, the zero-skill accuracy overtakes the with-skill accuracy. The paper's interpretation: a skill has already stopped helping before it's removed.

Then transfer. The Director trained with Qwen3.5-9B Workers is used unchanged with six other models as Workers, including DeepSeek, Gemini and GLM, and the paper reports gains on every benchmark. The authors say weaker models gain the most, and the in-distribution spread across models shrinks from twenty-five point seven points to six point four.

### Comparison

The ablations are in Table 2, all tested with zero skills. Remove the whole recursive self-play setup and keep only GRPO, and AIME drops from eighty-one point three three to fifty-nine point three three, while WebShop falls from ninety-one point zero nine to seventy-one point seven two.

Replace Skill Withdrawal with a fixed set of skills, and AIME is sixty-six point six seven, WebShop seventy-six point zero nine. Withdraw skills by a success-rate threshold instead, the PATS rule, and AIME is seventy-four point six seven. All below the full system.

Change only the Proposer's objective, to uniform sampling, DAPO's dynamic sampling, or R-Zero's uncertainty reward, and none of them matches Recursive Learnability on the six in-distribution benchmarks. On AIME, the runner-up, Absolute Zero, scores seventy-seven point three three against eighty-one point three three.

Picking tasks is also cheap. By the paper's count, R2Orch uses one hundred and twenty rollouts per cycle with no extra selection rollouts, while DAPO and R-Zero use seven hundred and twenty and seven hundred and three.

And the picks are useful. Tasks with an intermediate success rate produce a mixed group, some wins and some losses, about four times as often as tasks at zero or one. The authors also find the trained Proposer learns to skip tasks that are already solved.

On the withdrawal side, there were twelve withdrawals during training, each with an expected remaining benefit of at most zero point zero one nine. One MedQA topology card was withdrawn at cycle six, then restored after re-testing.

My read is that the most valuable idea here is turning "is this skill still useful?" into something you can measure directly. Swapping a success-rate threshold for a randomized comparison is clean, and it costs no extra rollouts.

My read is also that the size of the lead matters. Against PATS, the strongest baseline, R2Orch is three point eight points higher on the in-distribution average and two point seven on the held-out average. That's not a blowout. And each test set has only one hundred and twenty-eight items, AIME just thirty, so a few points deserve some caution.

### Limitations

The authors list one limitation. The initial skills are customized by hand for each dataset, and every later withdrawal, revision and distillation builds on them. Deriving those initial skills automatically for a new domain is still unsolved.

The setup itself shows a few more boundaries: training uses a single backbone, Qwen3.5-9B. The baselines run the best configurations reported in their own papers. And the main results table compares accuracy only; it doesn't list the inference cost of calling the Workers.

In their ethics section, the authors also note that a self-improving orchestrator can be misused like any agent system, and they recommend running it in a sandbox.

### Future work

On future work, the open problem the paper names is generating those initial skills automatically. The authors frame this work as a step toward recursive self-improvement of agent orchestrators. The code is public on GitHub.

My read is that hiding part of a group and comparing with and without isn't limited to orchestrators. Any agent propped up by rules and tips stuffed into its prompt could use the same trick to find out which rules it has learned and can drop. The paper doesn't test that; it's my extrapolation.

My read is that the thing to watch is independent replication. A lead of a few points, one training backbone, and hand-made starting skills: the question is whether the result holds with other models and other tasks.
