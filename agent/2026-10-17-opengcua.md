## 中文讲解

### 开场

这里是每日前沿文章。今天讲一篇阿里巴巴的论文，叫 OpenGCUA，目标是把通用电脑操作 Agent 的整套技术栈，开放给社区一起做。

先说结果。作者用同一套运行框架，测了包括 GPT-6 Astra 和 Claude Opus 5 在内的 8 个前沿模型，在 OSWorld-v2 上，平均部分得分提高了 19.6 分，每个任务的步数平均少了 53%。

### 问题

先说背景。电脑操作 Agent，英文叫 computer-use agent，就是让模型像人一样操作电脑完成任务。过去很多研究，把它当成纯图形界面的 Agent，看截图，然后点鼠标、敲键盘。

但作者认为，问题已经变了。前沿系统开始把图形界面和命令行、无障碍接口这些工具混在一起用，OpenAI 现在也推荐让模型写代码来操作电脑。问题从模型会不会点界面，变成了系统能不能用任何可行的办法，在真实电脑上把活干完。

难点在于，像 GPT-6 Astra 这样的前沿系统基本是闭源的，模型权重、完整的提示词、真机运行框架和执行轨迹都拿不到，外界很难复现，也很难比较不同的设计。

### 以前的方法

作者先给了一个定义，叫通用电脑操作 Agent，简称 GCUA。它的特点是，每一步都由模型自己做三个决定，看什么，怎么做，以及怎么组织自己的工作。

拿这三个决定去看以前的方法，就很清楚了。这张表里，纯 GUI Agent 三个决定全被固定，只看截图，每步一个操作，记忆按规则保留。命令行 Agent 看不到屏幕。多 Agent 混合系统，由调度者按子任务分配用哪种界面。

他们自己之前的工作 Qwen-UI-Agent，把图形界面和命令行放进同一个动作空间，一次可以输出一批动作。但每一步固定给截图，记忆也按规则管理。在作者的框架里，这只是 GCUA 的一个特例。

### 核心想法

这篇的核心有两个设计。第一个叫代码执行，就是让模型每一步写一段程序，把点击、键盘这些界面操作，和 shell 命令、Python 计算写在一起。

它和批量动作的区别在于，批量动作在生成时就定死了，模型得在看到第一次点击的结果之前，就把所有点击都决定好。程序不一样，可以写条件、循环和检查，比如弹窗出现了就关掉，每一行填三个字段，最后确认状态显示已保存。作者的说法是，一批动作，就是没有控制流的程序。

第二个设计，叫 harness 到模型的决策转移。harness 就是包在模型外面的运行框架。很多 harness 用固定规则替模型做决定，比如每一步之后都截一张图。作者的思路是，框架提供可靠的机制，什么时候用，由模型来决定。

### 方法

具体实现上，提示词要求模型每一步输出一个 Python 代码块，在 OSWorld-v2 的配置里，桌面操作用 PyAutoGUI，shell 命令用一个叫 bash 的函数。框架先检查语法再执行，然后把标准输出、报错和执行状态返回给模型。

作者分析了 GPT-6 Astra 的执行轨迹，总结出五种常见写法，这张图是其中三种。比如生成合同，程序先点按钮，再用代码检查文件和完成状态，通过了才点下一个按钮。又比如回邮件前，先把草稿复制出来，和保存的版本比对，一致才点发送。

决策转移这边有三个机制。一是按需截图，模型调用 screenshot 才拿到新截图，文字输出够用就不要。二是 todo 任务记录，模型自己记下哪些做了，哪些还没验证。三是 intent，每段程序执行前，先用一句话说明目的，方便真机上的用户看懂。

另外有两条规则还留在框架手里，滚动截图缓冲成批删掉旧截图，micro-compaction 把旧的工具输出换成短占位符，都是为了控制上下文长度，其中滚动缓冲成批删除，是为了少破坏提示词缓存。

论文还做了真机部分，包括一个跨设备 SDK，用同一套接口操作电脑、浏览器和手机，以及一个真机 harness。它优先用无障碍接口操作界面元素，其次是针对窗口的坐标输入，最后才用前台输入，尽量不打扰同时在用电脑的人。这两部分都还是初步版本。

### 实验和效果

实验在 OSWorld-v2 的离线子集上做，一共 82 个任务，去掉了 26 个需要联网的任务。指标有两个，完整成功率，和按完成程度给分的部分得分。对比的基线，是只用图形界面、但支持批量动作的设置。

结果在表 2。8 个模型的平均部分得分，从 45.3 提高到 64.9，每个模型的完整成功率也都提高了。提升最大的是 GLM-5.3-Flash，加了 35.2 分，DeepSeek-V4.1-Flash 加了 29.8 分。

原本最强的 GPT-6 Astra，分数从 67.1 提到 75.7，每个任务的步数从 102.1 降到 33.5，少了 67.2%。

不过步数少，不一定 token 少。8 个模型里有 6 个输出 token 减少，平均少了 27.2%，但 GPT-6 Astra 的输出 token 基本没变。

作者还算了一笔钱的账，这张图的横轴是每个任务的平均花费。按作者假设的 API 价格，预算很低的时候，得分最高的是 Qwen3.8-Flash，大约每个任务 0.38 美元，拿到 60.5 分。预算往上加，最后是 GPT-6 Astra 拿到最高的 75.7 分，大约每个任务 15.26 美元。

### 和以前方法的对比

更关键的，是和图形界面加命令行的混合方案比，也就是他们自己之前那一类做法。两边能用的界面一样，区别只在代码执行和模型自主的流程控制。表 3 里，4 个模型的分数都提高了 4.4 到 9.1 分，步数也更少。

代码执行的消融在这张图。在 Qwen3.8-Max、DeepSeek 和 GLM 三个模型上，代码执行的分数都最高，步数都最少。和批量 GUI 加命令行相比，GLM-5.3-Flash 的分数从 55.8 提到 63.2，Qwen3.8-Max 的步数从 66.1 降到 54.9。

决策转移的消融在表 4，作者自己也说，这些机制大多不是为了提分。按需截图让缓存命中率明显上升，Qwen3.8-Max 从 75.6% 到 86.1%，DeepSeek 从 61.9% 到 76.3%。todo 让分数小幅上升，intent 反而让分数略降，它本来的目的是让用户看懂。

真机部分是四个 macOS 任务。同一套 harness 下，GPT-6 Astra 四个任务都完成了，平均每个任务 12.9K 个输出 token。Qwen3.8-Max 完成了 3 个，输出 token 是它的 5.7 倍，推理 token 是 19.4 倍。但按作者的价格估算，Qwen3.8-Max 每个任务大约 1.49 美元，GPT-6 Astra 大约 18.29 美元。

这张图是一个具体案例。一个 Excel 工作簿任务，GPT-6 Astra 先写了一个求解器，用 7 个示例验证，再把 125 道题全部算完。Qwen3.8-Max 也用了函数和循环，但写死了行号范围，只覆盖了 85 道，留下 40 个答案格没填。作者的结论是，差距不在会不会写循环，而在能不能用代码覆盖整个任务，并检查遗漏。

我的判断是，这篇最有说服力的，是在同样能用图形界面和命令行的情况下，代码执行依然带来提升，说明执行方式本身就是一个设计变量，不只是给模型多接几个工具。

我的判断是，也要看到，主实验的基线是纯图形界面，这个基线偏弱。换成更强的图形界面加命令行基线，提升就缩小到 4.4 到 9.1 分，而且这部分只测了 4 个模型。

### 局限

论文没有单独的局限章节，但文中写明了几点。第一，这次发布不包含训练好的模型，所有结果都是用现成的前沿模型，测试框架设计的效果。

第二，消融部分多处写的是挑选出的那次运行，论文没有给出多次重复的误差范围。表 4 里也能看到，加了按需截图之后，两个模型每个任务的步数反而变多了。

第三，真机实验只有 4 个任务，每个模型只取一次运行的结果，作者明确说，这只能刻画被测的配置，不能当成模型排名。另外，OSWorld-v2 上按用时限制的那组比较，用时受 API 带宽、限流和排队影响，没有在模型之间控制，作者只把它当探索性的参考。

第四，todo 里记的状态只是模型自己的判断，不是独立验证，程序里的断言检查，也不能代替独立评测。真机 harness 和 SDK，目前都还是初步版本。

### 未来方向

作者的路线图里，下一次发布的核心是一个 GCUA 模型，把这篇研究的设计变成模型学到的能力，比如用代码协调界面和程序操作，需要时才观察，持续维护任务状态，尤其是加强真机场景。

他们还计划让推理更简洁，减少过度思考，并在真机上，尤其是 macOS 上，建立评测环境和 benchmark。

我的判断是，这篇的价值更多在开放和方法论，它给了社区一套可以复现、可以比较的电脑操作 Agent 设计，还有 8 个前沿模型的评测轨迹。真正的考验，是下一版自己训练的模型，能不能把这些设计内化，而不只是靠提示词和框架。

## English walkthrough

### Intro

This is Daily Frontier Papers. Today's paper is from Alibaba. It's called OpenGCUA, and the aim is to open up the full stack behind general-purpose computer-use agents.

The headline result: with one shared harness, the authors tested eight frontier models, including GPT-6 Astra and Claude Opus 5. On OSWorld-v2, mean partial score rose by nineteen point six points, and steps per task fell by fifty-three percent on average.

### Problem

A computer-use agent is a model that operates a computer like a person would. Much of the research treats these as pure GUI agents: look at a screenshot, then click and type.

The authors argue the question has moved on. Frontier systems now mix the GUI with the shell, accessibility trees and other tools, and OpenAI now recommends having models write code to drive the computer. The question is no longer how well a model clicks. It's how well a system gets work done on a real computer, by whatever means works.

The trouble is that systems like GPT-6 Astra are largely closed. Weights, full prompts, real-device harnesses and execution trajectories aren't available, so outsiders can't reproduce them or compare design choices.

### Prior work

So the authors define the generalist computer-use agent, or GCUA. At every step, the model makes three decisions itself: what to observe, how to act, and how to organize its work.

That makes earlier approaches easy to place. In this table, a GUI agent has all three fixed: screenshot only, one GUI action per step, memory by rule. A command-line agent can't see the screen. Multi-agent hybrids have an orchestrator pick the interface once per subtask.

The team's own earlier system, Qwen-UI-Agent, put GUI and command-line actions in one action space and let the model emit a batch of actions per call. But it still got a screenshot every step, and memory followed a fixed rule. Here, that's just a special case of a GCUA.

### Key idea

The paper rests on two ideas. The first is code execution: each step, the model writes a program that mixes clicks and key presses with shell commands and Python.

Compare that with batched actions. A batch is fixed when it's generated, so the model must decide every click before seeing what the first one did. A program can branch, loop and check: if a dialog appears, dismiss it; for each row, fill three fields; at the end, assert the status reads Saved. As the authors put it, a batch is a program without control flow.

The second idea is harness-to-model decision transfer. The harness is the software wrapped around the model, and many harnesses decide things by rule, like taking a screenshot after every step. The authors' view: the harness should provide reliable mechanisms, and the model should decide when to use them.

### Method

Concretely, the prompt asks for one Python code block per step, and on OSWorld-v2 the model drives the desktop with PyAutoGUI and runs shell commands through a function called bash. The harness syntax-checks and runs the code, then returns the output, errors and execution status.

From GPT-6 Astra's trajectories, the authors pull out five recurring patterns; this figure shows three. In a contract task, the program clicks a button, checks the files and completion status in code, and only then clicks the next button. Before sending an email, it compares the draft with the saved version and clicks Send only if they match.

Decision transfer has three mechanisms. On-demand screenshots: the model gets a new image only when it asks for one. A todo record, where the model tracks what's done and what's unverified. And an intent line, one sentence on what each program is for, so a user on a real machine can follow along.

Two policies stay with the harness: a rolling screenshot buffer that drops old images in batches, and micro-compaction, which swaps old tool outputs for short placeholders. Both limit context, and the screenshot buffer drops images in batches to disturb the prompt cache as little as possible.

There's also a real-device side: a cross-device SDK with one interface for computers, browsers and phones, and a harness for real machines. It prefers acting through accessibility, then window-targeted input, and only then foreground input, to stay out of the user's way. Both pieces are preliminary.

### Results

Evaluation uses the offline subset of OSWorld-v2: eighty-two tasks, excluding twenty-six that need the internet. Metrics are full-task success and a partial score that credits partial completion. The baseline is GUI-only, with batched actions allowed.

The results are in Table 2. Mean partial score across the eight models rises from forty-five point three to sixty-four point nine, and full-task success rises for every model. The biggest gains: GLM-5.3-Flash, up thirty-five point two, and DeepSeek-V4.1-Flash, up twenty-nine point eight.

Even GPT-6 Astra, the strongest to begin with, goes from sixty-seven point one to seventy-five point seven, and its steps per task drop from about a hundred and two to thirty-three and a half, sixty-seven percent fewer.

Fewer steps doesn't always mean fewer tokens, though. Output tokens fall for six of the eight models, by twenty-seven percent on average, but GPT-6 Astra's output stays about the same.

The authors also looked at cost; this figure plots score against average spend per task. Under their assumed API prices, the cheap end is led by Qwen3.8-Flash, about thirty-eight cents a task for sixty point five points. At the top, GPT-6 Astra scores seventy-five point seven, at about fifteen dollars twenty-six a task.

### Comparison

The more telling comparison is against GUI plus command-line hybrids, the kind of system the team built before. Same interfaces on both sides; the difference is code execution and model-driven workflow control. In Table 3, all four models gain four point four to nine point one points, with fewer steps.

The code-execution ablation is in this figure. On Qwen3.8-Max, DeepSeek and GLM, code execution has the highest score and fewest steps every time. Against batched GUI plus command line, GLM-5.3-Flash goes from fifty-five point eight to sixty-three point two, and Qwen3.8-Max cuts steps from sixty-six point one to fifty-four point nine.

The decision-transfer ablation is in Table 4, and the authors say most of these mechanisms aren't meant to raise scores. On-demand screenshots lift the cache hit rate, from seventy-five point six to eighty-six point one percent for Qwen3.8-Max, and from sixty-one point nine to seventy-six point three for DeepSeek. Todo nudges scores up; intent nudges them slightly down, and its purpose is helping the user follow along, not scores.

The real-device part is four macOS tasks. Under the same harness, GPT-6 Astra completes all four, averaging twelve point nine thousand output tokens per task. Qwen3.8-Max completes three, with five point seven times the output tokens and nineteen point four times the reasoning tokens. Yet by the authors' estimates, Qwen3.8-Max costs about a dollar fifty a task, versus about eighteen thirty for GPT-6 Astra.

This figure shows one case. On an Excel workbook task, GPT-6 Astra writes a solver, checks it against seven worked examples, and answers all one hundred twenty-five questions. Qwen3.8-Max also uses loops, but hard-codes row ranges, covers only eighty-five, and leaves forty answer cells empty. The gap, the authors conclude, isn't writing a loop. It's using code to cover the whole task and checking for what's missing.

My read is that the strongest result is that code execution still helps when both sides already have the GUI and the shell. How the agent executes is a design variable in its own right, not just a matter of adding tools.

My read is also that the headline baseline, GUI-only, is weak. Against the stronger GUI plus command-line baseline, the gain shrinks to four point four to nine point one points, on only four models.

### Limitations

There's no separate limitations section, but the paper is explicit about several things. First, this release has no trained model; every result is existing frontier models running in the new harness.

Second, many ablations are described as selected runs, and the paper doesn't report variation across repeats. Table 4 also shows on-demand screenshots actually increased steps per task for both models.

Third, the real-device study is four tasks with one selected run per model, and the authors say it describes the configurations tested, not a model ranking. Separately, the OSWorld-v2 time-limit comparison depends on API bandwidth, rate limits and queuing that weren't controlled, so they treat it as exploratory.

Fourth, todo statuses are the model's own assessment, not independent verification, and in-program assertions don't replace independent evaluation. The real-device harness and SDK are still preliminary.

### Future work

On the roadmap, the next release centers on a GCUA model that turns these designs into learned skills: coordinating GUI and programmatic actions through code, observing only when needed, tracking task state, and especially doing better on real devices.

They also plan more concise reasoning with less overthinking, and real-device evaluation environments and benchmarks, macOS in particular.

My read is that the value here is mostly openness and method: a reproducible, comparable design for computer-use agents, plus evaluation trajectories from eight frontier models. The real test is whether their own trained model can internalize these designs instead of leaning on prompts and a harness.
