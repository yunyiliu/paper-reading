**失败的题换个框架再学**

- 方向 Direction: Agent

## 中文讲解

### 开场

这里是每日前沿文章。今天讲一篇上海交通大学和小红书等单位的论文，叫 Harness-S，意思是，向兄弟 harness 学习，训练能泛化的 Agent。

它要回答的问题是，换一套更好的外部框架，能救活不少失败任务，那这些本事，能不能学进模型本身，拿掉框架以后还在。

### 问题

先解释 harness。Agent 表现好不好，不只看模型权重，还要看包在外面的那一层，提示词、工具接口、上下文和记忆、执行规则，论文统称 harness，可以理解成执行框架。

模型不变，换一套 harness，模型看到的信息、决定怎么变成动作，都会变。所以最近不少工作，用执行反馈自动修改 harness。

作者从一个基础框架 H0 出发，不断改出变体，叫兄弟 harness，并观察到三个现象。

第一，局部性。一次修改通常只修好一部分失败，又会弄坏原来做对的题。比如图里的 H1，修好 26 道，弄坏 11 道。

第二，互补性。兄弟之间能救回彼此的错。在 AppWorld 上，四个兄弟各跑一次，合起来覆盖 65.65% 的任务，基础框架跑四次只有 44.66%。

第三，不稳定性。harness 的好坏会随模型训练而变。H1 一开始比 H0 多解 15 道题，到第 20 步，反而少了 4 道。

### 以前的方法

以前主要有两条路。一条是固定模型，只优化 harness，想找一个最好的通用框架，比如 Meta-Harness。

作者认为这很难走通。各个修补的要求可能冲突，就算兼容，叠在一起也会互相干扰，合成的框架反而丢掉了各自的长处。

另一条是 harness 和模型一起进化，比如 WHALE 和 HarnessForge。可模型一变，旧修补就不太管用，得反复生成新变体，成本很高，回到基础框架上，提升也不一定还在。

### 核心想法

Harness-S 不找万能框架。基础框架做不出来的题，才请兄弟 harness 救场，再把救场学到的本事，训练进同一个模型。

检验标准很严格，训练完的模型回到原来的 H0 上跑，看提升还在不在。

这张总览图分三块，左边离线进化出兄弟池，中间是救场训练，右边是能力转移进模型。

### 方法

第一步，定向 harness 进化。从 H0 开始跑训练任务，分析失败的根本原因，把相关原因归成一个修复方向，每个子 harness 只针对一个方向改。

能改的组件有六类，提示词、技能、上下文、记忆、hooks，也就是工具调用后自动插入的提醒，还有工具视图。编辑模型是 GLM-5.3，在 AppWorld 上进化了三轮。

挑父代时，不挑单个最强的，而是挑一组合起来在验证集上覆盖题目最多的。所有能运行、合规的子代都留下，组成兄弟池，训练中不再改动。最终池里有 H0 和 19 个兄弟。

举两个例子。一个兄弟加了提醒，看到分页就翻到最后，别把第一页当全部。另一个要求，任务有多个条件时分别查询，再取交集。

第二步，互补救场训练。训练用强化学习里的 GRPO，每道题在 H0 下跑 8 次，组内比较，强化成功的，抑制失败的。

问题是，如果 8 次全失败，组内没有好坏之分，这道题就没有学习信号。

这时 Harness-S 出手。路由器挑出 8 个兄弟，同一个模型在每个兄弟下从头再试一次，这组新轨迹替换掉全失败的那组，拿去训练。

只要救回一部分，组里就有成功也有失败，模型就有东西可学。算损失时只算模型自己写的 token，harness 插入的指令和工具返回都不算。

第三块是自适应路由器。每个兄弟有一份行为档案，写着它在什么情况下比 H0 好，什么情况下更差，由大模型对比成对的验证轨迹总结出来。

选择时，多个大模型各自排名，每张选票排四个，权重分别是 1、0.75、0.5 和 0.25，加总取前几名。

因为 harness 的价值会变，档案要定期刷新。在 AppWorld 4B 实验里，每训练 10 步，用当前模型重跑验证集更新档案，论文叫重新锚定。

训练完后，路由器还能在推理时用，给每道题挑排第一的 harness，叫 Rank-1。

### 实验和效果

模型是 Qwen3.5 的 4B 和 9B，H0 是 DeepSeek Harness。基准有三个，AppWorld 调用应用 API，DBBench 操作数据库，SWE-Gym 修代码。每题跑 3 次，Pass@3 是至少成功一次的比例，Avg@3 是平均成功率。

主要结果在表 1。最严格的设置，是训练完的 4B 模型回到 H0 上。AppWorld 的 Pass@3 从训练前的 42.62 提到 67.56，普通 GRPO 只到 60.31。

SWE-Gym 上差距更大，同样是 4B，普通 GRPO 是 24.38，Harness-S 是 38.75。

会不会只是多采样的功劳。论文做了对照，全失败时也补采样，但仍在 H0 下补，叫 H0 rescue。在三个基准、两个尺寸上，Harness-S 都比它好。

加上 Rank-1 路由，9B 模型在 DBBench 上 Pass@3 达到 78.00，超过论文测的三个前沿模型，其中最高的 GLM-5.3-Flash 是 76.67。

再看训练信号。AppWorld 4B 上，同时有成功和失败的有效组，Harness-S 占 79.38%，H0 rescue 是 70.94%，普通 GRPO 是 64.69%。验证集成功率最后分别是 63.33%、54.00% 和 48.00%。

有意思的是，固定混合 harness，比如一半在 H0、一半在 Claude Code 下跑，最后验证成功率反而低于普通 GRPO。作者的解读是，多样性要用在基础框架失败的题上，才更有用。

行为也变了。AppWorld 上，第一次调用 API 前先查接口说明的比例，基础模型 22.9%，GRPO 38.2%，Harness-S 67.6%。SWE-Gym 上测试跑不起来时，改用断言检查的比例，Harness-S 是 48.5%，GRPO 只有 13.3%。这些比例由大模型给轨迹打标签统计。

一个案例。训练时，某个兄弟救回了一道 Venmo 账户找回任务。后来在没训练过的 Amazon 题目上，训练后的模型在 H0 下走完了读验证码、重置密码、验证登录的整套流程，GRPO 模型却没改密码。

路由器的数据也支持能力被学了进去。训练前，路由器把 H0 排第一的题只有 1.53%，训练后是 22.52%。Rank-1 比 H0 高出的 Pass@3，从 14 个多点缩到 0.76 个点。

换到训练没用过的外部框架 Claude Code 和 OpenClaw，Harness-S 的 Pass@3 仍然最高，比 GRPO 高 4.96 到 12.50 个百分点。

### 和以前方法的对比

和其他 harness 方法比。模型冻结、只进化 harness 时，兄弟池加按题路由，4B 在 AppWorld 上 Pass@3 是 56.87，Meta-Harness 是 48.09。

和模型、harness 一起进化的方法比，WHALE 是 63.36，HarnessForge 是 59.54，用的还是各自选出的最佳框架，而 Harness-S 回到 H0 上就有 67.56。

成本上，比起普通 GRPO，Harness-S 多用 18.44% 的训练采样，GPU 时间从 50.58 涨到 67.19 卡时，Avg@3 高 7.89 个点。H0 rescue 多用 41.25% 采样，花了 97.77 卡时，效果却不如 Harness-S。

算上搜索 harness 的全流程，Harness-S 用了 18.69 百万 API token，比 WHALE 多，比 HarnessForge 少。

我的判断是，这篇的价值，是把 harness 从部署时的拐杖，变成训练时的探索工具。全失败的题本来是 GRPO 的盲区，换个框架救回来，正好补上强化学习最缺的信号。

### 局限

论文没有单独的局限章节，但从实验设置看，有几点要注意。

第一，只测了 Qwen3.5 的 4B 和 9B。训练信号、救场策略、路由器这些分析，基本只在 AppWorld 4B 一个设置上做。

第二，和前沿模型还有差距。最好的 9B 加路由，AppWorld 的 Pass@3 是 75.19，GPT-6-Sol 是 82.82，SWE-Gym 上是 43.75 对 53.13。

第三，换到外部框架后，Harness-S 的分数都低于它在 DeepSeek Harness 下的成绩，作者也承认执行框架仍有影响。整套流程还要靠外部大模型改 harness、写档案和投票。

另外，行为迁移案例只有两个，行为比例也是大模型打的标签，论文的措辞是，这些证据支持能力转移。

### 未来方向

作者的下一步，一是能力转移能否长期保持，兄弟池怎么跨模型复用，二是独立开发的 harness 之间怎么交换任务状态，三是 Harness Scaling，看修复方向更多时，收益和校准成本怎么变。

我的判断是，如果兄弟池真能跨模型复用，进化 harness 的成本就能摊薄，方法会实用很多，但论文还没验证这一点。

我的判断是，对做 Agent 训练的团队，这篇的启发很实在，全失败的题别直接扔，换个框架再试，救回来的轨迹就是最缺的信号。

## English walkthrough

### Intro

This is Daily Frontier Papers. Today's paper comes from Shanghai Jiao Tong University, Xiaohongshu and partners. It's called Harness-S: learning from sibling harnesses for generalizable agent training.

The question is practical. A better wrapper around an agent can rescue a lot of failed tasks. Can the model learn those skills, so they survive once the wrapper is gone?

### Problem

First, what's a harness? An agent's behavior depends on more than its weights. It also depends on the layer around the model: prompts, tool interfaces, context and memory, and execution rules. The paper calls that layer the harness.

Keep the model fixed, swap the harness, and both what the model sees and how its decisions become actions change. So a lot of recent work optimizes harnesses automatically from execution feedback.

The authors start from a base harness, H zero, and keep editing it into variants they call sibling harnesses. They notice three things.

First, locality. An edit fixes some failures and breaks some tasks that used to work. Here, H one repairs twenty-six tasks but regresses eleven.

Second, complementarity. Siblings rescue each other's mistakes. On AppWorld, four siblings run once each cover sixty-five point six five percent of tasks, while four attempts with the base harness reach forty-four point six six.

Third, nonstationarity. A harness's value changes as the model trains. H one starts out solving fifteen more tasks than H zero. By step twenty, it solves four fewer.

### Prior work

There have been two main approaches. One freezes the model and optimizes only the harness, searching for a single best design, like Meta-Harness.

The authors argue that's a dead end. Local repairs can conflict, and even compatible ones interfere when stacked, so the merged design loses the strengths of its parts.

The other evolves harness and model together, as in WHALE and HarnessForge. But each time the model changes, old repairs matter less, so variants must be regenerated and revalidated, which is expensive. And the gains may not survive a return to the base harness.

### Key idea

Harness-S doesn't look for one universal harness. Only when the base harness fails does it call in siblings to rescue the task, and then it trains what the rescue found into one shared model.

The test is strict. After training, the model goes back to the original H zero, and the question is whether the gains hold.

The overview figure has three parts: offline evolution of a sibling pool, rescue training, and transfer into the policy.

### Method

Step one is directional harness evolution. Starting from H zero, the model runs training tasks, failures are traced to root causes, related causes form a repair direction, and each child harness targets one direction.

Six kinds of components can be edited: prompts, skills, context, memory, hooks, meaning reminders injected after a tool call, and the tool view. The editor is GLM-5.3, and the AppWorld search ran three rounds.

Parents for the next round aren't the single strongest variants, but the set that jointly solves the most validation tasks. Every child that runs and follows the protocol is kept, forming a sibling pool that stays fixed during training. The final pool holds H zero plus nineteen siblings.

Two examples. One sibling adds a reminder: when results are paginated, keep going, and don't treat the first page as complete. Another says that when a request combines conditions, fetch each separately and take the intersection.

Step two is complementary harness rescue training. Training uses GRPO, a reinforcement learning method. Each task gets eight attempts under H zero, compared within the group, so successes are reinforced over failures.

But if all eight fail, there's nothing to compare, and the task gives no learning signal.

That's where Harness-S steps in. A router picks eight siblings, and the same model makes one fresh attempt under each from the task's initial state. This group replaces the all-failure group for training.

If even a few succeed, the group has successes and failures, and there's something to learn. The loss only counts tokens the model wrote; harness instructions and tool outputs are excluded.

Part three is the adaptive router. Each sibling has a behavior profile: when it helps compared with H zero, and when it hurts. A language model writes these by comparing paired validation trajectories.

To choose, several language models rank candidates independently. Each ballot ranks four, weighted one, three quarters, one half and one quarter, and the scores are summed.

Because a harness's value shifts, profiles get refreshed. In the AppWorld 4B run, every ten updates the current model reruns validation and the profiles are rebuilt. The paper calls this re-anchoring.

After training, the router can also be used at inference, picking the top-ranked harness per task. That's called Rank-1.

### Results

The models are Qwen3.5 4B and 9B, and H zero is DeepSeek Harness. The benchmarks are AppWorld for app APIs, DBBench for databases, and SWE-Gym for software engineering. Each task gets three attempts: pass at three is the share solved at least once, average at three the mean success rate.

The main results are in Table 1. Strictest setting first: the trained 4B model back on H zero. AppWorld pass at three goes from forty-two point six two before training to sixty-seven point five six. Plain GRPO reaches sixty point three one.

The gap is bigger on SWE-Gym. For the same 4B model, plain GRPO gets twenty-four point three eight, Harness-S thirty-eight point seven five.

Is it just extra sampling? There's a control: when all attempts fail, resample, but under H zero again, called H zero rescue. Harness-S beats it on all three benchmarks at both sizes.

Add Rank-1 routing, and the 9B model hits seventy-eight point zero zero on DBBench, above all three frontier models tested. The best of those, GLM-5.3-Flash, scores seventy-six point six seven.

Now the training signal. On AppWorld 4B, effective groups, with both successes and failures, are seventy-nine point three eight percent for Harness-S, seventy point nine four for H zero rescue, and sixty-four point six nine for plain GRPO. Final validation success is sixty-three point three three, fifty-four, and forty-eight percent.

Interestingly, fixed harness mixtures, like half the attempts under H zero and half under Claude Code, end with lower validation success than plain GRPO. The authors' reading: diversity helps most when aimed at tasks where the base harness fails.

Behavior changes too. On AppWorld, checking the API schema before the first call goes from twenty-two point nine percent for the base model and thirty-eight point two for GRPO to sixty-seven point six. On SWE-Gym, when tests are blocked, Harness-S switches to assertion checks forty-eight point five percent of the time, versus thirteen point three for GRPO. A language model labeled these trajectories.

One case. In training, a sibling rescued a Venmo account-recovery task: read the codes, reset the password, verify the login. Later, on an Amazon instance it never trained on, the trained model completed the whole procedure under H zero. The GRPO model read the inbox but never changed the password.

The router data points the same way. Before training, the router ranked H zero first on one point five three percent of tasks, and after training, on twenty-two point five two. Rank-1's pass at three lead over H zero shrinks from just over fourteen points to zero point seven six.

On outside harnesses not used in training, Claude Code and OpenClaw, Harness-S still has the highest pass at three, four point nine six to twelve point five points above GRPO.

### Comparison

Against other harness methods. With the model frozen, the sibling pool with per-task routing gets fifty-six point eight seven on AppWorld 4B, versus forty-eight point zero nine for Meta-Harness.

Against joint model-and-harness methods, WHALE scores sixty-three point three six and HarnessForge fifty-nine point five four, each on its own best harness. Harness-S, on plain H zero, scores sixty-seven point five six.

On cost, versus plain GRPO, Harness-S uses eighteen point four four percent more training rollouts, and GPU hours rise from fifty point five eight to sixty-seven point one nine, for an average at three seven point eight nine points higher. H zero rescue uses forty-one point two five percent more rollouts and ninety-seven point seven seven GPU hours, and still scores lower.

Counting harness search, the full pipeline uses eighteen point six nine million API tokens: more than WHALE, fewer than HarnessForge.

My read is that the real contribution is turning the harness from a deployment crutch into a training-time exploration tool. All-failure tasks are a blind spot for GRPO, and rescuing them fills in exactly the signal it's missing.

### Limitations

There's no separate limitations section, but the setup suggests some caveats.

First, only Qwen3.5 4B and 9B were tested. The deeper analyses of training signal, rescue strategy and routing are mostly on one setting, AppWorld with 4B.

Second, there's still a gap to frontier models. The best 9B with routing gets seventy-five point one nine on AppWorld against eighty-two point eight two for GPT-6-Sol, and forty-three point seven five against fifty-three point one three on SWE-Gym.

Third, on outside harnesses, Harness-S scores below its own DeepSeek Harness results, and the authors acknowledge the execution interface still affects reliability. The pipeline also leans on external language models to edit harnesses, write profiles and vote.

And there are only two behavior-transfer cases, with behavior rates labeled by a language model. The paper's wording is that this evidence supports transfer.

### Future work

The authors list three next steps: whether transfer lasts and how to reuse a pool across policies; how independent harnesses can exchange task state; and harness scaling, measuring how more repair diversity affects gains and calibration cost.

My read is that if a sibling pool can be reused across models, the cost of evolving harnesses gets spread out, and the method gets much more practical. That hasn't been tested yet.

My read is that for teams training agents, the takeaway is concrete: don't throw away tasks where every attempt fails. Retry them under a different harness, because rescued trajectories are often exactly the signal you're missing.
