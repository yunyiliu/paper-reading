## 中文讲解

### 开场

这里是每日前沿文章。今天讲一篇韩国科学技术院 KAIST 的论文，名字叫 L3G-World，意思是用潜空间的 3D 高斯做记忆，实时生成一个可以一直走下去的世界。

它想做的是，给一张图片和一条相机路线，模型一边走一边生成视频，走得很远再走回来，看到的还是原来那个地方，而且要实时。

### 问题

先说背景。交互式视频世界模型，就是根据用户的操作，比如按键或者相机移动，生成接下来的画面，可以用在游戏、真实世界仿真和具身仿真里。

难点在于两件事要同时做到。一是长时间探索之后，回到走过的地方，场景还要一致，这叫回环一致性。二是生成速度要跟得上，做到实时。

### 以前的方法

以前主要有两条路。第一条是时间上下文，生成新的一段视频时，回头去取历史帧，或者扩散模型注意力层里的 KV cache。

问题是，这些历史的显存和计算量，会随着生成的长度一起涨。论文表 1 里，WorldKV 生成 400 帧直接显存溢出，Yume 1.5 峰值显存 66.7 GiB，每秒只有 1.42 帧。

第二条是显式的 3D 记忆，把生成过的画面重建成点云或者 3D 高斯存起来。其中前馈式的方法速度快，但它给每个像素都预测 3D 点，同一块区域被反复堆进去，越来越冗余，渲染越来越慢，而且存进去的点不会再更新，早先重建错的几何，可能一直留在记忆里。

另一类是优化式的方法，记忆比较紧凑，但每次都要迭代优化，延迟很大。表 1 里的 ArtiFixer，每秒只有 0.10 帧。

还有一个容易忽略的开销。现在的视频生成模型都工作在 VAE 的潜空间里，也就是压缩后的特征空间。以前的 3D 记忆只能渲染出普通的 RGB 图片，再用 VAE 编码一遍才能喂给生成器，这一步就让实时变得不可能。

### 核心想法

L3G-World 围绕两个决定来设计记忆。第一，记忆是有选择地更新的，只在新看到的地方生成新的高斯，已经有的高斯就去修正它，这样记忆的大小跟着场景的范围涨，而不是跟着视频的长度涨。

第二，每个高斯除了颜色，还存一份 VAE 潜空间的特征。这样记忆可以直接渲染到生成器的潜空间里，不用再走一遍 VAE 编码。

这里解释一下 3D 高斯。3D Gaussian Splatting 是把一个场景表示成很多个半透明的椭球，每个椭球有位置、形状、不透明度和颜色，从任意视角都能很快地渲染出图像。

### 方法

整个系统由两个模块轮流工作。L3G-Mem 负责读写记忆，L3G-Gen 负责生成下一段视频。生成出来的视频交给 L3G-Mem 更新记忆，更新后的记忆再去指导下一段生成。

先看 L3G-Mem 怎么决定在哪里加新高斯。它把已有的记忆渲染到当前的相机视角，得到颜色图和不透明度图。不透明度低，说明这里记忆还没覆盖，颜色误差大，说明这里记忆没画对。这两类区域被标记出来，叫生成掩码。

在被标记的区域里，用几何基础模型 Depth Anything 3 提取特征，再用 K-means 聚类，得到一小批查询 token。每个 token 最后解码成 32 个高斯。

再看修正。当前视角能看见的旧高斯，把它们对应的记忆 token 取出来，和新的查询 token 一起送进同一个 transformer，输出对旧高斯的残差更新。看不见的高斯保持不动。

为了让记忆能直接渲染成潜空间特征，L3G-Mem 还有一个分支，从当前视频的 VAE 特征里取信息。每个新高斯除了几何和颜色，还带一个 16 维的 VAE 特征，渲染方式和颜色完全一样。

再看生成端 L3G-Gen。它把记忆渲染到目标相机下，得到对齐好的 VAE 特征和一张不透明度遮罩，在通道维度上和带噪声的视频特征拼在一起，再加上按相机位置检索出来的最多三个历史潜空间特征作为参考，然后生成下一段视频。

生成器的底座是 NVIDIA 的 Cosmos-Predict2.5 2B 模型，用 LoRA 微调。这个老师模型每次用 35 步去噪生成 81 帧，太慢。所以作者把它蒸馏成一个少步的学生模型，每次只用 4 步去噪，生成 3 个潜空间帧，这个版本叫 L3G-World Fast。

蒸馏用的是 on-policy 的方式，学生在自己生成的轨迹上训练，再和冻结的老师比较分布，作者说这样能减少训练和推理时的不一致。

### 实验和效果

实验设置。生成器在 DL3DV 和 RealEstate10K 两个数据集上训练，记忆模块只用了 DL3DV，评测在这两个数据集的测试集上做。作者专门构造了 481 帧的回环轨迹，相机先往外走，再沿原路倒回来，比较去程和回程同一个位置的两帧画面，看场景有没有变，这就是自洽性指标。

对比的方法有八个。点云记忆的 Lyra 2.0、GEN3C、Spatia、SPMem 和 3DScenePrompt，3D 高斯记忆的 NeoVerse，还有靠时间上下文的 Yume 1.5 和 Matrix-Game 3.0。

先看效率，在表 2。DL3DV 上，L3G-World 的记忆里只有 3.3 万个高斯，占 11.88 MiB。同样用 3D 高斯的 NeoVerse，有 876.6 万个，占 501.57 MiB。

直接渲染 VAE 特征的速度，L3G-World 是每秒 1086.58 帧，NeoVerse 是 3.11 帧。论文报告，在两个数据集上，和 NeoVerse 比，这一项快了 349 到 359 倍。

端到端的速度在表 1。在一张 H100 上生成 400 帧，L3G-World 每秒 9.02 帧，峰值显存 7.4 GiB，作者说这是配合少步蒸馏得到的。表里其他方法最快的是 NeoVerse，每秒 1.99 帧，不过各方法的分辨率并不相同。

再看自洽性。回环之后同一位置的 PSNR，越高说明前后越一致。DL3DV 上 L3G-World 是 16.00，最好的对手 Spatia 是 13.96。RealEstate10K 上是 18.36，最好的对手 Matrix-Game 3.0 是 17.95。

生成质量用 FID 衡量，越低越好。DL3DV 上 L3G-World 是 40.57，最好的对手 GEN3C 是 48.65。RealEstate10K 上是 36.09，对手 Lyra 2.0 是 37.36。

但它不是全面领先。论文自己写了，在 RealEstate10K 上，其他方法的相机位姿误差和 3D 一致性误差更低。比如平移误差，Lyra 2.0 是 0.091，L3G-World 是 0.216。

快速版也有代价。RealEstate10K 上，L3G-World Fast 的回环 PSNR 是 16.19，低于 Matrix-Game 3.0、Lyra 2.0、Spatia 和 GEN3C 这四个对手。

这张图是定性对比，所有方法从同一张图出发，走出去再回到起点。作者称，基线会出现漂移、模糊或者渲染瑕疵，L3G-World 回到起点时结构和外观都保住了。

### 和以前方法的对比

消融实验先看记忆模块，在表 3。去掉自适应生成，改成对所有特征做聚类，高斯数量从 4.1 万涨到 7.5 万，大约 1.8 倍，新视角的 PSNR 反而从 16.52 降到 16.26。去掉修正，PSNR 掉到 15.52。

如果不存 VAE 特征，改成先渲染 RGB 再用 VAE 编码，VAE 渲染速度从每秒 943.6 帧掉到 2.97 帧，而且特征误差从 0.177 涨到 0.570。

再看整个系统，在表 4。去掉记忆修正，让高斯生成之后就固定不动，回环 PSNR 从 15.11 降到 14.82，旋转误差从 5.22 度涨到 7.85 度。

不过同一张表里，去掉 VAE 特征、改成 RGB 再编码的版本，回环 PSNR 是 15.41，SSIM 是 0.480，反而比完整版高。完整版赢在 FID 这些生成质量指标上，也省掉了编码的开销。

我的判断是，这篇的核心贡献，是把 3D 记忆从不断往上堆的缓冲区，变成可以改写的场景表示，并且直接用生成器的潜空间存信息，记忆这一侧的速度提升，主要来自这两点，端到端能到实时，还要靠少步蒸馏。

我的判断是，也要看到评测的范围比较窄。训练和测试都只用了 DL3DV 和 RealEstate10K 这两个数据集，而且有几个基线要由作者改造，才能放进单张图片起步的设置里，作者在附录里说明了这些改动。

### 局限

作者自己列了三条局限。第一，这套记忆主要为静态场景设计，不显式建模独立运动的物体。

第二，记忆虽然跟着探索范围涨，而不是跟着视频长度涨，但如果探索的范围特别大，它还是会变大。

第三，修正机制可以逐步改正错误的高斯，但长时间自回归生成里引入的错误，仍然可能传到后续的记忆更新里。

### 未来方向

作者提到的方向，一是把动态内容从静态几何里分离出来，支持更一般的交互环境，二是用自适应剪枝或者分层记忆，进一步控制记忆的规模。

作者的结论是，紧凑的、存在潜空间里的 3D 记忆，可以作为可扩展的交互式世界模型的实用基础。

我的判断是，每秒 9 帧、480 乘 832 的分辨率，作为实时演示已经可以，但要真正用在游戏或者机器人仿真里，帧率、画质和动态物体都还要往前走一步。

## English walkthrough

### Intro

This is Daily Frontier Papers. Today's paper comes from KAIST in South Korea. It's called L3G-World, and the idea is in the name: a latent 3D Gaussian memory that lets a model generate a world you can keep exploring, in real time.

Here's the setup. You give the model one image and a camera path. It generates video as the camera moves, and if you walk far away and then come back, you should see the same place you left, all at interactive speed.

### Problem

Some background. Interactive video world models generate the next frames from a user's actions, like key presses or camera motion. People use them for games, real-world simulation, and simulation for embodied agents.

The hard part is getting two things at once. First, after a long exploration, coming back to a spot should show the same scene. That's loop-closure consistency. Second, generation has to keep up in real time.

### Prior work

There are two standard approaches. The first is temporal context: when generating a new chunk, the model looks back at past frames, or at the KV cache inside the diffusion model's attention layers.

The catch is that this history grows with the length of the video, and so do memory and compute. In the paper's Table 1, WorldKV runs out of memory on a four-hundred-frame video, and Yume 1.5 peaks at sixty-six point seven gibibytes and runs at one point four two frames per second.

The second approach is an explicit 3D memory: rebuild what's been generated as a point cloud or as 3D Gaussians. The feed-forward versions are fast, but they predict 3D points for every pixel, so the same region gets stacked up again and again. The memory gets redundant, rendering slows down, and since stored points aren't updated, geometry that was wrong early on can stick around.

Optimization-based versions keep a compact memory, but they have to run iterative optimization, which is slow. ArtiFixer in Table 1 manages zero point one zero frames per second.

There's one more cost people tend to miss. Modern video generators work in a VAE latent space, a compressed feature space. Older 3D memories can only render ordinary RGB images, which then have to be run through the VAE encoder before the generator can use them. That step alone rules out real time.

### Key idea

L3G-World builds its memory around two decisions. First, the memory is updated selectively. It adds new Gaussians only where it sees something new, and corrects the Gaussians it already has. So the memory grows with the size of the scene, not the length of the video.

Second, every Gaussian stores a VAE latent feature alongside its color. That way the memory renders straight into the generator's latent space, with no VAE encoding step.

A quick word on 3D Gaussians. Gaussian splatting represents a scene as a large set of semi-transparent blobs, each with a position, a shape, an opacity and a color, and it can render an image from any viewpoint very quickly.

### Method

The system has two modules that take turns. L3G-Mem reads and writes the memory. L3G-Gen generates the next chunk of video. Each new chunk goes back to L3G-Mem to update the memory, and the updated memory guides the next chunk, round and round.

So how does L3G-Mem decide where to add Gaussians? It renders the current memory from the current camera views, getting a color image and an opacity map. Low opacity means the memory doesn't cover that spot yet. High color error means it covers it badly. Both kinds of region get marked in what the paper calls a spawn mask.

Inside the marked region, a geometry foundation model, Depth Anything 3, extracts features, and K-means clustering turns them into a small set of query tokens. Each token is eventually decoded into thirty-two Gaussians.

Then there's correction. The old Gaussians that are visible from the current views have their memory tokens pulled out and sent through the same transformer as the new queries, which outputs residual updates for them. Gaussians that aren't visible stay as they are.

To make the memory renderable in latent space, L3G-Mem has one more branch that reads the current video's VAE features. Each new Gaussian then carries a sixteen-dimensional VAE feature, rendered exactly the same way as color.

Now the generator, L3G-Gen. It renders the memory from the target cameras, getting aligned VAE features and an opacity mask, and stacks them channel-wise with the noisy video latents. It also gets up to three earlier latents, retrieved by camera-pose proximity, as references. Then it generates the next chunk.

The generator is built on NVIDIA's Cosmos-Predict2.5 2B, fine-tuned with LoRA. This teacher model uses thirty-five denoising steps to make each eighty-one-frame clip, which is too slow. So the authors distill it into a few-step student that uses four denoising steps and produces three latent frames at a time. That version is called L3G-World Fast.

The distillation is on-policy: the student trains on its own generated rollouts, which are compared against the frozen teacher's distribution. The authors say this reduces the mismatch between training and inference.

### Results

The setup. The generator is trained on the DL3DV and RealEstate10K datasets, the memory module on DL3DV only, and evaluation uses the test splits of both. The authors build four-hundred-eighty-one-frame loop-closure paths: the camera heads out, then retraces the same path back. Comparing the outbound and return frames at the same camera pose tells you whether the scene stayed the same. That's the self-consistency metric.

There are eight baselines. Point-cloud memories: Lyra 2.0, GEN3C, Spatia, SPMem and 3DScenePrompt. A 3D Gaussian memory: NeoVerse. And two temporal-context models: Yume 1.5 and Matrix-Game 3.0.

Efficiency first, from Table 2. On DL3DV, L3G-World's memory holds thirty-three thousand Gaussians in eleven point eight eight mebibytes. NeoVerse, which also uses 3D Gaussians, holds about eight point seven seven million, in about five hundred mebibytes.

Rendering VAE features directly, L3G-World runs at about one thousand eighty-seven frames per second, against three point one one for NeoVerse. Across the two datasets, the paper reports that as three hundred forty-nine to three hundred fifty-nine times faster.

End-to-end speed is in Table 1. Generating four hundred frames on one H100, L3G-World runs at nine point zero two frames per second with a peak of seven point four gibibytes, and the authors say that's with the few-step distillation. The fastest other method in the table is NeoVerse at one point nine nine frames per second, though the methods run at different resolutions.

Now self-consistency. PSNR between matching frames, where higher means more consistent. On DL3DV, L3G-World scores sixteen point zero zero, against thirteen point nine six for the best baseline, Spatia. On RealEstate10K it's eighteen point three six, against seventeen point nine five for the best baseline, Matrix-Game 3.0.

Generation quality is measured with FID, where lower is better. On DL3DV, L3G-World gets forty point five seven, against forty-eight point six five for GEN3C, the best baseline. On RealEstate10K it's thirty-six point zero nine, against thirty-seven point three six for Lyra 2.0.

But it doesn't win everything. The paper notes that on RealEstate10K, other methods have lower camera-pose error and better 3D consistency scores. Translation error, for example, is zero point zero nine one for Lyra 2.0 and zero point two one six for L3G-World.

The fast version also pays a price. On RealEstate10K, L3G-World Fast has a loop-closure PSNR of sixteen point one nine, below four baselines: Matrix-Game 3.0, Lyra 2.0, Spatia and GEN3C.

This figure is the qualitative comparison. Every method starts from the same image, walks out, and comes back. The authors say the baselines show drift, blur or rendering artifacts, while L3G-World returns with structure and appearance intact.

### Comparison

The ablations start with the memory module, in Table 3. Drop adaptive spawning and cluster all features instead, and the Gaussian count goes from forty-one thousand to seventy-five thousand, about one point eight times, while novel-view PSNR falls from sixteen point five two to sixteen point two six. Drop refinement, and PSNR falls to fifteen point five two.

Skip storing VAE features, rendering RGB and encoding it instead, and VAE rendering drops from nine hundred forty-three point six frames per second to two point nine seven. The latent error also rises, from zero point one seven seven to zero point five seven zero.

Then the full system, in Table 4. Turn off memory refinement, so Gaussians are fixed once created, and loop-closure PSNR drops from fifteen point one one to fourteen point eight two, while rotation error rises from five point two two degrees to seven point eight five.

But in the same table, the variant that renders RGB and re-encodes it actually has higher loop-closure PSNR, fifteen point four one, and higher SSIM, zero point four eight zero, than the full model. The full model wins on generation quality metrics like FID, and it skips the encoding cost.

My read is that the core contribution is turning 3D memory from a buffer that only grows into a scene representation that can be revised, and having it store information directly in the generator's latent space. Those two choices explain most of the memory-side speedup, and reaching real time end to end also takes the few-step distillation.

My read is also that the evaluation is narrow. Training and testing use only two datasets, DL3DV and RealEstate10K, and several baselines had to be adapted by the authors to fit the single-image setup. The appendix documents those changes.

### Limitations

The authors list three limitations. First, the memory is built mainly for static scenes and doesn't explicitly model objects that move on their own.

Second, the memory grows with the area explored, not the length of the video, but over a very large exploration it can still get big.

Third, refinement can gradually fix wrong Gaussians, but errors introduced during long autoregressive generation can still carry into later memory updates.

### Future work

The directions the authors name are separating dynamic content from static geometry, for more general interactive environments, and using adaptive pruning or hierarchical memory to keep the memory size in check.

Their conclusion is that compact 3D memories stored in latent space can be a practical foundation for scalable interactive world models.

My read is that nine frames per second at four eighty by eight thirty-two is fine for a real-time demo, but frame rate, image quality and moving objects all need another step before this is used in games or robot simulation.
