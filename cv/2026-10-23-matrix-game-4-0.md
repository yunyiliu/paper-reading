## 中文讲解

### 开场

这里是每日前沿文章。今天讲一篇 Skywork AI 联合香港中文大学等高校和研究机构的技术报告，叫 Matrix-Game 4.0，讲的是怎么用视频模型，做出能实时玩的游戏世界。

它的思路，第一页就写得很直白，代码管规则，视频模型负责画出每一帧。在一张 RTX 5090 上，从按键到画面的延迟是 112 毫秒。

### 问题

先说背景。像 Genie 系列这样的交互式世界模型，已经能根据你的操作，一帧一帧生成可以探索的画面。

但作者认为，如果目标不只是到处逛逛，而是一个能长时间玩、有规则的游戏，只靠视频生成来维持世界状态，会遇到四个问题。

第一，没有外部纠正，世界状态只藏在生成的像素和上下文里，视野外的东西没人记着。第二，误差会累积，小错一步步放大，画面越来越不一致。

第三，记忆靠堆历史帧，玩得越久，成本越高。第四，玩法很有限，基本就是走来走去，很难支持可执行的规则和明确的目标。

作者还有一个更根本的看法。扩散模型学到的主要是统计相关性，画面逼真，不代表懂因果和物理，它本身更像一个渲染器。

### 以前的方法

以前的方法大致有两类。第一类是 Genie、GameNGen、Oasis，还有 Matrix-Game 自己的 2.0 和 3.0，在这些模型里，神经网络既要负责世界怎么变化，也要负责画面长什么样。

第二类是最近出现的一条路线，把状态和规则交给可执行的代码，视频模型只管渲染，比如 Code World Model、StreamRender-H3、AgentGarten 和 Magpie。

问题在于延迟和硬件。按论文表 3 的整理，它们的端到端延迟从大约半秒到十秒，用的是 H100、H200 这类数据中心显卡，StreamRender-H3 还要 8 张 GB200。

### 核心想法

Matrix-Game 4.0 的核心想法，就是把游戏怎么运行，和游戏长什么样，彻底分开。代码定义规则，引擎维护状态，视频模型只负责画面。

论文这张路线图里有三个角色。游戏引擎是裁判，多模态的 coding agent 是编剧兼翻译，视频生成模型是画师。

运行起来是一个循环。玩家输入操作，引擎更新世界状态，输出结构渲染和控制信号，视频模型实时渲染，画面再返回给玩家。

这样一来，游戏就不再依赖视频模型的记忆，来维持世界状态和执行规则。

### 方法

先看引擎。它不画精细的画面，只用简化的几何体表示道路、建筑和角色。血量、背包、重力、碰撞、任务进度，都在代码里明确维护，物体走出视野，它的状态也还在。

引擎输出的画面叫 low-poly proxy，也就是低多边形的代理画面。天空是黑的，地面是灰色棋盘格，建筑变成纯色方块，树是一个圆柱加一个球，没有纹理，没有阴影。

再看 coding agent，它往两个方向工作。往下，是把引擎里的场景翻译成文字，比如一个简单的方块，可以描述成一座被海风侵蚀的旧茅草屋，有一扇深红色的木门。

往上，是把玩家的想法写成游戏代码。比如玩家说，让怪物从四面八方涌过来，agent 还要定义它们在哪刷新，怎么攻击，胜负怎么判定。

分工很清楚。玩家打中一个油桶，有没有打中，会不会爆炸，是引擎判定的，agent 只负责描述爆炸之后的画面。

交给视频模型的文字，叫动态 caption。场景里每个物体有一个 ID，对应一段语义描述，系统从引擎读出当前看得见的物体和它们的状态，填进模板，生成和当前画面对应的描述。

这张图是一段城市驾驶的例子。车往前开，停着的车离开了描述，行人从站着变成走近。这一步是按规则模板生成的，不用视觉语言模型。

两者是互补的。proxy 给结构，也就是位置、布局和运动，caption 给语义，也就是画面里有什么，各自是什么状态。

训练数据从哪来。作者在虚幻引擎 5 里，把同一段画面，用同一个相机录两遍，一遍是低多边形的结构渲染，一遍是高保真画面，两者逐像素对齐。

一共四个场景，中世纪城堡、古埃及沙漠、峡谷空战和城市驾驶，训练片段一共 114334 个，合计 1712 小时。

渲染模型从 Wan2.2 的 5B 模型出发，改成一个视频到视频的模型。条件有四路，proxy 管画什么、画在哪，caption 补细节，空间记忆帧让玩家回到老地方时场景不变，第一帧负责和屏幕上已有的画面接上。

网络结构在这张图里。DiT 有 5B 参数，30 个 block，每次生成一个 chunk，也就是一个潜空间帧，对应四帧视频。注意力的 KV cache 里存着 3 帧空间记忆、参考帧，和最近 20 个 chunk。

训练分两大步。先在配对数据上做监督微调，每个游戏单独训练一个模型。然后参照 Causal Forcing++ 的做法，把双向模型蒸馏成因果的自回归生成器，每个 chunk 只去噪一到两步。

蒸馏本身分三个阶段，先把模型改成因果的，再做一致性蒸馏压到四步，最后用分布匹配蒸馏，也就是 DMD，压到两步。

光有蒸馏还不够。作者又做了一整套推理优化，比如 CUDA Graph、FP8 权重、融合 kernel、环形 KV cache，还把解码器换成了轻量的 TAEHV。

效果在表 2 里逐行叠加。最初的版本，每秒只有 4.5 帧，延迟 1110 毫秒。全部优化加上之后，是每秒 83.4 帧，延迟 112 毫秒，速度大约是原来的 19 倍。

### 实验和效果

先看速度。在一张 RTX 5090 上，480p 分辨率，一步去噪大约每秒 83 帧，两步大约 57 帧，峰值显存都是大约 18.2 GiB。一步去噪时，生成一个四帧的 chunk 要 48 毫秒。

16 GiB 显存的消费级显卡也能跑。在固定 prompt 的情况下，RTX 5080 大约每秒 67 帧，RTX 5070 Ti 大约 58 帧。

再看画面。作者在留出的录制场次上测试，这些场次没有任何片段进过训练。从真实的第一帧开始，用两步去噪的蒸馏模型，自回归连续生成 961 帧，按每秒 24 帧算，就是 40 秒。

这张图是三个游戏各取四个时刻，上面是引擎的 proxy，下面是生成的画面。按论文的描述，建筑、树和车都出现在 proxy 指定的位置，纯色方块变成了石墙、茅草屋和城市街景，40 秒里角色的外观保持一致。

最后是玩法。玩家可以用自然语言让 coding agent 改游戏。射击游戏加上了血量、有耐久上限的护盾和射速更高的霰弹枪，驾驶游戏加上了带检查点和碰撞罚时的计时赛，还能改成追击模式。所有规则都在引擎里执行，视频模型只负责把引擎的输出画出来。

### 和以前方法的对比

对比在表 3，和四个同样由代码驱动视频生成的系统比。Matrix-Game 4.0 的端到端延迟是 112 毫秒，其次是 StreamRender-H3，大约 517 毫秒，最慢的 Code World Model 流式版大约 10.2 秒。

作者称，它的延迟大约是第二名的五分之一，而且在这几个系统里，是唯一能在单张消费级显卡上运行的，代码和权重在发布时开源。

不过这张表的条件并不统一。分辨率不同，Matrix-Game 是 864 乘 480，Code World Model 和 StreamRender-H3 是 1344 乘 768。延迟的算法也不同，按论文的说明，分块生成的系统算的是两个 chunk 的生成时间，Matrix-Game 测的是从按键到第一帧反映这个按键的画面。

我的判断是，这个对比能说明它在部署门槛上明显领先，但不能直接说明同等条件下它更快，更不能说明画质更好，因为论文没有在同一分辨率下对比，也没有比画面质量。

我的判断是，和 Matrix-Game 自己的 2.0、3.0 比，这一代把世界规律交还给了代码，换来规则可靠、玩法能随时改，代价是每个世界都要有引擎、代码和配对的训练数据。

### 局限

论文没有单独的局限章节，下面几条，是从论文的实验设置里能直接看出来的。

第一，画面质量只有定性展示，论文没有给出量化的画质或一致性指标，也没有和别的渲染器比画面。

第二，每个游戏单独训练一个渲染模型，训练数据是在虚幻引擎里专门录制的配对视频，论文没有展示同一个模型跨游戏使用。

第三，实时速度是在 480p 下测的，评测的连续生成也只有 40 秒，更高分辨率和更长时间游玩的表现，论文没有报告。

第四，coding agent 改玩法这部分，论文展示的是三种模式的案例，没有统计 agent 改代码的成功率。

### 未来方向

作者说，近期的重点是降低推理成本和硬件要求，目标是在 Steam 上发布一个技术预览版。

更长远的方向，包括提升画质和分辨率，多人游戏时让不同玩家看到一致的画面，以及扩展到更多游戏类型。

我的判断是，这篇最有价值的地方，不是某一个新模块，而是一种在工程上能落地的分工，代码管规则，模型管画面，并且在一张游戏显卡上跑到了可以玩的延迟。

我的判断是，接下来真正要回答的是画质和泛化。如果做不到一个渲染模型通用于各种游戏，每款游戏都得录数据、训模型，门槛就还卡在数据这一头。

## English walkthrough

### Intro

This is Daily Frontier Papers. Today's paper is a technical report from Skywork AI and several universities and labs, including the Chinese University of Hong Kong. It's called Matrix-Game 4.0, and it's about turning video models into game worlds you can actually play in real time.

The first page sums up the idea: code keeps the rules, and the video model draws every frame. On a single RTX 5090, the delay from pressing a key to seeing the result is one hundred and twelve milliseconds.

### Problem

Some background. Interactive world models, like the Genie series, can already generate explorable scenes on the fly, frame by frame, in response to your inputs.

But the authors argue that once the goal shifts from wandering around to a long-running game with real rules, relying on video generation to hold the world state runs into four problems.

First, there's no external correction. The state of the world lives only in the generated pixels and the model's context, and nothing keeps track of what's outside the field of view. Second, errors accumulate. Small mistakes compound through autoregressive generation, and consistency degrades.

Third, memory is just a growing pile of past frames, so the longer you play, the more it costs. Fourth, gameplay is thin. It's mostly navigation, with little support for executable rules or goals you can pursue.

They also make a more fundamental point. Diffusion models mostly learn statistical correlations. A realistic picture doesn't mean the model understands cause and effect, and diffusion behaves more like a renderer.

### Prior work

Earlier work falls into two camps. The first includes Genie, GameNGen, Oasis, and Matrix-Game's own versions two and three. In these models, the network carries both how the world changes and what it looks like.

The second is a more recent line of work that hands state and rules to executable code and leaves only rendering to a video model. Examples are Code World Model, StreamRender-H3, AgentGarten and Magpie.

The catch is latency and hardware. In the paper's Table 3, their end-to-end latencies range from about half a second to about ten seconds, on data-center GPUs like the H100 and H200, and StreamRender-H3 uses eight GB200s.

### Key idea

The key idea of Matrix-Game 4.0 is a clean split between how the game runs and how it looks. Code defines the rules, the engine keeps the state, and the video model only produces the visuals.

The roadmap figure casts three roles. The game engine is the referee, a multimodal coding agent is the scriptwriter and translator, and the video generation model is the painter.

At runtime it's a loop. The player acts, the engine updates the world state and sends out a structural render and control signals, the video model renders frames in real time, and those frames go back to the player.

So the game no longer depends on the video model's memory to keep the world state or to enforce the rules.

### Method

Start with the engine. It doesn't draw detailed graphics. It represents roads, buildings and characters with simplified geometry. Health, inventory, gravity, collisions and quest progress are all tracked explicitly in code, and an object that leaves the screen keeps its state.

What the engine outputs is called a low-poly proxy. The sky is black, the ground is a gray checkerboard, buildings become flat-colored boxes, a tree is a cylinder with a sphere on top, and there are no textures or shadows.

Next, the coding agent, which works in two directions. Downstream, it translates the engine's scenes into text. A plain box can be described as an old thatched cottage weathered by sea winds, with a dark red wooden door.

Upstream, it turns a player's ideas into game code. If a player says, make monsters swarm in from all directions, the agent also has to define where they spawn, how they attack, and what decides victory or defeat.

The division of labor is strict. If a player shoots an oil barrel, the engine decides whether the shot hits and whether it explodes. The agent only describes what the explosion looks like.

The text that goes to the video model is a dynamic caption. Every object in the scene has an ID linked to a description, and the system reads the visible objects and their current states from the engine and fills them into a template that matches the current frame.

This figure shows a city driving clip. As the car moves, parked cars drop out of the description, and pedestrians change from standing to approaching. It's all produced by a rule-based template, with no vision-language model involved.

The two signals complement each other. The proxy supplies structure, meaning position, layout and motion. The caption supplies semantics, meaning which objects are in view and what state each one is in.

Where does the training data come from? In Unreal Engine 5, the authors capture each clip twice from the same camera, once as a low-poly structure render and once as the full high-fidelity frame, aligned pixel by pixel.

There are four scenes: a medieval castle, an ancient Egypt desert, a desert canyon air combat, and a city for driving. That's one hundred and fourteen thousand, three hundred and thirty-four training clips, and one thousand seven hundred and twelve hours in total.

The renderer starts from the five-billion-parameter Wan two point two, turned into a video-to-video model with four conditions. The proxy says what to draw and where, the caption fills in details, spatial-memory frames keep a place consistent when you return, and the first frame connects to what's already on screen.

The architecture is in this figure. The DiT has five billion parameters and thirty blocks, and it generates one chunk at a time, which is one latent frame, or four video frames. The attention cache holds three spatial-memory frames, the reference frames, and the latest twenty chunks.

Training happens in two big steps. First, supervised fine-tuning on the paired data, with a separate model for each game. Then, following Causal Forcing plus plus, they distill the bidirectional model into a causal, autoregressive generator that denoises each chunk in just one or two steps.

The distillation itself has three stages. First the model is made causal. Then consistency distillation brings each chunk down to four steps. Finally, distribution matching distillation, or DMD, brings it down to two.

Distillation alone isn't enough. The authors add a stack of inference optimizations, such as CUDA Graphs, FP8 weights, fused kernels, a ring-buffer KV cache, and the lightweight TAEHV decoder.

Table 2 stacks these up row by row. The starting point runs at four point five frames per second, with one thousand one hundred and ten milliseconds of latency. With everything on, it's eighty-three point four frames per second and one hundred and twelve milliseconds. That's nineteen times faster.

### Results

Speed first. On one RTX 5090 at four-eighty p, the model generates about eighty-three frames per second with one denoising step and about fifty-seven with two, with peak memory around eighteen point two gigabytes either way. With one step, a four-frame chunk takes forty-eight milliseconds.

It also runs on sixteen-gigabyte consumer cards. With fixed prompts, it reaches about sixty-seven frames per second on an RTX 5080 and about fifty-eight on an RTX 5070 Ti.

Then visuals. The authors test on held-out capture sessions that contributed no training clips. Starting from the real first frame, the two-step distilled model generates nine hundred and sixty-one frames autoregressively, which is forty seconds at twenty-four frames per second.

This figure shows three games at four moments each, engine proxy on top, generated frame below. According to the paper, buildings, trees and vehicles appear where the proxy puts them, flat blocks become stone walls, thatched houses and city facades, and the character keeps the same look across the forty seconds.

Finally, gameplay. Players can ask the coding agent in plain language to change the game. The shooter gets health, a shield with limited durability, and a faster-firing shotgun. The driving game gets a time trial with checkpoints and collision penalties, and it can be turned into a pursuit. Every rule runs in the engine. The video model just draws whatever the engine outputs.

### Comparison

The comparison is Table 3, against four other systems that render code-driven worlds with video models. Matrix-Game 4.0's end-to-end latency is one hundred and twelve milliseconds. Next is StreamRender-H3 at about five hundred and seventeen milliseconds, and the slowest, the streaming Code World Model, takes about ten point two seconds.

The authors say that's about a fifth of the next system's latency, that it's the only one in the table running on a single consumer GPU, and that code and weights were released at launch.

But the conditions in that table aren't uniform. Resolutions differ: Matrix-Game runs at eight sixty-four by four eighty, while Code World Model and StreamRender-H3 run at thirteen forty-four by seven sixty-eight. Latency is also counted differently. According to the paper, for chunk-based systems it's two chunk generation times, while for Matrix-Game it's measured from a key press to the first frame that reflects it.

My read is that this table shows a clear lead in how easy it is to deploy, but it doesn't show the system is faster under equal conditions, and it says nothing about image quality, because the paper doesn't compare at a matched resolution or compare visuals at all.

My read is that compared with Matrix-Game two and three, this generation hands the world's rules back to code. You get reliable rules and gameplay you can change on the fly, and the price is that every world needs an engine, game code, and paired training data.

### Limitations

The paper has no dedicated limitations section, so these points come straight from its experimental setup.

First, image quality is only shown qualitatively. There are no quantitative quality or consistency metrics, and no visual comparison with other renderers.

Second, each game gets its own rendering model, trained on paired videos captured specifically in Unreal Engine, and the paper doesn't show one model working across games.

Third, the real-time numbers are at four-eighty p, and the evaluated rollouts last forty seconds. Higher resolutions and longer play sessions aren't reported.

Fourth, for the coding agent, the paper shows case studies of three game modes, but no success rate for the agent's code edits.

### Future work

In the near term, the authors say they'll focus on lowering inference cost and hardware requirements, with the goal of releasing a technical preview on Steam.

Further out, they list better image quality and resolution, multiplayer rendering with consistent views across players, and more game genres.

My read is that the most valuable thing here isn't any single new module. It's a division of labor that actually works as engineering, with code running the rules and a model drawing the pixels, at playable latency on one gaming GPU.

My read is that the next real questions are image quality and generalization. If one renderer can't serve many games, every new game means capturing data and training a model, and the barrier just moves to the data side.
