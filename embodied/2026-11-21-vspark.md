## 中文讲解

### 开场

这里是每日前沿文章。今天讲一篇 KAIST 和牛津大学 VGG 组的论文，名字叫 VSpark，讲的是怎么让自回归的 VLA 模型，也就是视觉语言动作模型，更快地输出机器人动作。

先说结论。论文报告，在四个 VLA 模型上，它把动作解码速度提高到原来的 1.28 倍到 2.10 倍，而且按设计，输出和原模型自己一个一个生成的结果一致，这叫无损。

### 问题

先说背景。VLA 看摄像头画面，听语言指令，输出机器人动作。自回归 VLA 把连续的动作变成离散的 token，像大模型写字一样，一个 token 一个 token 地生成。

代价是慢。每生成一个动作 token，都要把一个大模型完整跑一遍，这限制了机器人的控制频率。

后来有了压缩式的动作分词器，比如 FAST，把一整段未来动作压成更短的 token 序列。token 变少了，但剩下的还是得一个一个生成，这依然是主要瓶颈。

### 以前的方法

大模型加速里有个成熟办法，叫推测解码，speculative decoding。用一个很小的草稿模型，一次猜好几个 token，再让大模型在一次并行计算里检查，只接受和自己预测一致的那一段。因为只收一致的，结果和大模型自己生成的一样。

问题是，用在机器人上，效果打了折扣。很多不同的 token，其实对应几乎一样的动作，草稿已经猜得很接近了，只要 token 不一样，照样被拒。

已有的 VLA 加速方法，比如 Spec-VLA 和 KERV，选择放宽检查，草稿只要足够接近就接受。但它们依赖一种分词方式，每个动作维度单独分格子，相邻的格子就代表相近的数值。

换成 FAST 这种压缩分词器，就行不通了。一个 token 混着好几个维度、好几个时间步的信息，要拿到完整的 token 序列，才能还原出动作，没法单独判断一个 token 近不近。

那用 token 向量之间的距离来判断，行不行。作者测了，按向量距离排序和按真实动作距离排序，大约百分之 31 的情况对不上。在 π0-FAST 上用向量距离放宽检查，速度从 1.60 倍提到 1.90 倍，任务成功率却从百分之 91.7 掉到 71.4。

### 核心想法

VSpark 的思路正好反过来。检查一点都不放宽，保持严格一致，而是把动作相似这件事，用在草稿这一侧。

逻辑是这样的。既然很多 token 对应差不多的动作，草稿就不该只学 token 标签。既然被拒的 token 往往差不多是对的，大模型在它后面算出的预测，就还有用。

这张图左边是速度对比，右边是一个例子，被拒那条分支后面的预测，在修正之后往往依然成立。以前的方法直接扔掉，VSpark 把它们捡回来再用。

### 方法

具体来说，VSpark 建立在一个叫 DSpark 的并行草稿模型上。它一次就把后面几个位置的 token 全部猜出来，再用一个很轻的小模块，按前一个 token 做修正。

整体结构看这张图。在这个基础上，作者加了三样东西，两样改草稿的训练，一样改每轮检查哪些候选，大模型、分词器和检查规则都不动。

第一样，带噪声的 rollout。草稿模型通常只在示范数据走过的状态上训练。作者在仿真里让大模型自己控制机器人，同时给执行的动作加一点噪声，让机器人走到示范轨迹附近的更多状态。

噪声加多大，不是拍脑袋定的。作者先比较草稿和大模型解码出的动作差多少，用这个误差的统计量，来定噪声的大小和方向。而且只扰动执行的动作，存下来的监督信号，还是大模型在扰动之前给出的干净 token 和特征。

第二样，特征对齐。只用 token 标签训练的话，一个解码出来几乎一样动作的 token，和一个完全不对的 token，算作一样的错。

所以作者把大模型好几层的隐藏特征拿出来，既喂给草稿当输入，又让草稿去回归大模型输出层之前的那个特征。这给了草稿一个连续的信号，而不只是对或错。

第三样，续写复用，continuation reuse，这是推理阶段的。大模型在检查的时候，其实顺带算出了每个被拒 token 后面它会接什么。标准做法把这些全扔了。

举个例子，草稿猜 a，大模型要的是 b，那就接上 b。但同一次检查里，大模型也算出了 a 后面应该接 c。VSpark 把从 c 开始的这串预测留下，下一轮建草稿树的时候，在 b 后面把它们优先提出来。

这些候选在下一轮，还要被大模型在修正后的前缀下重新检查，所以依然无损。大模型不用多算，也不用重新训练任何模型。

### 实验和效果

实验设置。加速对象是四个公开的自回归 VLA，π0-FAST、StarVLA-FAST、ActionCodec 和 G0.5，覆盖了两类压缩分词器。对手是五种推测解码方法，包括 EAGLE-3 和 DSpark，大家加速同一个冻结的大模型，只有草稿不同。

评测用的是 LIBERO，它的两个分布偏移版本 LIBERO-Plus 和 LIBERO-Pro，还有换了一种机械臂的 SimplerEnv，全部在仿真里。草稿只有一层，所有实验在一张 RTX 4090 上跑。

主结果在表 1。在 LIBERO 上，VSpark 在每个模型、每组任务上，接受长度和加速比都是最高的。四个模型的平均加速，分别是 1.93 倍、1.61 倍、2.10 倍和 1.28 倍。

接受长度，就是每一轮检查平均能确定几个 token。和它的底座 DSpark 比，π0-FAST 上从 3.16 提到 3.94，ActionCodec 上从 3.69 提到 4.21。

不过，接受长度高，不一定就快。π0-FAST 上，EAGLE-3 接受的 token 数和 DSpark 几乎一样，速度却只有 1.26 倍对 1.60 倍，因为它的草稿要一个一个生成。

G0.5 最难加速。它用了线性注意力，不利于并行检查一棵树。三个对手方法在它上面比原模型还慢，最好的只有 1.09 倍，VSpark 是 1.28 倍。

换了机械臂的 SimplerEnv 上，VSpark 平均 1.95 倍，DSpark 是 1.75 倍。在有分布偏移的 LIBERO-Plus 和 LIBERO-Pro 上，所有方法的接受长度都下降了，但 VSpark 依然在八组任务、四个模型上全部最快，对 DSpark 的领先也保住了。

那时间省在哪。作者在 π0-FAST 上拆了时间，平均每个输出 token，原模型逐个生成要 14.47 毫秒，DSpark 是 8.93 毫秒，VSpark 是 7.44 毫秒，省下来最多的，是大模型检查的时间。

再说无损。论文报告，用 BF16 精度跑五个随机种子，π0-FAST 的平均成功率，原模型是百分之 92.71，VSpark 是 92.22，作者认为这点差别来自浮点运算的顺序。换成 FP32，在一个种子上，两者成功率完全相同，生成的动作 token 也完全一致。

### 和以前方法的对比

再和放宽检查的方法正面比。作者在 OpenVLA 上做了这组实验，因为它的分词方式允许放宽。严格检查的 VSpark，速度 1.27 倍，成功率百分之 76.8。放宽检查的 Spec-VLA，是 1.23 倍、百分之 75.0。KERV 在作者的复现里是 0.96 倍，比原模型还慢。

续写复用靠不靠谱，看表 5。一个 token 被拒之后，大模型原来在它后面的预测，在修正之后依然对的比例，π0-FAST 上是百分之 45.38，ActionCodec 上是百分之 54.88，比草稿自己的预测高了大约 18 个百分点。

消融在表 7。从 DSpark 出发逐个加组件，在 π0-FAST 上，特征对齐贡献最大，加速从 1.69 倍提到 1.90 倍。在 ActionCodec 上，续写复用贡献最大。三样全加上，分别是 1.93 倍和 2.10 倍。

还有一个反例。把续写复用搬到语言模型上，在 Qwen3-4B 和 Gemma-4-12B 上，加速没有提升，有的还略低。作者给的一个可能解释是，文字里前一个词变了，后面的话往往也得跟着变，动作序列不太是这样。

我的判断是，这篇最有价值的是它的取舍。它没有拿放宽检查去换速度，而是在严格无损的前提下，靠更聪明的草稿，在几个模型上拿到了接近 2 倍的加速。对机器人来说，不用调容忍度，按设计，加速也不会引入原模型之外的动作误差，这一点很实际。

我的判断是，也要看到它的边界。所有结果都在仿真里，测的是解码时间，不是真机上的控制频率。G0.5 只有 1.28 倍。而且它只适用于逐个生成 token 的 VLA，用扩散方式直接输出连续动作的模型，不在这个框架里。

### 局限

作者自己列了三条局限。第一，像 G0.5 这种混合注意力的结构，线性注意力层里的循环状态，让并行检查一棵树变得麻烦，即使接受长度提高了，加速也可能受限。

第二，续写复用只在被拒之后、后续预测不变的时候有用，这大约只占被拒情况的一半，而且随分词器不同而变化。

第三，带噪声的 rollout 需要仿真器。VSpark 对用真机数据训练的模型也有帮助，但没有仿真器的时候，怎么在真机上收集，还需要进一步研究。

### 未来方向

未来方向，作者提到两条，改进混合注意力上的并行检查，以及不靠仿真器收集带噪声的 rollout。

我的判断是，VLA 越做越大，推理速度会越来越像硬约束。把动作的结构用在草稿和候选上，而不是去改检查规则，这个思路值得后面的工作借鉴。

## English walkthrough

### Intro

This is Daily Frontier Papers. Today's paper comes from KAIST and the VGG group at Oxford. It's called VSpark, and it's about making autoregressive vision-language-action models, VLAs, produce robot actions faster.

The headline result: across four VLAs, the paper reports decoding speedups between one point two eight and two point one times. And by design, the output is exactly what the original model would have produced on its own. That's what lossless means here.

### Problem

Some background. A VLA looks at camera images, reads a language instruction, and outputs robot actions. An autoregressive VLA turns continuous actions into discrete tokens and generates them one token at a time, the way a language model writes text.

The cost is speed. Every action token needs a full forward pass of a large model, and that caps how fast the robot can be controlled.

Compressed action tokenizers like FAST helped. They squeeze a whole chunk of future actions into a shorter token sequence. But the tokens that remain are still generated one by one, and that's still the main bottleneck.

### Prior work

Language models have a well-known fix for this, called speculative decoding. A small draft model guesses several tokens ahead, and the big model checks them all in one parallel pass, keeping only the prefix that matches its own predictions. Since only matching tokens are kept, the output is the same as if the big model had generated it alone.

The catch is that this works less well for robots. Many different tokens encode almost the same motion, so a draft that's very close to the right action still gets rejected if its tokens differ.

Existing speculative decoders for VLAs, like Spec-VLA and KERV, relax the check instead, accepting a draft token if it's close enough. But they rely on tokenizers that bin each action dimension separately, where neighboring bins mean neighboring values.

That breaks with a compressed tokenizer like FAST. A single token mixes information from several dimensions and several timesteps, and you only get an action back once the whole sequence is decoded. So there's no direct way to tell whether one token is close.

What about measuring distance between token embeddings instead? The authors tested it: ranking tokens by embedding distance disagrees with ranking them by actual action distance for about thirty-one percent of pairs. And on pi-zero FAST, relaxing the check by embedding distance lifts the speedup from one point six to one point nine times, but drops task success from ninety-one point seven to seventy-one point four percent.

### Key idea

VSpark goes the other way. It doesn't relax the check at all. It keeps verification exact and uses the similarity between actions on the draft side.

The reasoning goes like this. If many tokens encode similar motions, the draft should learn from more than token labels. And if a rejected token is often nearly right, whatever the big model predicted after it is still useful.

In this figure, the left side shows the speedups, and the right side shows an example: predictions along a rejected branch often still hold after the correction. Standard decoding throws them away. VSpark recycles them.

### Method

Concretely, VSpark builds on a parallel draft model called DSpark. It guesses all the upcoming positions in one pass, then a very light module adjusts each guess based on the token before it.

Here's the overall picture. On top of DSpark, the authors add three things: two change how the draft is trained, and one changes which candidates get checked each round. The big model, the tokenizer and the verification rule are all left untouched.

First, rollouts with action noise. Draft models are usually trained only on states the demonstrations visit. Here the big model controls the robot in simulation while its executed actions are slightly perturbed, so the robot wanders into more states near the demonstrated paths.

The amount of noise isn't arbitrary. The authors measure how far the draft's decoded actions are from the big model's, and use the statistics of that error to set both the size and the direction of the noise. Only the executed action is perturbed, so the stored supervision is still the big model's clean tokens and features from before the perturbation.

Second, feature alignment. With token labels alone, a token that decodes to almost the same motion counts as just as wrong as a token that's completely off.

So the authors take hidden features from several layers of the big model, feed them to the draft as input, and also train the draft to regress the feature right before the big model's output head. That gives the draft a continuous signal, not just right or wrong.

Third, continuation reuse, which happens at inference time. When the big model checks a tree of guesses, it also computes what it would predict after every rejected token. Standard decoding throws all of that away.

Here's an example. The draft guesses a, the big model wants b, so b is appended. But in that same pass, the big model also predicted that c should follow a. VSpark keeps that sequence starting from c, and in the next round it promotes those tokens as candidates after b.

Those candidates are checked again by the big model under the corrected prefix, so decoding stays lossless. The big model does no extra work, and no model needs retraining for this step.

### Results

The setup. Four publicly released autoregressive VLAs are accelerated: pi-zero FAST, StarVLA-FAST, ActionCodec and G0.5, covering two families of compressed tokenizer. They're compared with five speculative decoding methods, including EAGLE-3 and DSpark, all accelerating the same frozen model, so only the draft differs.

Evaluation uses LIBERO, its two distribution-shift variants LIBERO-Plus and LIBERO-Pro, and SimplerEnv with a different robot arm, all in simulation. The drafts have a single layer, and everything runs on one RTX 4090 GPU.

Table 1 has the main results. On LIBERO, VSpark has the highest acceptance length and the highest speedup on every model and every task suite. Average speedups for the four models are one point nine three, one point six one, two point one, and one point two eight times.

Acceptance length is the average number of tokens locked in per checking round. Compared with DSpark, which it's built on, it goes from three point one six to three point nine four on pi-zero FAST, and from three point six nine to four point two one on ActionCodec.

There's a subtle point here. A longer acceptance length doesn't automatically mean faster. On pi-zero FAST, EAGLE-3 accepts about as many tokens as DSpark, but reaches only one point two six times against DSpark's one point six, because EAGLE-3's draft generates its guesses one at a time.

G0.5 is the hardest to speed up. It uses linear attention, which makes checking a tree in parallel awkward. Three of the baselines are actually slower than plain decoding on it, the best reaches one point zero nine times, and VSpark reaches one point two eight.

On SimplerEnv, with the different arm, VSpark averages one point nine five times, against one point seven five for DSpark. Under the distribution shifts of LIBERO-Plus and LIBERO-Pro, every method's acceptance length drops, but VSpark is still the fastest on all eight suites and all four models, and keeps its lead over DSpark.

So where does the time go? On pi-zero FAST, the authors break it down per output token: plain decoding takes fourteen point four seven milliseconds, DSpark eight point nine three, and VSpark seven point four four. Most of the saving comes from less time spent by the big model checking.

Now, losslessness. In BF16 over five random seeds, the paper reports average success on pi-zero FAST of ninety-two point seven one percent for plain decoding and ninety-two point two two for VSpark, and the authors attribute the gap to floating-point operation order. In FP32, on one seed, the success rates are identical and the generated action tokens match exactly.

### Comparison

Next, a head-to-head with methods that relax verification. The authors run this on OpenVLA, whose tokenizer allows relaxing. VSpark with exact checking gets one point two seven times, at seventy-six point eight percent success. Spec-VLA with relaxed checking gets one point two three times at seventy-five percent. KERV, in the authors' reproduction, runs at zero point nine six times, slower than plain decoding.

Does continuation reuse really hold up? Table 5 says yes. After a token is rejected, what the big model had predicted next is still correct after the correction forty-five point four percent of the time on pi-zero FAST, and fifty-four point nine percent on ActionCodec, roughly eighteen points more often than the draft's own guess.

The ablation is in Table 7. Adding components to DSpark one at a time, feature alignment gives the biggest jump on pi-zero FAST, from one point six nine to one point nine times. On ActionCodec, continuation reuse contributes most. With all three, it's one point nine three and two point one times.

And one negative result. Moved over to language models, Qwen3-4B and Gemma-4-12B, continuation reuse gives no speedup, and in some cases slightly less. One possible explanation the authors give is that in text, changing one word often changes what should come next, while action sequences are less like that.

My read is that the most valuable thing here is the trade-off it refuses to make. Instead of buying speed by relaxing verification, it gets close to two times faster on several models with exact checking, purely by making the draft smarter. For robots, that's practical: no tolerance to tune, and by design no action errors beyond what the original model would make.

My read is that the limits matter too. Every result is in simulation, and what's measured is decoding time, not control frequency on a real robot. G0.5 only gets one point two eight times. And it only applies to VLAs that generate tokens one by one; diffusion-style models that output continuous actions are outside this framework.

### Limitations

The authors list three limitations. First, with hybrid attention like G0.5's, the recurrent state in the linear attention layers makes parallel tree checking awkward, which can limit the speedup even when acceptance improves.

Second, continuation reuse only helps when a rejection leaves the following predictions unchanged, which happens in roughly half of rejections and varies with the tokenizer.

Third, the noisy rollouts need a simulator. VSpark does help a model trained on real-robot data, but collecting noisy rollouts on a real robot without a simulator still needs further study.

### Future work

Looking ahead, the authors name two directions: better parallel verification for hybrid attention architectures, and collecting noisy rollouts without a simulator.

My read is that as VLAs get bigger, inference speed will look more and more like a hard constraint. VSpark's approach, putting the structure of the action space into the draft and the candidates rather than into the acceptance rule, is one later work on autoregressive VLAs should build on.
