## 中文讲解

### 开场

这里是每日前沿文章。今天讲一篇北京大学牵头的论文，合作单位有新加坡国立大学、英伟达、同济大学和芝加哥大学，论文叫 PyRUA-Dex。

它问的问题很直接，灵巧手的操作，能不能不靠人类示范，而是让 coding agent 写一段程序来完成。论文报告，在两个仿真 benchmark 上，这样的程序都超过了所有用示范训练的策略，真机上还能弹钢琴、用毛笔写字。

### 问题

先说背景。今天教机器人做灵巧操作，主要靠示范数据。模仿学习，VLA，也就是视觉语言动作模型，还有 world-action model，基本都是拿人遥操作录下来的数据训练的。

可是多指灵巧手的高质量示范很难拿到。把人类视频映射到机器手上不够精确，遥操作的时候，操作员感受不到接触的力，外骨骼采集又很难规模化。而且数据和采集用的那只手绑定，换一只手，就得重新采、重新训。

结果就是，在 Bench2Dex 这个双手灵巧操作评测里，最强的训练策略也只能成功一半多一点的回合，场景外观或物体位置一被扰动，它们的表现全都下降。

### 以前的方法

另一条路，是让大模型写代码控制机器人。程序化策略，就是把行为写成一段程序，而不是一堆网络权重，所以能读、能测、能验证。

但以前的机器人程序，通常是根据提示一次写成，或者在一个很小的专用语言里搜索出来，没有针对各种不同的摆放，反复打磨鲁棒性。

对灵巧手来说，之前的做法是让 Agent 一直留在回路里，每个测试回合都由它观察、它下指令。论文指出，这样每个回合要消耗数百万 token，在步数预算内，还是大多数回合失败。

### 核心想法

作者的想法是，让 coding agent 在开发阶段把任务学一次，产出一段程序，测试的时候，这段程序自己跑，不再调用任何大模型。

学这样一段程序，有两个不同的难题。第一是找到解法，用什么抓法，两只手谁先谁后，每一步怎么动，这是一个搜索问题。

第二是让解法稳定。一个灵巧任务由好几个连续阶段组成，总成功率等于每个阶段成功率的乘积。论文举的例子是，五个阶段各 80%，总成功率只有 33%。

所以总成功率不会超过最弱的那个阶段。要提高鲁棒性，就得在很多摆放上测出每个阶段的成功率，然后专门修最不可靠的那一个，也就是瓶颈。

### 方法

方法正好对应这两个难题，分两个阶段，所有学习都在仿真里完成。Agent 用的是 Codex CLI，模型是 GPT-6 Astra，每个 Agent 有自己的 shell 和自己的仿真器。

第一阶段叫探索。八个 Agent 并行做同一个任务，每个负责一个还没解决的阶段。它们可以给仿真器存档，失败了就读档重来，每个摆放最多八次，这样重试一个阶段，不用每次从头跑前面的阶段。

每个 Agent 的尝试，都写进一个共享记忆，记下到了哪个阶段，用了什么代码。一个 Agent 解决的阶段，马上变成其他 Agent 的起点。

最后，一个负责蒸馏的 Agent 读完所有评测记录，写出一份任务库，再选出一段程序，或者从不同 Agent 那里，各取最擅长的那个阶段，拼成一段。

第二阶段叫精修，只用一个 Agent。先让程序在 32 个新摆放上跑，按阶段拆解失败，找出瓶颈。Agent 一次修一个阶段，先修瓶颈，修完再在几十个新摆放上测。

为了防止只在训练摆放上好看，每用 160 个训练摆放，就在一组保留摆放上评测一次，Agent 只能看到成功的计数，最后选保留集上最好的版本。另有 32 个 Agent 从没见过的验证摆放，新程序在上面不比旧的差，才能替换。

程序本身是普通的 Python，结构固定，一个 setup 函数先测量场景，然后每个阶段一个函数，按顺序执行。某个阶段失败，不会终止整个回合，只要还有步数，失败的阶段会被重新调用。

同一套代码，怎么驱动不同的手。作者做了一个叫 codebox 的工具层，从机器人的描述文件生成。它把每只手建模成手指和拇指，算出每组手指能抓多宽的物体，再提供抓取、握紧、检查是否握住这样的调用。是否接触，靠指尖触觉，以及关节指令和实际位置之间的滞后来判断。

测试时，程序只拿普通策略也能拿到的输入，标定过的相机、关节位置和指尖触觉，不读仿真器状态，不调用大模型，按机器人的控制频率运行。

### 实验和效果

先看 Bench2Dex。它有 26 个双手任务，涉及 12 种机械臂加灵巧手的组合。PyRUA-Dex 得分 72.9，论文称这是排行榜上新的 SOTA，之前最好的 ME-Dex 1.5 是 70.5。

它的成功率是 60.6%，阶段完成率 82.3%，都高于所有训练出来的策略。而且对扰动很稳，四种扰动通道之间，成功率只差 4.1 个百分点。相比之下，GR00T N1.7 从 39.4% 掉到 13.2%。

精修这一步很关键，它把成功率从 44.6% 提到 60.6%，26 个任务里有 20 个提高。论文分析了探索后的失败，68% 的失败回合还剩至少三成步数，只有 2% 是步数用完，也就是说，失败来自某个不稳的阶段，而不是时间不够。

第二个 benchmark 是 DexJoCo，换了仿真器，换成 16 自由度的 Allegro 手，而且不给阶段信息，只告诉 Agent 成没成功。在物体随机化的设置下，成功率 88.5%，全随机化下 81.0%，最强的训练策略 π0.5 分别是 54.1% 和 40.3%。11 个任务，每一个都超过了最好的训练策略。

真机上，平台是两台 Franka FR3 机械臂，加两只 22 个关节的 Sharpa 灵巧手。作者先根据标定搭了一个 MuJoCo 仿真，并且辨识了手的驱动参数，仿真关节和真实关节的误差，从 0.80 到 3.1 度，降到了 0.12 到 0.18 度。

然后在仿真里学，在真机上跑，真机暴露的问题写回仿真，再精修下一轮。六个任务的仿真验证成功数，从 119 个提高到 168 个，一共 192 个。真机上，程序能把方块放进篮子，叠三层方块，用毛笔写出 Dex，还能双手弹钢琴。

钢琴任务还沉淀出一个可以复用的演奏技能。有了它，学一首新曲子，通常只要 30 分钟到一小时的迭代。

### 和以前方法的对比

最有意思的对比，是和同一个模型在线操控比。在线 Agent 同样是 GPT-6 Astra，但每个测试回合都要它亲自观察、下指令。在 benchmark 规定的步数内，冻结的程序在全扰动通道成功 61.5%，是在线 Agent 25.6% 的 2.4 倍。

在线 Agent 要给到十倍的步数预算，才追得上 61.5%，而那时每个回合要花 3370 万 token。

开发成本论文也算了。每个任务，探索的中位数是 4.27 亿 token、21.6 个 Agent 小时，精修是 2.14 亿 token、14.8 个 Agent 小时。作者称，开发全部 26 个任务用的 token，还不到在线 Agent 跑完 5200 个测试回合的三分之一，而且之后每多跑一个回合，程序都不再花 token。

我的判断是，这篇最有价值的地方，是把大模型的推理，从测试时搬到了开发时。大模型不再当实时控制器，而是当工程师，写出一段能读、能测、能直接部署的程序。

我的判断是，也要看到这个优势有边界。它没有赢下所有任务，26 个任务里，只有 15 个超过最好的训练策略，另外 11 个，还是训练出来的策略领先。

### 局限

作者自己总结得很直白，coding agent 写运动写得好，写持续接触写得差。程序在几何、顺序和时机决定成败的任务上最强，在需要连续控制力和防打滑的任务上最弱，比如煎锅、两手之间倒酒、拼图，都是训练策略领先。

原因之一，是程序靠明确的目标和阈值来动作，而仿真里的指尖触觉渲染得很粗，程序主要从关节滞后来推断接触。

另外，精修只能加强在部分摆放上已经能成功的阶段，一个阶段如果从来没成功过，还得回到探索去解决。而且每个任务都是单独学的。

还有很重要的一条，真机部分，论文展示了程序在机器人上运行，但可靠性是在标定过的仿真里测的，没有在真机上做多次重复试验来统计成功率。

### 未来方向

作者提了三个方向。第一，把接触阶段交给学习出来的控制器，并且用更逼真的触觉仿真来开发程序。

第二，跨任务迁移，用相关任务的任务库，给新任务的探索起个头，钢琴曲已经说明，同一类任务里，技能可以复用。第三，在真机上做系统评测，统计重复试验的成功率。

我的判断是，接下来最值得看的是真机成功率。仿真里的数字很亮眼，但灵巧操作真正难的是接触，而这恰恰是仿真最不准、程序最弱的地方。

## English walkthrough

### Intro

This is Daily Frontier Papers. Today's paper is led by Peking University, with co-authors from the National University of Singapore, NVIDIA, Tongji University and the University of Chicago. It's called PyRUA-Dex.

It asks a blunt question. Can a robot learn dexterous hand skills without any human demonstrations, by having a coding agent write a program instead? The paper reports that these programs beat every demonstration-trained policy on two simulated benchmarks, and on a real robot they play piano and write with a brush.

### Problem

Some background first. Dexterous manipulation today is learned mostly from demonstrations. Imitation learning, vision-language-action models, and world-action models are all trained on episodes that a human recorded by teleoperation.

But good demonstrations for multi-fingered hands are scarce. Retargeting human video to a robot hand is imprecise, teleoperators get no force feedback during contact, and exoskeletons are hard to scale. On top of that, the data is tied to the hand it was collected on, so a new hand means new data and retraining.

The result: on Bench2Dex, a benchmark of two-handed dexterous tasks, the strongest trained policies succeed in little more than half the episodes, and every one of them degrades when the scene's appearance or object placement is perturbed.

### Prior work

The alternative is to have language models write code that controls the robot. A programmatic policy represents behavior as a program instead of network weights, so you can read it, test it and verify it.

But robot programs have typically been written once from a prompt, or found by search in a small domain-specific language. They aren't refined to stay robust across many different layouts.

And for dexterous hands, the agent has so far stayed in the loop, observing and acting in every test episode. The paper notes that this burns millions of tokens per episode, and still fails most episodes within the step budget.

### Key idea

The authors' idea is to let a coding agent learn the task once, during development, and hand over a program. At test time the program runs on its own and never calls a language model.

Learning such a program means solving two separate problems. The first is finding a solution at all: which grasps, which hand goes first, and what motions finish each step. That's a search problem.

The second is making that solution reliable. A dexterous task is a chain of stages, and the overall success rate is the product of the stage success rates. The paper's example: five stages at eighty percent each give only thirty-three percent overall.

So the overall rate can never beat the weakest stage. To make a program robust, you measure every stage over many layouts and fix the least reliable one, the bottleneck.

### Method

The method has two stages that match those two problems, and all learning happens in simulation. The agents are Codex CLI sessions running GPT-6 Astra, each with its own shell and its own simulator.

Stage one is exploration. Eight agents work on the same task in parallel, each assigned a stage that hasn't been solved yet. They can checkpoint the simulator and reset to it, up to eight times per layout, so they can retry one stage without replaying everything before it.

Every attempt goes into a memory shared by all the agents, recording which stages it reached and the code that got there. A stage one agent solves becomes everyone else's starting point.

At the end, a distilling agent reads all the evaluation records, writes a task library, and picks one program, or stitches one together by taking each stage from whichever agent handled it best.

Stage two is refinement, with a single agent. First the program runs on thirty-two fresh layouts, and the failures are broken down by stage to find the bottleneck. The agent repairs one stage at a time, bottleneck first, then re-tests on dozens of new layouts.

To keep it honest, every hundred and sixty training layouts the current version is evaluated on a held-out set where the agent only sees the counts, and the best held-out version is selected. There's also a set of thirty-two validation layouts no agent ever sees. A new program only replaces the old one if it does no worse there.

The program itself is plain Python with a fixed shape: a setup function that measures the scene, then one function per stage, run in order. A failed stage doesn't end the episode. While steps remain, failed stages get called again.

So how does one codebase drive many different hands? The authors built a tool layer called the codebox, generated from the robot's description file. It models each hand as fingers and a thumb, works out which object widths each set of fingers can hold, and exposes calls like grasp, close, and check whether something is held. Contact is read from fingertip touch, and from the lag between where a joint was commanded to go and where it actually is.

At test time the program gets only what an ordinary policy gets: calibrated cameras, joint positions and fingertip touch. No simulator state, no language model, and it runs at the robot's control rate.

### Results

Start with Bench2Dex: twenty-six two-handed tasks across twelve arm and hand combinations. PyRUA-Dex scores seventy-two point nine, which the paper reports as a new state of the art on the leaderboard, ahead of the previous best, ME-Dex 1.5, at seventy point five.

Its success rate is sixty point six percent and its stage completion is eighty-two point three percent, both above every trained policy. It's also stable under perturbation: success varies by only four point one points across the four perturbation channels. GR00T N1.7, by contrast, drops from thirty-nine point four to thirteen point two percent.

Refinement does a lot of the work. It lifts success from forty-four point six to sixty point six percent, with gains on twenty of the twenty-six tasks. Looking at failures after exploration, sixty-eight percent ended with at least thirty percent of the steps unused, and only two percent ran out of steps. So failures came from an unreliable stage, not from running out of time.

The second benchmark is DexJoCo, with a different simulator, the sixteen-joint Allegro hand, and no stage information at all, just success or failure. PyRUA-Dex succeeds in eighty-eight point five percent of episodes with randomized objects and eighty-one percent under full randomization, against fifty-four point one and forty point three for the strongest trained policy, pi zero point five. It beats the best trained policy on every one of the eleven tasks.

On real hardware, the platform is two Franka FR3 arms with two Sharpa hands of twenty-two joints each. The authors first built a MuJoCo simulation from the robot's calibration and identified the hands' drive parameters, cutting the gap between simulated and real joints from between zero point eight and three point one degrees down to between zero point one two and zero point one eight degrees.

Then they learn in simulation, run on the robot, write what the robot reveals back into the simulation, and refine again. Across six tasks, simulated validation successes rose from one hundred nineteen to one hundred sixty-eight out of one hundred ninety-two. On the real robot, the programs drop cubes in a basket, stack three cubes, write the word Dex with a brush, and play piano with both hands.

The piano work also produced a reusable player skill. With it, a new piece typically takes thirty minutes to an hour of iteration.

### Comparison

The most interesting comparison is against the same model acting online. The online agent is also GPT-6 Astra, but it observes and acts in every test episode. At the benchmark's step budget, the frozen programs succeed on sixty-one point five percent of the fully perturbed episodes, two point four times the online agent's twenty-five point six.

The online agent only matches sixty-one point five percent when given ten times the step budget, and by then it's spending thirty-three point seven million tokens per episode.

The paper also counts development cost. Per task, exploration takes a median of four hundred twenty-seven million tokens and twenty-one point six agent hours, and refinement two hundred fourteen million tokens and fourteen point eight agent hours. The authors say developing all twenty-six tasks used less than a third of the tokens the online agent spends on the benchmark's five thousand two hundred test episodes, and every further episode of a program costs no tokens at all.

My read is that the real contribution here is moving the model's reasoning from test time to development time. The language model stops being a real-time controller and becomes an engineer, producing a program you can read, test and deploy.

My read is also that the advantage has limits. It doesn't win everywhere: PyRUA-Dex beats the best trained policy on fifteen of the twenty-six tasks, and trained policies still lead on the other eleven.

### Limitations

The authors put it plainly: coding agents write motion well and sustained contact poorly. Programs are strongest where geometry, order and timing decide the task, and weakest where continuous control of force and slip matters. On the frying pan, the pour from hand to hand, and the jigsaw puzzle, trained policies lead.

Part of the reason is that programs act through explicit targets and thresholds, while the simulated fingertip sensors render contact coarsely, so the programs mostly infer contact from joint lag.

Also, refinement can only strengthen stages that already succeed on some layouts. A stage that never works is still an exploration problem. And every task is learned separately.

One more that matters a lot: on the real robot, the paper shows the programs running, but measures their reliability in the calibrated simulation, not over repeated hardware trials.

### Future work

The authors point to three directions. First, hand the contact phases to learned controllers, and develop programs against more faithful tactile simulation.

Second, transfer across tasks, seeding a new task's exploration with the libraries of related tasks, as the piano pieces already show within one family. Third, a systematic evaluation on hardware, with success rates over repeated real trials.

My read is that the number to watch next is real-robot success rate. The simulated results are strong, but the hard part of dexterity is contact, and that's exactly where the simulation is least faithful and the programs are weakest.
